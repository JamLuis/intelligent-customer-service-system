# 客户汇报：结合船舶告警与巡查卫士的角色场景卖点说明

> 适用场景：面向客户说明 LightGraph 二开智能客服 / 业务诊断系统的价值。重点不是展示一个“会聊天的机器人”，而是展示一个能理解业务系统、接口、数据库、页面、设备和工单闭环的“业务协同与诊断中台”。

## 1. 一句话定位

本系统可以作为客户、客服、实施、运维、研发和管理层共同使用的智能业务助手：把后台接口能力、数据库结构、业务文档、运行日志、设备状态、告警记录、巡查记录、前端页面入口组织成知识图谱，再通过受控 MCP 工具按权限调用真实系统能力，帮助用户快速回答“是什么、为什么、查哪里、怎么处理、谁来负责、处理到哪一步”。

对客户来说，购买的不是一个问答框，而是一套能降低沟通成本、缩短故障定位时间、沉淀业务知识、提升售后响应能力、辅助运营决策的智能化交付能力。

## 2. 为什么 app-ship-alarm 与 guard_platform 能证明价值

app-ship-alarm 是后端业务系统，覆盖船舶告警、AI 设备、巡查记录、船舶定位、围栏、通知、MQTT、短信邮件、第三方开放 API、视频抓图、数据统计等能力。

guard_platform 是巡查卫士前端平台，覆盖地图船舶动态、最新告警、视频监控、巡查计划、巡查记录、围栏打卡、AI 设备管理、固件升级、告警过滤、统计看板、系统权限等页面。

这两个项目组合后，正好形成客户真实使用链路：页面上看见问题、客服接到咨询、系统调用后端接口查询、结合数据库和图谱解释原因、必要时生成工单交给实施/运维/研发处理，并把过程留痕。

## 4. 面向客户的核心卖点

### 4.1 它能理解业务，不只是匹配文档

传统客服知识库只能回答“某个按钮在哪里”。本系统通过图谱把页面、接口、数据库、配置、任务、设备、告警状态连接起来，可以回答更深的问题。

例如客户问：“为什么长江2号今天有告警，但平台地图上点进去没有最新告警？”

系统不只是搜索“最新告警”四个字，而是按链路分析：

1. 前端地图弹窗来自 guard_platform 的船舶动态模块。
2. 弹窗可显示当日告警数、打开视频监控、打开最新告警。
3. 最新告警依赖后端告警列表、船舶 ID、机构/设备权限、时间范围、告警确认/处理状态。
4. 如果船舶未上报定位，前端会提示“船舶未上报定位信息”，地图点位也可能无法定位。
5. 如果用户没有对应 deviceIds 或 tenant 权限，即使后端有告警，前端也可能不展示。

这就是从“查文档”升级到“理解业务链路”。

### 4.2 它能查真数据，但不会裸奔式暴露接口

客户常会问：“你是不是把后台所有接口都给 AI 调了？安全吗？”

汇报时要明确：系统不会把所有 Controller 原样暴露成 MCP。MCP 暴露的是经过治理的业务能力，比如：

| MCP 能力 | 背后可能调用 | 安全控制 |
| --- | --- | --- |
| 查询某船告警摘要 | 告警列表、告警详情、船舶信息 | 只读、按租户/船舶权限过滤、字段脱敏 |
| 查询驾驶舱抓图失败原因 | 第三方配置、船舶信息、GB 通道配置、视频服务状态 | 默认只诊断，不自动重试生产抓图 |
| 查询账号/设备质保提醒发送状态 | Redis 标记、notice 记录、MQTT topic、定时任务状态 | 不允许越权查看其他租户用户隐私 |
| 查询巡查记录异常原因 | 巡查计划、巡查点、围栏半径、打卡位置、证明材料 | 只展示授权范围内的巡查数据 |
| 生成工单和处理建议 | 工单系统、知识图谱、历史案例 | 高风险动作需人工确认 |

这能向客户证明：AI 能接入真实业务，但边界是受控的。

### 4.3 它能把一次排障沉淀成长期资产

每次客服或运维处理问题后，系统都可以沉淀：问题描述、证据链、根因、处理动作、涉及接口、涉及表、涉及页面、最终结论。下一次同类问题出现时，不再从零开始。

例如“驾驶舱抓图失败”第一次需要研发解释接口流程；第二次系统就能自动提示：先查 token，再查 shipName 是否一致，再查 jww_third_api_configure 权限，再查 jww_ship_info，再查 jww_dvr_media_gb_config 是否存在含“驾驶”的通道，再查 VideoService.manualCapture 返回是否为空。

这就是客户愿意持续使用的原因：越用越懂业务，越用越省人。

## 5. 角色一：客服坐席副驾

### 5.1 解决的问题

客服每天面对的是模糊问题：客户不会说接口名、表名、字段名，只会说“告警看不到”“船不显示”“视频打不开”“账号没提醒”“巡查结果不对”。

客服副驾的作用是把模糊描述转换成可查询、可解释、可派单的问题。

### 5.2 app-ship-alarm 示例：客户说“告警接口查不到数据”

客户原话可能是：“我们对接你们船舶告警开放 API，昨天还有数据，今天查不到。”

系统可自动追问和排查：

| 排查点 | 系统能做什么 | 对客服的帮助 |
| --- | --- | --- |
| Token 是否有效 | 检查是否通过 POST /dnl/api/token 获取 Bearer Token，token 是否超过 1 小时 | 避免客服只回答“重新登录试试” |
| 时间范围是否合规 | 检查 /dnl/api/alarm/list 的 updateTimeStart/updateTimeEnd 是否超过 7 天 | 快速指出参数错误 |
| 租户权限是否匹配 | 根据 token 关联 tenantId，只返回授权租户告警 | 解释“有告警但查不到”的权限原因 |
| 告警状态是否符合预期 | 查看 isDeal、confirmStatus、dealTime、alarmTag、alarmLevel | 区分未处理、已处理、误报、超时升级 |
| 船舶字段是否完整 | 查看 shipMmsi、shipCn、shipName、shipType、alarmAddress | 帮客户确认对接字段含义 |

系统给客服的标准回复可以是：

“已按您的 access_token 查询，当前 token 对应租户为 XX。您本次请求时间范围为 10 天，超过接口约定的 7 天限制，因此返回为空/失败。建议将查询拆成两个时间段。若调整后仍无数据，我可以继续检查该租户下对应时间段是否存在 alarmCode、isDeal、confirmStatus 数据。”

这类回复比“请检查参数”更有说服力。

### 5.3 guard_platform 示例：客户说“地图上船点不显示”

客户原话可能是：“巡查卫士地图上看不到某条船，但是后台有船舶资料。”

系统可按前后端链路判断：

| 排查点 | 证据来源 | 可能结论 |
| --- | --- | --- |
| 船舶是否有实时定位 | guard_platform 地图模块调用 shipTravelReal / getRealShip | 船舶未上报定位，前端会提示“船舶未上报定位信息” |
| 当前账号是否有权限 | 前端 state.user.deviceId、部门树、tenant 权限 | 用户无该船或该部门权限 |
| 地图视野是否过滤 | 地图可视区域、船舶点绘制逻辑 | 船在视野外或被筛选条件过滤 |
| 定时刷新是否异常 | 地图定时器、事件监听、异步状态 | 可能是刷新或组件状态问题 |
| 船舶基础数据是否绑定 | 船舶 MMSI、CN、定位器编号、设备绑定关系 | 船舶资料存在但未绑定定位设备 |

客服可直接拿到清晰结论，而不是转给前端、后端、实施三方来回确认。

## 6. 角色二：业务查询助手

### 6.1 解决的问题

客户业务人员不一定知道系统菜单和字段。业务查询助手可以让他们用自然语言查询：

- “今天长江2号有几条告警？哪些还没处理？”
- “本周误报最多的告警类型是什么？”
- “某机构下面哪些 AI 设备快过保？”
- “昨天巡查有哪些漏检点？”
- “哪些船舶没有上报定位？”
- “这个告警有没有视频或图片证据？”

### 6.2 app-ship-alarm 示例：自然语言查告警闭环

客户问：“上周一级告警处理闭环怎么样？”

系统可组合查询：告警列表、处理状态、确认状态、处理时间、统计接口，并生成业务语言结论：

“上周一级告警共 X 条，已确认 X 条，已处理 X 条，超时未确认 X 条，超时未处理 X 条。闭环率较低的对象集中在 XX 船舶/XX 机构，主要告警类型为 XX。建议优先复盘这几类场景。”

这对应 app-ship-alarm 里的告警处理、确认、统计能力，也能连接 guard_platform 的看板和告警详情页面。

### 6.3 guard_platform 示例：自然语言查巡查质量

客户问：“昨天巡查有没有漏检？证据在哪？”

系统可结合巡查计划、巡查记录、巡查点、围栏半径、打卡位置、证明材料，输出：

“昨天巡查记录中，XX 线路有 2 个点位漏检，1 个点位异常。漏检点位为 A、B；A 点围栏半径为 50 米，未产生有效打卡证明；B 点有打卡记录但不在围栏内。相关图片/视频证明可在巡查记录详情中查看。”

这对客户的价值是：管理者不需要一个页面一个页面找，系统直接把结果和证据组织好。

## 7. 角色三：运维诊断助手

### 7.1 解决的问题

运维最难的是跨组件排查：接口正常不代表数据正常，数据正常不代表 MQTT 正常，MQTT 正常不代表前端展示正常。运维诊断助手可以把链路串起来。

### 7.2 示例：账号过期提醒没有收到

app-ship-alarm 已有账号过期提醒和设备质保到期提醒设计：定时任务查即将过期用户，写 Redis，生成 jww_notice，向 commonNotice_{userId} 或 commonNotice_{tenantId} 推送 MQTT。

客户问：“为什么某用户没有收到账号过期提醒？”

系统可按链路排查：

| 链路 | 检查内容 | 可能原因 |
| --- | --- | --- |
| 用户数据 | status=0，accountEffectiveTimeSet=1，accountEffectiveTime 是否在 30 天内 | 用户未启用自定义有效期或不在提醒范围 |
| 定时任务 | getAccountExpiresUserInfo 是否执行 | XXL Job 未配置或执行失败 |
| Redis 缓存 | nearAccountExpiresUserInfo:{userId} 是否存在 | 缓存未写入或已过期 |
| 防重复标记 | nearAccountExpiresUserInfoNoticeTag:{userId} 是否存在 | 今天已提醒过，系统防重复 |
| Notice 记录 | jww_notice 是否有 noticeType=2 | 数据库记录是否生成 |
| MQTT 推送 | commonNotice_{userId} 是否发送 | topic 或客户端订阅异常 |

运维不需要从代码里翻完整逻辑，系统直接给出排查顺序和证据。

### 7.3 示例：设备质保到期提醒没有推送

系统可排查设备是否进入临期范围、Redis 防重标记是否存在、notice 是否写入、MQTT topic 是否为 commonNotice_{tenantId}、原有钉钉/短信发送是否成功。

客户价值：这类问题原本会涉及业务、后端、消息、前端通知多方，系统能把责任边界说清楚。

### 7.4 示例：AI 设备配置下发失败

从 guard_platform 的接口看，AI 设备涉及设备列表、未绑定设备、摄像头绑定、算法配置、媒体通道、网络配置、GB28181、重启、密码重置、TTS、固件升级计划等能力；app-ship-alarm 后端通过 MQTT 向设备控制 topic 下发配置。

客户问：“设备在线，但算法配置没有生效。”

系统可诊断：

1. 平台是否保存了对应 AI 设备和任务配置。
2. 设备是否绑定了摄像头/媒体通道。
3. 算法配置是否同步到设备。
4. MQTT 下发是否成功。
5. 设备是否回传状态。
6. 固件版本是否支持该算法。
7. GB28181 或视频通道是否影响取流。

这就是把“设备问题”拆成“平台配置、消息下发、设备回执、视频链路、固件能力”几个可验证环节。

## 8. 角色四：实施交付顾问

### 8.1 解决的问题

实施人员面对的是现场交付：船舶资料、定位器、摄像头、围栏、巡查线路、人员规则、AI 设备、固件、视频平台、第三方对接。出错时通常不是代码 bug，而是配置链路不完整。

### 8.2 示例：配置一条船舶从地图展示到告警闭环

系统可给实施人员生成配置检查清单：

| 步骤 | 要检查的内容 | 关联能力 |
| --- | --- | --- |
| 船舶基础资料 | shipName、shipMmsi、shipCn、shipType、tenantId | 船舶管理、开放 API 字段 |
| 定位设备绑定 | ship_locator_code / 设备编号是否绑定 | 地图船舶动态、W6/AIS 数据 |
| 用户权限 | 当前账号是否拥有机构/船舶权限 | 前端 deviceIds、部门树 |
| 告警设备 | AI 设备是否绑定该船舶/场景 | aiDeviceList、alarmDeviceList |
| 视频通道 | 驾驶舱摄像头是否存在，media_name 是否含“驾驶” | jww_dvr_media_gb_config、视频抓图 |
| 告警类型 | 告警类型、过滤规则、误报规则是否配置 | alarmType、filterRule |
| 处置闭环 | 是否能确认、处理、批量处理、统计 | DealController、DataStatisticsController |

这类清单可以直接变成实施 SOP，降低人员经验依赖。

### 8.3 示例：配置巡查计划与围栏打卡

系统可指导实施人员：

1. 建立巡查线路和巡查点。
2. 设置围栏半径。
3. 设置巡查人员规则和时间规则。
4. 验证打卡是否在围栏内。
5. 验证巡查状态是否能正确显示正常、异常、未知、漏检。
6. 验证巡查证明图片/视频是否生成。

客户价值：系统不仅能回答售后问题，还能帮助项目交付标准化。

## 9. 角色五：研发排障助手

### 9.1 解决的问题

研发常收到不完整问题：“页面不显示”“接口报错”“数据不对”。研发排障助手可以先帮研发把问题翻译成代码和接口层面的定位信息。

### 9.2 示例：驾驶舱抓图失败定位

蓝水木驾驶舱抓图接口 POST /lanshuimuVideoPic 涉及外部 token 验证、openId、shipName、接入方配置、船舶定位器编号、权限过滤、GB 通道、海康 manualCapture、图片下载和 Base64 返回。

系统可自动生成研发排查单：

| 检查点 | 关联对象 | 失败表现 |
| --- | --- | --- |
| token 验证 | open.api.validate.url | token invalid、外部 code 非 200 |
| shipName 比对 | 外部 data.shipName 与请求 shipName | 船名不一致导致认证失败 |
| 接入方配置 | jww_third_api_configure | openId 无配置或 apiType 不匹配 |
| 船舶存在性 | jww_ship_info.ship_locator_code | msaShipId 找不到船 |
| 权限过滤 | filter_type / filter_id | 无权限获取该船数据 |
| 驾驶舱通道 | jww_dvr_media_gb_config media_name LIKE '%驾驶%' | 未找到驾驶舱摄像头通道 |
| 抓图服务 | VideoService.manualCapture(gbNum) | code=201，未获取到图片 |
| 图片下载 | picUrl HTTP 下载 | 图片下载失败 |

对研发来说，这比“客户说抓图失败”更可处理。

### 9.3 示例：前端地图卡顿或内存泄漏

guard_platform 已有地图优化材料，涉及定时器清理、事件监听清理、异步状态保护、JSON.parse 保护、坐标校验、批量覆盖物处理。

系统可把用户反馈“地图越用越卡”转换成研发检查项：

- 地图组件销毁时是否清理定时器。
- 地图事件监听是否重复绑定。
- 异步请求返回后组件是否已销毁。
- 覆盖物是否批量清理。
- 船舶坐标是否存在非法值导致异常渲染。
- JSON.parse 是否对空值/非法值做保护。

客户价值：问题进入研发前已经被结构化，减少沟通损耗。

## 10. 角色六：运营分析参谋

### 10.1 解决的问题

管理层关心的不是单条告警，而是趋势、风险和投入产出。

系统可以把 app-ship-alarm 的统计接口、guard_platform 的看板、大屏、告警处置、巡查质量、设备健康统一成自然语言经营分析。

### 10.2 示例：告警运营日报

系统可每日生成：

- 今日告警总数、一级/二级告警数量。
- 待确认、已确认、误报、已处理、超时未处理数量。
- 闭环率、误报率、处理及时率。
- 告警最多的船舶、机构、场景、设备。
- 视频/图片证据缺失的告警。
- 建议重点关注的设备或区域。

客户价值：从“系统里有数据”升级为“系统主动给管理建议”。

### 10.3 示例：巡查质量周报

系统可汇总：

- 巡查计划执行率。
- 正常、异常、未知、漏检点位数量。
- 经常漏检的线路/点位。
- 打卡不在围栏内的记录。
- 缺少证明材料的巡查记录。
- 一线人员执行差异。

客户价值：帮助甲方把平台从“监控工具”用成“管理工具”。

### 10.4 示例：设备健康分析

系统可汇总：

- AI 设备在线/离线情况。
- 固件版本分布和升级计划进度。
- GB28181 配置异常设备。
- 视频通道缺失或取流异常设备。
- 临近质保到期设备。
- 告警高发但处置低效的设备。

客户价值：提前发现设备风险，减少突发故障。

## 11. 角色七：审计与权限助手

### 11.1 解决的问题

政企客户通常会担心：AI 是否会越权查数据？是否会泄露敏感信息？是否会直接执行危险操作？

系统需要把“可控、可审计”作为卖点，而不是回避。

### 11.2 可控边界

| 边界 | 说明 |
| --- | --- |
| 权限继承 | AI 查询继承当前用户的租户、角色、船舶、设备权限 |
| 默认只读 | 首期只开放查询、解释、诊断、工单草拟，不自动修改生产数据 |
| 高风险确认 | 批量处理告警、重启设备、修改配置、清除规则等动作必须人工确认 |
| 字段脱敏 | token、手机号、账号、密钥、内部 URL 等敏感字段按规则脱敏 |
| 调用留痕 | 每次 MCP 调用记录用户、时间、能力、参数摘要、结果摘要 |
| 证据可追溯 | AI 结论必须能追溯到接口、表、文档、日志或历史工单 |

### 11.3 对客户的表达方式

“我们不是把所有后台接口直接交给 AI，而是把接口封装成受控业务能力。AI 能帮你查、帮你判断、帮你生成建议，但涉及生产变更和敏感数据时一定受权限、审批和审计约束。”

这句话能增强客户信任。

## 13. 客户最容易买单的讲法

### 13.1 对一线用户

“以后你不用记那么多菜单，也不用知道接口名。你直接问：某条船为什么没告警、某个巡查点有没有漏检、某个设备为什么不在线，系统会带着证据告诉你答案。”

### 13.2 对客服主管

“它能把一线客服从传话筒变成专业坐席。系统会自动补齐排查步骤、证据链和标准回复，减少反复转研发。”

### 13.3 对运维负责人

“它能把接口、数据库、Redis、MQTT、设备状态、视频通道串成一条排障链。不是只告诉你报错，而是告诉你下一步查什么。”

### 13.4 对项目经理

“它能把项目交付经验沉淀为 SOP，新人也能按步骤配置船舶、围栏、巡查、设备和告警规则，减少现场依赖老员工。”

### 13.5 对甲方管理层

“它能把平台数据转成管理建议：哪些船风险高、哪些设备不健康、哪些告警处理慢、哪些巡查点经常漏检。系统不只是记录问题，还能推动管理改进。”

### 13.6 对安全合规负责人

“AI 不直接裸调全部后台接口，所有查询都受权限控制、敏感字段脱敏、操作留痕，高风险动作需要人工确认。”

## 14. 试点建设建议

### 14.1 第一阶段：做 5 个最能打动客户的场景

建议先做以下试点，不追求一次覆盖所有系统：

1. 船舶告警查询与状态解释。
2. 地图船舶不显示诊断。
3. 驾驶舱抓图失败排查。
4. 账号/设备质保提醒未收到排查。
5. 巡查漏检与围栏打卡证据查询。

这 5 个场景覆盖客服、运维、实施、研发、管理层，适合用于客户演示。

### 14.2 第二阶段：接入受控 MCP 能力

优先封装只读工具：

- 查询告警摘要。
- 查询船舶基础信息。
- 查询船舶定位状态。
- 查询巡查记录详情。
- 查询 AI 设备状态。
- 查询 notice/MQTT 推送状态。
- 查询第三方接口配置摘要。
- 查询视频通道配置摘要。

暂不开放自动处理告警、重启设备、修改配置、删除规则等高风险写操作。

### 14.3 第三阶段：建设业务知识图谱

图谱不应直接镜像数据库，而应治理成业务概念：

- 船舶、设备、摄像头、告警、告警类型、处置、确认、误报、巡查计划、巡查点、围栏、人员、租户、通知、第三方接入方。
- 接口、页面、字段、表、任务、MQTT topic、Redis key、错误码、历史案例之间的关系。
- 常见问题到排查链路的关系。

这样图谱才适合客服和管理层使用，而不是只给技术人员看表结构。

### 14.4 第四阶段：形成可售卖闭环

形成以下交付物后，即可对客户包装为产品能力：

| 交付物 | 客户价值 |
| --- | --- |
| 智能客服问答台 | 一线快速答复 |
| 业务诊断工作台 | 运维/实施排障 |
| 工单草拟与流转 | 问题闭环 |
| 知识图谱管理 | 知识沉淀 |
| MCP 工具治理台 | 安全接入真实系统 |
| 运营分析报表 | 管理决策 |
| 审计日志 | 合规可追溯 |

## 15. 汇报时建议强调的边界

为了避免客户产生不切实际预期，建议主动说明边界：

1. 系统可以辅助判断，但不替代源业务系统作为事实主库。
2. 系统可以调用受控 MCP 查询真实数据，但不会裸露所有后台接口。
3. 系统可以生成处理建议和工单，但生产变更需人工确认。
4. 系统可以解释大多数高频问题，但对设备硬件损坏、第三方平台异常、网络中断等仍需要现场或外部系统配合。
5. 系统初期价值来自高频场景试点，后续通过问题沉淀逐步扩大覆盖范围。

这不是削弱卖点，反而会让客户觉得方案可靠、可落地。

## 16. 最终销售主张

本系统的核心卖点可以总结为三句话：

1. 让客户用自然语言理解复杂业务系统，减少学习成本。
2. 让客服、运维、实施、研发围绕同一条证据链协同，减少扯皮和等待。
3. 让每一次告警、巡查、设备、接口问题都沉淀为知识资产，持续提升交付和服务能力。

如果只卖“AI 问答”，客户会觉得可有可无；如果卖“懂船舶告警、懂巡查卫士、能连真实系统、能诊断问题、能沉淀知识、能受控审计的业务智能中台”，客户就能看到明确的投入回报。
