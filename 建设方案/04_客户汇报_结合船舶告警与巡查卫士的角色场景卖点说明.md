# 客户汇报：结合船舶告警与巡查卫士的角色场景卖点说明

> 适用场景：面向客户说明 LightGraph 二开智能客服 / 业务诊断系统的价值。重点不是展示一个“会聊天的机器人”，而是展示一个能理解业务系统、接口、数据库、页面、设备和工单闭环的“业务协同与诊断中台”。

## 1. 一句话定位

本系统可以作为客户、客服、实施、运维、研发和管理层共同使用的智能业务助手：把后台接口能力、数据库结构、业务文档、运行日志、设备状态、告警记录、巡查记录、前端页面入口组织成知识图谱，再通过受控 MCP 工具按权限调用真实系统能力，帮助用户快速回答“是什么、为什么、查哪里、怎么处理、谁来负责、处理到哪一步”。

对客户来说，购买的不是一个问答框，而是一套能降低沟通成本、缩短故障定位时间、沉淀业务知识、提升售后响应能力、辅助运营决策的智能化交付能力。

## 2. 为什么 app-ship-alarm 与 guard_platform 能证明价值

app-ship-alarm 是后端业务系统，覆盖船舶告警、AI 设备、巡查记录、船舶定位、围栏、通知、MQTT、短信邮件、第三方开放 API、视频抓图、数据统计等能力。

guard_platform 是巡查卫士前端平台，覆盖地图船舶动态、最新告警、视频监控、巡查计划、巡查记录、围栏打卡、AI 设备管理、固件升级、告警过滤、统计看板、系统权限等页面。

这两个项目组合后，正好形成客户真实使用链路：页面上看见问题、客服接到咨询、系统调用后端接口查询、结合数据库和图谱解释原因、必要时生成工单交给实施/运维/研发处理，并把过程留痕。

## 4. 面向客户的核心卖点

### 4.1 它能理解业务，不只是匹配文档

传统客服知识库只能回答“某个按钮在哪里”。本系统通过图谱把页面、接口、数据库、配置、任务、设备、告警状态连接起来，可以回答更深的问题。

例如客户问：“为什么长江2号今天有告警，但平台地图上点进去没有最新告警？”

系统不只是搜索“最新告警”四个字，而是按链路分析：

1. 前端地图弹窗来自 guard_platform 的船舶动态模块。
2. 弹窗可显示当日告警数、打开视频监控、打开最新告警。
3. 最新告警依赖后端告警列表、船舶 ID、机构/设备权限、时间范围、告警确认/处理状态。
4. 如果船舶未上报定位，前端会提示“船舶未上报定位信息”，地图点位也可能无法定位。
5. 如果用户没有对应 deviceIds 或 tenant 权限，即使后端有告警，前端也可能不展示。

这就是从“查文档”升级到“理解业务链路”。

### 4.2 它能查真数据，但不会裸奔式暴露接口

客户常会问：“你是不是把后台所有接口都给 AI 调了？安全吗？”

汇报时要明确：系统不会把所有 Controller 原样暴露成 MCP。MCP 暴露的是经过治理的业务能力，比如：

| MCP 能力 | 背后可能调用 | 安全控制 |
| --- | --- | --- |
| 查询某船告警摘要 | 告警列表、告警详情、船舶信息 | 只读、按租户/船舶权限过滤、字段脱敏 |
| 查询驾驶舱抓图失败原因 | 第三方配置、船舶信息、GB 通道配置、视频服务状态 | 默认只诊断，不自动重试生产抓图 |
| 查询账号/设备质保提醒发送状态 | Redis 标记、notice 记录、MQTT topic、定时任务状态 | 不允许越权查看其他租户用户隐私 |
| 查询巡查记录异常原因 | 巡查计划、巡查点、围栏半径、打卡位置、证明材料 | 只展示授权范围内的巡查数据 |
| 生成工单和处理建议 | 工单系统、知识图谱、历史案例 | 高风险动作需人工确认 |

这能向客户证明：AI 能接入真实业务，但边界是受控的。

### 4.3 它能把一次排障沉淀成长期资产

每次客服或运维处理问题后，系统都可以沉淀：问题描述、证据链、根因、处理动作、涉及接口、涉及表、涉及页面、最终结论。下一次同类问题出现时，不再从零开始。

例如“驾驶舱抓图失败”第一次需要研发解释接口流程；第二次系统就能自动提示：先查 token，再查 shipName 是否一致，再查 jww_third_api_configure 权限，再查 jww_ship_info，再查 jww_dvr_media_gb_config 是否存在含“驾驶”的通道，再查 VideoService.manualCapture 返回是否为空。

这就是客户愿意持续使用的原因：越用越懂业务，越用越省人。

## 5. 角色一：客服坐席副驾

### 5.1 解决的问题

客服每天面对的是模糊问题：客户不会说接口名、表名、字段名，只会说“告警看不到”“船不显示”“视频打不开”“账号没提醒”“巡查结果不对”。

客服副驾的作用是把模糊描述转换成可查询、可解释、可派单的问题。

### 5.2 app-ship-alarm 示例：客户说“告警接口查不到数据”

客户原话可能是：“我们对接你们船舶告警开放 API，昨天还有数据，今天查不到。”

系统可自动追问和排查：

| 排查点 | 系统能做什么 | 对客服的帮助 |
| --- | --- | --- |
| Token 是否有效 | 检查是否通过 POST /dnl/api/token 获取 Bearer Token，token 是否超过 1 小时 | 避免客服只回答“重新登录试试” |
| 时间范围是否合规 | 检查 /dnl/api/alarm/list 的 updateTimeStart/updateTimeEnd 是否超过 7 天 | 快速指出参数错误 |
| 租户权限是否匹配 | 根据 token 关联 tenantId，只返回授权租户告警 | 解释“有告警但查不到”的权限原因 |
| 告警状态是否符合预期 | 查看 isDeal、confirmStatus、dealTime、alarmTag、alarmLevel | 区分未处理、已处理、误报、超时升级 |
| 船舶字段是否完整 | 查看 shipMmsi、shipCn、shipName、shipType、alarmAddress | 帮客户确认对接字段含义 |

系统给客服的标准回复可以是：

“已按您的 access_token 查询，当前 token 对应租户为 XX。您本次请求时间范围为 10 天，超过接口约定的 7 天限制，因此返回为空/失败。建议将查询拆成两个时间段。若调整后仍无数据，我可以继续检查该租户下对应时间段是否存在 alarmCode、isDeal、confirmStatus 数据。”

这类回复比“请检查参数”更有说服力。

### 5.3 guard_platform 示例：客户说“地图上船点不显示”

客户原话可能是：“巡查卫士地图上看不到某条船，但是后台有船舶资料。”

系统可按前后端链路判断：

| 排查点 | 证据来源 | 可能结论 |
| --- | --- | --- |
| 船舶是否有实时定位 | guard_platform 地图模块调用 shipTravelReal / getRealShip | 船舶未上报定位，前端会提示“船舶未上报定位信息” |
| 当前账号是否有权限 | 前端 state.user.deviceId、部门树、tenant 权限 | 用户无该船或该部门权限 |
| 地图视野是否过滤 | 地图可视区域、船舶点绘制逻辑 | 船在视野外或被筛选条件过滤 |
| 定时刷新是否异常 | 地图定时器、事件监听、异步状态 | 可能是刷新或组件状态问题 |
| 船舶基础数据是否绑定 | 船舶 MMSI、CN、定位器编号、设备绑定关系 | 船舶资料存在但未绑定定位设备 |

客服可直接拿到清晰结论，而不是转给前端、后端、实施三方来回确认。

### 5.4 复杂严重示例：监管领导现场巡查时，重点船舶告警、地图、视频同时异常

这个案例适合在客户汇报中重点讲，因为它不是一个单点小问题，而是客户真实现场最怕发生的“多系统同时出问题”：监管领导正在大屏前查看重点船舶，平台上某危化品船没有正常显示位置；客户说现场明明发生了安全帽/区域入侵类告警，但最新告警点不开；同时视频监控打不开，驾驶舱抓图接口返回失败。此时一线客服如果只能说“我帮您反馈研发”，客户会认为系统不可控、服务不可依赖。

客户原话可能是：

“领导现在就在现场看大屏，长江2号在重点监管区域内，地图上船舶位置不对，最新告警点不开，视频也打不开。我们需要马上知道是平台问题、设备问题、权限问题，还是船舶本身没有上报。”

没有智能副驾时，客服通常要同时拉后端、前端、运维、实施、设备厂家来排查：前端查页面，后端查告警，运维查 MQTT 和视频，实施查船舶绑定，设备厂家查摄像头。每个人都只掌握一段信息，客户等待时间长，而且很容易出现“数据有，但页面没有”“页面有入口，但后端无权限”“设备在线，但视频通道未配置”这类扯皮。

客服坐席副驾可以把这个严重问题拆成一条完整证据链：

| 排查层级 | 系统自动检查 | 可能发现的问题 | 客服能给客户的即时解释 |
| --- | --- | --- | --- |
| 事件定级 | 判断是否涉及重点船舶、重点区域、一级/二级告警、领导现场保障 | 属于高优先级现场保障事件 | “该问题已按重大现场保障事件处理，系统正在按船舶、告警、视频、权限四条链路并行核查。” |
| 船舶定位链路 | 查询船舶基础资料、MMSI/CN、定位器编号、实时定位上报、最后更新时间 | 船舶资料存在，但定位器 20 分钟未上报 | “地图不显示不是页面丢数据，而是该船定位数据已超时未上报。” |
| 前端权限链路 | 检查当前账号 tenant、deviceIds、部门树、船舶授权范围 | 客户账号无该船或该部门权限 | “当前账号看不到该船是权限过滤导致，不是系统无数据。” |
| 告警数据链路 | 查询告警列表、alarmCode、alarmTime、isDeal、confirmStatus、alarmLevel、alarmTag | 后端有告警，但状态为误报/已处理/超时升级 | “告警存在，但展示口径受确认状态和处理状态影响。” |
| 地图弹窗链路 | 检查船舶弹窗是否有 shipId、shipName、当日告警数、最新告警入口 | 弹窗船舶 ID 与后端告警对象不一致 | “地图对象与告警对象绑定关系异常，需要实施/数据侧修正。” |
| 视频链路 | 检查监控中心、GB28181、媒体通道、驾驶舱通道、VideoService 抓图返回 | 未配置含“驾驶”的 GB 通道或抓图返回空 | “视频入口可见，但该船驾驶舱通道未完成配置/当前抓图失败。” |
| 通知链路 | 检查 MQTT topic、notice 记录、告警通知是否推送 | 告警已入库但 MQTT 未推送到前端 | “后端已有告警，前端未收到实时推送，需检查消息链路。” |
| 工单分派 | 根据根因自动生成客服回复、运维任务、实施任务、研发任务 | 多责任方问题被拆清楚 | “我们已经把定位超时、视频通道、告警展示口径分别派给对应处理人。” |

系统在 1 到 3 分钟内可以给客服一份“现场可说”的阶段性结论，而不是等所有人排完再回复：

“当前问题不是单一页面故障。系统已核查到：长江2号船舶基础资料存在，但最近一次定位上报已超时；该船在后端存在 2 条当日告警，其中 1 条已确认为误报，1 条处于待处理；当前登录账号具备机构权限，但船舶设备授权列表中未包含该定位设备；视频链路方面，驾驶舱 GB 通道未匹配到含‘驾驶’的通道配置，因此抓图返回 201。建议先由实施补齐船舶定位设备授权和驾驶舱通道配置，运维同步检查定位上报链路，客服已生成工单并关联告警编号、船舶编号和截图证据。”

这个案例能证明客服副驾的关键价值：

1. **能定级**：知道这是领导现场保障，不是普通咨询。
2. **能并行排查**：同时看船舶、告警、权限、视频、MQTT、页面入口。
3. **能给阶段性答复**：即使根因未完全修复，也能先让客户知道问题在哪里。
4. **能减少扯皮**：把“前端问题、后端问题、配置问题、设备问题”拆成证据明确的任务。
5. **能沉淀复盘**：这次事件会变成下次重大现场保障的标准排查模板。

对客户的销售表达可以是：

“真正值钱的不是 AI 会回答‘按钮在哪里’，而是在领导现场、大屏保障、重点船舶异常这类高压场景下，它能把客服从传话筒变成现场指挥副驾，几分钟内拿出证据链、阶段性结论和分派动作。”

## 6. 角色二：业务查询助手

### 6.1 解决的问题

客户业务人员不一定知道系统菜单和字段。业务查询助手可以让他们用自然语言查询：

- “今天长江2号有几条告警？哪些还没处理？”
- “本周误报最多的告警类型是什么？”
- “某机构下面哪些 AI 设备快过保？”
- “昨天巡查有哪些漏检点？”
- “哪些船舶没有上报定位？”
- “这个告警有没有视频或图片证据？”

### 6.2 app-ship-alarm 示例：自然语言查告警闭环

客户问：“上周一级告警处理闭环怎么样？”

系统可组合查询：告警列表、处理状态、确认状态、处理时间、统计接口，并生成业务语言结论：

“上周一级告警共 X 条，已确认 X 条，已处理 X 条，超时未确认 X 条，超时未处理 X 条。闭环率较低的对象集中在 XX 船舶/XX 机构，主要告警类型为 XX。建议优先复盘这几类场景。”

这对应 app-ship-alarm 里的告警处理、确认、统计能力，也能连接 guard_platform 的看板和告警详情页面。

### 6.3 guard_platform 示例：自然语言查巡查质量

客户问：“昨天巡查有没有漏检？证据在哪？”

系统可结合巡查计划、巡查记录、巡查点、围栏半径、打卡位置、证明材料，输出：

“昨天巡查记录中，XX 线路有 2 个点位漏检，1 个点位异常。漏检点位为 A、B；A 点围栏半径为 50 米，未产生有效打卡证明；B 点有打卡记录但不在围栏内。相关图片/视频证明可在巡查记录详情中查看。”

这对客户的价值是：管理者不需要一个页面一个页面找，系统直接把结果和证据组织好。

### 6.4 复杂严重示例：事故复盘时，需要还原“告警、船舶轨迹、巡查、视频证据”的完整过程

客户管理层最关心的不是“查一条数据”，而是事故复盘时能不能快速还原全过程。例如某重点水域发生险情，客户需要回答：事故前船舶在哪里、有没有进入围栏、有没有触发告警、告警是否被确认、巡查人员是否按计划到场、是否有视频/图片证据、处理是否超时。

业务查询助手可以把客户一句话“帮我查昨天下午长江2号那次异常到底怎么回事”拆成多跳查询：船舶实时/历史轨迹、告警列表、告警详情、确认状态、处理状态、巡查计划、巡查记录、围栏打卡、证明材料、视频通道、通知记录。最后输出面向管理层的事件时间线：

1. 14:02 船舶进入重点监管区域，定位正常上报。
2. 14:05 触发区域入侵/安全作业类告警，告警等级为二级。
3. 14:07 平台生成告警，但 10 分钟内未确认，后续被标记为超时未确警。
4. 14:15 巡查计划应到达 A 点，但巡查记录显示该点漏检。
5. 14:18 视频通道无驾驶舱画面，抓图失败，缺少关键证据。
6. 14:25 客服/运维介入，生成处理工单。

这个能力能把“到处翻页面找证据”变成“一句话生成复盘材料”，客户能直接用于内部汇报、责任界定和整改跟踪。

## 7. 角色三：运维诊断助手

### 7.1 解决的问题

运维最难的是跨组件排查：接口正常不代表数据正常，数据正常不代表 MQTT 正常，MQTT 正常不代表前端展示正常。运维诊断助手可以把链路串起来。

### 7.2 示例：账号过期提醒没有收到

app-ship-alarm 已有账号过期提醒和设备质保到期提醒设计：定时任务查即将过期用户，写 Redis，生成 jww_notice，向 commonNotice_{userId} 或 commonNotice_{tenantId} 推送 MQTT。

客户问：“为什么某用户没有收到账号过期提醒？”

系统可按链路排查：

| 链路 | 检查内容 | 可能原因 |
| --- | --- | --- |
| 用户数据 | status=0，accountEffectiveTimeSet=1，accountEffectiveTime 是否在 30 天内 | 用户未启用自定义有效期或不在提醒范围 |
| 定时任务 | getAccountExpiresUserInfo 是否执行 | XXL Job 未配置或执行失败 |
| Redis 缓存 | nearAccountExpiresUserInfo:{userId} 是否存在 | 缓存未写入或已过期 |
| 防重复标记 | nearAccountExpiresUserInfoNoticeTag:{userId} 是否存在 | 今天已提醒过，系统防重复 |
| Notice 记录 | jww_notice 是否有 noticeType=2 | 数据库记录是否生成 |
| MQTT 推送 | commonNotice_{userId} 是否发送 | topic 或客户端订阅异常 |

运维不需要从代码里翻完整逻辑，系统直接给出排查顺序和证据。

### 7.3 示例：设备质保到期提醒没有推送

系统可排查设备是否进入临期范围、Redis 防重标记是否存在、notice 是否写入、MQTT topic 是否为 commonNotice_{tenantId}、原有钉钉/短信发送是否成功。

客户价值：这类问题原本会涉及业务、后端、消息、前端通知多方，系统能把责任边界说清楚。

### 7.4 示例：AI 设备配置下发失败

从 guard_platform 的接口看，AI 设备涉及设备列表、未绑定设备、摄像头绑定、算法配置、媒体通道、网络配置、GB28181、重启、密码重置、TTS、固件升级计划等能力；app-ship-alarm 后端通过 MQTT 向设备控制 topic 下发配置。

客户问：“设备在线，但算法配置没有生效。”

系统可诊断：

1. 平台是否保存了对应 AI 设备和任务配置。
2. 设备是否绑定了摄像头/媒体通道。
3. 算法配置是否同步到设备。
4. MQTT 下发是否成功。
5. 设备是否回传状态。
6. 固件版本是否支持该算法。
7. GB28181 或视频通道是否影响取流。

这就是把“设备问题”拆成“平台配置、消息下发、设备回执、视频链路、固件能力”几个可验证环节。

### 7.5 复杂严重示例：多个租户同时反馈告警不推送，疑似消息链路故障

如果多个客户同时反馈“平台有告警，但前端没有实时提醒、手机端没有通知、大屏也没有刷新”，这已经不是普通单点问题，而可能是消息链路、定时任务、MQTT、Redis 或前端订阅异常。传统处理方式需要运维逐个系统登录排查，耗时且容易遗漏。

运维诊断助手可以按平台级故障处理：先判断影响范围是单租户、单船舶、单设备，还是多租户共性问题；再检查告警是否入库、notice 是否生成、MQTT topic 是否发送、Redis 防重标记是否异常、前端订阅 topic 是否正确、设备是否正常回传、是否存在任务积压。系统可以自动给出故障分级和处置建议：

- 如果告警已入库但 MQTT 未发送，优先检查后端消息网关和 topic 配置。
- 如果 MQTT 已发送但前端未收到，优先检查客户端订阅、WebSocket/MQTT 连接和账号权限。
- 如果告警未入库，优先检查设备上报、算法任务、Kafka/线程处理链路。
- 如果只有某租户异常，优先检查 tenant 权限、设备授权、过滤规则。

对客户来说，这证明系统不是只能回答单个用户问题，而是能辅助运维处理平台级故障，缩短重大问题的定位时间。

## 8. 角色四：实施交付顾问

### 8.1 解决的问题

实施人员面对的是现场交付：船舶资料、定位器、摄像头、围栏、巡查线路、人员规则、AI 设备、固件、视频平台、第三方对接。出错时通常不是代码 bug，而是配置链路不完整。

### 8.2 示例：配置一条船舶从地图展示到告警闭环

系统可给实施人员生成配置检查清单：

| 步骤 | 要检查的内容 | 关联能力 |
| --- | --- | --- |
| 船舶基础资料 | shipName、shipMmsi、shipCn、shipType、tenantId | 船舶管理、开放 API 字段 |
| 定位设备绑定 | ship_locator_code / 设备编号是否绑定 | 地图船舶动态、W6/AIS 数据 |
| 用户权限 | 当前账号是否拥有机构/船舶权限 | 前端 deviceIds、部门树 |
| 告警设备 | AI 设备是否绑定该船舶/场景 | aiDeviceList、alarmDeviceList |
| 视频通道 | 驾驶舱摄像头是否存在，media_name 是否含“驾驶” | jww_dvr_media_gb_config、视频抓图 |
| 告警类型 | 告警类型、过滤规则、误报规则是否配置 | alarmType、filterRule |
| 处置闭环 | 是否能确认、处理、批量处理、统计 | DealController、DataStatisticsController |

这类清单可以直接变成实施 SOP，降低人员经验依赖。

### 8.3 示例：配置巡查计划与围栏打卡

系统可指导实施人员：

1. 建立巡查线路和巡查点。
2. 设置围栏半径。
3. 设置巡查人员规则和时间规则。
4. 验证打卡是否在围栏内。
5. 验证巡查状态是否能正确显示正常、异常、未知、漏检。
6. 验证巡查证明图片/视频是否生成。

客户价值：系统不仅能回答售后问题，还能帮助项目交付标准化。

### 8.4 复杂严重示例：新项目上线当天，船舶、围栏、视频、AI 设备配置不完整导致验收失败

项目验收时，客户通常不会接受“功能已经开发完，只是配置没配好”。例如上线当天客户要求演示：地图上看到重点船舶、船舶进入围栏触发告警、点击告警打开视频、巡查人员按计划打卡、管理层看板看到统计。但现场发现船舶能建档却不显示位置，围栏告警不触发，驾驶舱视频打不开，巡查记录没有证明材料。

实施交付顾问可以在验收前自动生成“上线前体检清单”：

1. 船舶资料是否完整：shipName、MMSI、CN、定位器编号、tenantId。
2. 船舶是否绑定定位设备，并且最近 N 分钟有上报。
3. 该船是否在当前账号 deviceIds 和部门树权限内。
4. 围栏是否配置半径、坐标、关联船舶/区域。
5. 告警类型、过滤规则、误报规则是否启用。
6. AI 设备是否绑定船舶/摄像头/媒体通道。
7. GB28181 和驾驶舱通道是否能取流/抓图。
8. 巡查线路、巡查点、人员规则、时间规则是否完整。
9. 看板统计是否能读取对应告警、巡查、设备数据。

这个复杂案例能证明系统可以把交付经验产品化：客户买到的不只是软件，还包括可复制的上线保障能力。

## 9. 角色五：研发排障助手

### 9.1 解决的问题

研发常收到不完整问题：“页面不显示”“接口报错”“数据不对”。研发排障助手可以先帮研发把问题翻译成代码和接口层面的定位信息。

### 9.2 示例：驾驶舱抓图失败定位

蓝水木驾驶舱抓图接口 POST /lanshuimuVideoPic 涉及外部 token 验证、openId、shipName、接入方配置、船舶定位器编号、权限过滤、GB 通道、海康 manualCapture、图片下载和 Base64 返回。

系统可自动生成研发排查单：

| 检查点 | 关联对象 | 失败表现 |
| --- | --- | --- |
| token 验证 | open.api.validate.url | token invalid、外部 code 非 200 |
| shipName 比对 | 外部 data.shipName 与请求 shipName | 船名不一致导致认证失败 |
| 接入方配置 | jww_third_api_configure | openId 无配置或 apiType 不匹配 |
| 船舶存在性 | jww_ship_info.ship_locator_code | msaShipId 找不到船 |
| 权限过滤 | filter_type / filter_id | 无权限获取该船数据 |
| 驾驶舱通道 | jww_dvr_media_gb_config media_name LIKE '%驾驶%' | 未找到驾驶舱摄像头通道 |
| 抓图服务 | VideoService.manualCapture(gbNum) | code=201，未获取到图片 |
| 图片下载 | picUrl HTTP 下载 | 图片下载失败 |

对研发来说，这比“客户说抓图失败”更可处理。

### 9.3 示例：前端地图卡顿或内存泄漏

guard_platform 已有地图优化材料，涉及定时器清理、事件监听清理、异步状态保护、JSON.parse 保护、坐标校验、批量覆盖物处理。

系统可把用户反馈“地图越用越卡”转换成研发检查项：

- 地图组件销毁时是否清理定时器。
- 地图事件监听是否重复绑定。
- 异步请求返回后组件是否已销毁。
- 覆盖物是否批量清理。
- 船舶坐标是否存在非法值导致异常渲染。
- JSON.parse 是否对空值/非法值做保护。

客户价值：问题进入研发前已经被结构化，减少沟通损耗。

### 9.4 复杂严重示例：版本升级后告警闭环率异常下降，需要快速判断是否引入回归

客户升级版本后发现闭环率突然下降，管理层认为系统质量有问题。这个问题可能来自多个层面：告警状态字段口径变化、确认/处理接口变更、前端筛选条件变化、统计接口聚合逻辑变化、误报过滤规则变化、数据库历史数据兼容问题。

研发排障助手可以把“闭环率下降”转换成影响面分析：

- 对比升级前后告警确认接口、处理接口、批量处理接口是否变更。
- 检查 isDeal、confirmStatus、dealTime、alarmTag、alarmLevel 等字段是否存在口径变化。
- 检查 DataStatisticsController 相关统计接口是否改动。
- 检查 guard_platform 告警列表、统计看板、筛选条件是否改动。
- 检查过滤规则、误报恢复、自动关闭配置是否影响统计结果。
- 生成“可能回归点、涉及接口、涉及页面、涉及表、验证用例”的研发排查清单。

这类问题如果没有系统辅助，研发往往要从客户截图、接口日志、数据库、前端页面逐层猜。系统能先把排查范围收窄，让研发集中验证最可能的回归点。

## 10. 角色六：运营分析参谋

### 10.1 解决的问题

管理层关心的不是单条告警，而是趋势、风险和投入产出。

系统可以把 app-ship-alarm 的统计接口、guard_platform 的看板、大屏、告警处置、巡查质量、设备健康统一成自然语言经营分析。

### 10.2 示例：告警运营日报

系统可每日生成：

- 今日告警总数、一级/二级告警数量。
- 待确认、已确认、误报、已处理、超时未处理数量。
- 闭环率、误报率、处理及时率。
- 告警最多的船舶、机构、场景、设备。
- 视频/图片证据缺失的告警。
- 建议重点关注的设备或区域。

客户价值：从“系统里有数据”升级为“系统主动给管理建议”。

### 10.3 示例：巡查质量周报

系统可汇总：

- 巡查计划执行率。
- 正常、异常、未知、漏检点位数量。
- 经常漏检的线路/点位。
- 打卡不在围栏内的记录。
- 缺少证明材料的巡查记录。
- 一线人员执行差异。

客户价值：帮助甲方把平台从“监控工具”用成“管理工具”。

### 10.4 示例：设备健康分析

系统可汇总：

- AI 设备在线/离线情况。
- 固件版本分布和升级计划进度。
- GB28181 配置异常设备。
- 视频通道缺失或取流异常设备。
- 临近质保到期设备。
- 告警高发但处置低效的设备。

客户价值：提前发现设备风险，减少突发故障。

### 10.5 复杂严重示例：月度复盘发现“告警很多、处理很慢、误报也高”，需要给管理层整改建议

管理层不会只问某一条告警，而会问：“为什么这个月告警变多了？是不是设备问题？是不是人员处理慢？是不是规则太敏感？下个月怎么改？”

运营分析参谋可以把告警、巡查、设备、人员、区域、误报、闭环率组合分析，输出管理层可执行建议：

- 哪些船舶/区域告警数量异常升高。
- 哪些告警类型误报率高，建议调整过滤规则或算法阈值。
- 哪些机构确认慢、处理慢，建议纳入考核。
- 哪些设备告警高发但视频证据缺失，建议优先维护。
- 哪些巡查点漏检频繁，建议调整线路或人员排班。
- 哪些固件版本设备故障率更高，建议统一升级。

这个场景能证明系统不只是售后工具，还能成为客户的运营管理工具，帮助客户持续优化制度、设备和人员配置。

## 11. 角色七：审计与权限助手

### 11.1 解决的问题

政企客户通常会担心：AI 是否会越权查数据？是否会泄露敏感信息？是否会直接执行危险操作？

系统需要把“可控、可审计”作为卖点，而不是回避。

### 11.2 可控边界

| 边界 | 说明 |
| --- | --- |
| 权限继承 | AI 查询继承当前用户的租户、角色、船舶、设备权限 |
| 默认只读 | 首期只开放查询、解释、诊断、工单草拟，不自动修改生产数据 |
| 高风险确认 | 批量处理告警、重启设备、修改配置、清除规则等动作必须人工确认 |
| 字段脱敏 | token、手机号、账号、密钥、内部 URL 等敏感字段按规则脱敏 |
| 调用留痕 | 每次 MCP 调用记录用户、时间、能力、参数摘要、结果摘要 |
| 证据可追溯 | AI 结论必须能追溯到接口、表、文档、日志或历史工单 |

### 11.3 对客户的表达方式

“我们不是把所有后台接口直接交给 AI，而是把接口封装成受控业务能力。AI 能帮你查、帮你判断、帮你生成建议，但涉及生产变更和敏感数据时一定受权限、审批和审计约束。”

这句话能增强客户信任。

### 11.4 复杂严重示例：客户担心 AI 查询跨租户数据，要求证明可审计、可追责

在政企客户采购时，安全顾虑经常比功能顾虑更关键。客户可能会问：“如果客服用自然语言问某条船的信息，AI 会不会查到其他机构的数据？如果有人让 AI 导出所有告警，系统会不会照做？出了问题能不能追责？”

审计与权限助手可以把安全边界展示成可验证机制：

1. 用户发起问题时，系统先识别当前登录人、租户、角色、授权船舶、授权设备。
2. MCP 工具调用前做权限裁剪，只允许查询授权范围内的数据。
3. 返回结果对 token、手机号、账号、密钥、内部 URL 等字段脱敏。
4. 对“批量导出、批量处理、重启设备、修改规则”等高风险动作，默认拒绝或要求审批。
5. 每次调用记录用户、时间、问题、工具、参数摘要、结果摘要、是否命中脱敏/拒绝策略。
6. 管理员可以按用户、租户、工具、时间范围回放审计记录。

对客户的采购价值是：系统不是一个不可控的 AI 黑箱，而是一个有权限、有边界、有审计、有追责能力的业务智能平台。

| 账号过期提醒没收到 | “用户没收到提醒” | 运维诊断助手 | 查定时任务、Redis、notice、MQTT topic | 定位是任务、缓存、消息还是客户端问题 |
| 设备质保提醒没推送 | “设备快过保但没人收到通知” | 运维诊断助手 | 查临期设备、Redis 防重、jww_notice、commonNotice_{tenantId} | 避免漏通知造成售后风险 |
| 地图船舶不显示 | “船在系统里，但地图上没有” | 客服副驾 + 实施顾问 | 查定位上报、设备绑定、权限、地图筛选、视野 | 现场问题快速闭环 |
| 最新告警点不开 | “地图弹窗最新告警没反应” | 研发排障助手 | 查船舶 ID、告警列表、前端弹窗、权限、路由 | 前后端责任边界清晰 |
| 地图越用越卡 | “大屏开久了卡顿” | 研发排障助手 | 查定时器、事件监听、覆盖物、异步状态、坐标数据 | 提升平台稳定性 |
| 巡查漏检争议 | “这个点到底有没有巡查？” | 业务查询助手 | 查巡查记录、围栏半径、打卡位置、证明材料 | 用证据回答争议 |
| 巡查计划不会配 | “现场人员不知道怎么设置规则” | 实施交付顾问 | 生成巡查线路、点位、人员规则、时间规则配置清单 | 降低交付门槛 |
| AI 设备配置不生效 | “算法下发了但没效果” | 运维诊断助手 | 查设备状态、算法配置、媒体通道、MQTT 回执、固件版本 | 设备问题分层定位 |
| 固件升级风险 | “哪些设备需要升级？会不会影响业务？” | 运营分析参谋 | 汇总固件版本、升级计划、设备状态、风险设备 | 支持客户做维护计划 |
| 误报率高 | “告警太多，很多是误报” | 运营分析参谋 | 统计误报类型、对象、时间段、过滤规则 | 优化规则，减少一线负担 |
| 告警闭环慢 | “处理效率为什么低？” | 管理层参谋 | 分析确认率、处理率、超时、人员/机构排名 | 支持考核和管理改进 |
| AI 越权担忧 | “AI 会不会看到别的机构数据？” | 审计权限助手 | 展示权限继承、字段脱敏、调用留痕 | 解决采购安全顾虑 |

## 13. 客户最容易买单的讲法

### 13.1 对一线用户

“以后你不用记那么多菜单，也不用知道接口名。你直接问：某条船为什么没告警、某个巡查点有没有漏检、某个设备为什么不在线，系统会带着证据告诉你答案。”

### 13.2 对客服主管

“它能把一线客服从传话筒变成专业坐席。系统会自动补齐排查步骤、证据链和标准回复，减少反复转研发。”

### 13.3 对运维负责人

“它能把接口、数据库、Redis、MQTT、设备状态、视频通道串成一条排障链。不是只告诉你报错，而是告诉你下一步查什么。”

### 13.4 对项目经理

“它能把项目交付经验沉淀为 SOP，新人也能按步骤配置船舶、围栏、巡查、设备和告警规则，减少现场依赖老员工。”

### 13.5 对甲方管理层

“它能把平台数据转成管理建议：哪些船风险高、哪些设备不健康、哪些告警处理慢、哪些巡查点经常漏检。系统不只是记录问题，还能推动管理改进。”

### 13.6 对安全合规负责人

“AI 不直接裸调全部后台接口，所有查询都受权限控制、敏感字段脱敏、操作留痕，高风险动作需要人工确认。”

## 14. 试点建设建议

### 14.1 第一阶段：先选高价值试点场景，作为建设边界

这里的“先选场景”不是先开发场景功能，而是先确定建设边界和验收目标。因为没有 MCP 和知识图谱支撑，场景只能停留在演示话术，无法查真实数据、无法走调用链路、无法输出证据链。

建议先选 5 个最能打动客户、也最能覆盖核心链路的试点场景：

1. 船舶告警查询与状态解释。
2. 地图船舶不显示诊断。
3. 驾驶舱抓图失败排查。
4. 账号/设备质保提醒未收到排查。
5. 巡查漏检与围栏打卡证据查询。

这 5 个场景覆盖客服、运维、实施、研发、管理层，适合用于客户演示，也适合作为第一期建设范围。后续所有数据源、图谱关系、MCP 工具和 LightGraph 编排，都围绕这 5 个场景反推，而不是先盲目接入全量系统。

### 14.2 第二阶段：梳理每个场景的数据源、接口、表、权限和证据链

选定试点场景后，先做链路盘点，明确每个问题到底需要哪些证据才能回答。

| 试点场景 | 需要的数据源 | 需要证明的问题 |
| --- | --- | --- |
| 船舶告警查询与状态解释 | 告警列表、告警详情、告警处置、船舶信息、租户权限 | 告警是否生成、是否处理、是否确警、是否误报、客户为什么查不到 |
| 地图船舶不显示诊断 | 船舶基础资料、定位上报、deviceIds、部门树、地图筛选、前端页面入口 | 船是否存在、是否有定位、账号是否有权限、地图是否过滤 |
| 驾驶舱抓图失败排查 | 第三方 token、openId、shipName、jww_third_api_configure、jww_ship_info、jww_dvr_media_gb_config、VideoService | 是认证失败、无权限、船舶不存在、通道缺失，还是抓图服务失败 |
| 账号/设备质保提醒未收到 | 定时任务、Redis key、notice 记录、MQTT topic、用户/租户关系 | 是任务没跑、缓存没写、已防重复、notice 未生成，还是 MQTT 未推送 |
| 巡查漏检与围栏打卡证据查询 | 巡查计划、巡查记录、巡查点、围栏半径、打卡位置、证明材料 | 是否漏检、是否在围栏内、是否有图片/视频证据、责任如何界定 |

这一阶段的产出应是“场景 -> 数据源 -> 接口 -> 表 -> 权限 -> 证据 -> 输出结论”的链路清单。它决定后续图谱怎么建、MCP 怎么封装、LightGraph 怎么编排。

### 14.3 第三阶段：构建场景最小业务知识图谱

图谱建设应先做最小可用图谱，而不是一开始镜像整个数据库。第一期图谱只围绕试点场景抽象核心业务概念和关系：

- 船舶、租户、用户、角色、部门、授权设备。
- AI 设备、定位设备、摄像头、媒体通道、GB28181 通道。
- 告警、告警类型、告警等级、确认状态、处理状态、误报、超时升级。
- 巡查计划、巡查线路、巡查点、围栏、打卡记录、证明材料。
- notice、MQTT topic、Redis key、定时任务、第三方接入方。
- 前端页面、后端接口、数据库表、配置项、错误码、历史案例。

图谱要回答的是“对象之间是什么关系”：某条船属于哪个租户、绑定哪些设备、哪些告警来自哪些设备、哪个页面展示这些数据、哪个接口能查询、哪个字段决定状态、哪个配置影响推送。

这样图谱才适合客服和管理层使用，而不是只给技术人员看表结构。

### 14.4 第四阶段：封装受控 MCP 工具

有了链路清单和最小图谱后，再封装受控 MCP 工具。MCP 不应裸暴露所有后台 Controller，而应封装为可审计、可限权、可复用的业务能力。

第一期优先封装只读工具：

- 查询告警摘要。
- 查询船舶基础信息。
- 查询船舶定位状态。
- 查询巡查记录详情。
- 查询 AI 设备状态。
- 查询 notice/MQTT 推送状态。
- 查询第三方接口配置摘要。
- 查询视频通道配置摘要。

每个 MCP 工具都要明确：输入参数、权限边界、脱敏字段、调用日志、异常返回、是否允许跨租户、是否允许批量查询。暂不开放自动处理告警、重启设备、修改配置、删除规则等高风险写操作。

### 14.5 第五阶段：基于 LightGraph 做场景诊断编排

当最小图谱和受控 MCP 都具备后，才真正进入“场景能力”建设。LightGraph 负责把用户问题编排成诊断流程：

1. 识别用户问题属于哪个试点场景。
2. 从图谱中找到相关对象、关系和候选证据。
3. 按权限选择可调用的 MCP 工具。
4. 查询真实数据，补齐证据链。
5. 判断当前处于哪个故障分支。
6. 输出阶段性结论、处理建议和工单草稿。
7. 把本次排查结果沉淀为历史案例。

因此，正确顺序不是“先做场景，再接 MCP 和图谱”，而是“先选场景定边界，再围绕场景建设最小图谱和受控 MCP，最后把它们编排成可演示、可验收、可扩展的场景能力”。

### 14.6 第六阶段：形成可售卖闭环

形成以下交付物后，即可对客户包装为产品能力：

| 交付物 | 客户价值 |
| --- | --- |
| 智能客服问答台 | 一线快速答复 |
| 业务诊断工作台 | 运维/实施排障 |
| 工单草拟与流转 | 问题闭环 |
| 知识图谱管理 | 知识沉淀 |
| MCP 工具治理台 | 安全接入真实系统 |
| 运营分析报表 | 管理决策 |
| 审计日志 | 合规可追溯 |

对客户汇报时可以这样表达：第一期不是“大而全地接所有系统”，而是用 5 个高价值场景牵引建设，先把数据源、图谱、MCP 和编排闭环打通；一旦这条路径跑通，后续新增场景就是复用同一套图谱和工具治理体系，成本会越来越低。

## 15. 汇报时建议强调的边界

为了避免客户产生不切实际预期，建议主动说明边界：

1. 系统可以辅助判断，但不替代源业务系统作为事实主库。
2. 系统可以调用受控 MCP 查询真实数据，但不会裸露所有后台接口。
3. 系统可以生成处理建议和工单，但生产变更需人工确认。
4. 系统可以解释大多数高频问题，但对设备硬件损坏、第三方平台异常、网络中断等仍需要现场或外部系统配合。
5. 系统初期价值来自“高频场景牵引的最小图谱 + 受控 MCP + LightGraph 编排”闭环，后续通过问题沉淀逐步扩大覆盖范围。

这不是削弱卖点，反而会让客户觉得方案可靠、可落地。

## 16. 最终销售主张

本系统的核心卖点可以总结为三句话：

1. 让客户用自然语言理解复杂业务系统，减少学习成本。
2. 让客服、运维、实施、研发围绕同一条证据链协同，减少扯皮和等待。
3. 让每一次告警、巡查、设备、接口问题都沉淀为知识资产，持续提升交付和服务能力。

如果只卖“AI 问答”，客户会觉得可有可无；如果卖“懂船舶告警、懂巡查卫士、能连真实系统、能诊断问题、能沉淀知识、能受控审计的业务智能中台”，客户就能看到明确的投入回报。
