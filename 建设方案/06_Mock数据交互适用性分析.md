# Mock 数据交互适用性分析

> 目的：单独分析“客户汇报中的角色与场景，是否适合先用 Mock 数据做交互”，供原型设计、UE 评审、前端实现、一期演示边界确认使用；不混入客户汇报主文档。

## 1. 结论

结论是：**适合，但必须分层使用，不能把 Mock 交互当成真实生产能力本身。**

原因很直接。当前角色和场景，本质上不是单页面表单联动，而是“用户提问 -> 系统识别场景 -> 并行查询多类证据 -> 汇总结论 -> 生成建议/工单”的业务编排过程。对于这种产品，前期如果完全等真实系统全部接通再做交互，开发成本高、演示节奏慢、很多关键价值点也难以在早期稳定复现；但如果所有内容都只靠前端写死，也会让客户误以为系统已经具备真实诊断和真实治理能力，后期反而容易失信。

因此更合理的方式是把 Mock 当成“场景化交互与编排验证层”，而不是“生产能力替身”。

## 2. 为什么这批场景适合先做 Mock 交互

这批场景有三个共同特点，决定了前期很适合用 Mock 方式构造可控交互。

### 2.1 场景复杂，且需要稳定复现

比如“领导现场巡查时，重点船舶告警、地图、视频同时异常”“多个租户同时反馈告警不推送”“版本升级后告警闭环率异常下降”。这类场景在真实生产里未必随时能复现，但客户汇报和产品联调时，必须稳定演示出完整证据链。

### 2.2 价值点主要在推理与协同过程

客户真正要买单的是：系统能不能识别角色、拆解问题、并行查看船舶、告警、权限、视频、巡查、MQTT、工单，最后给出阶段性结论。这个过程非常适合先用 Mock 数据把交互链路跑通。

### 2.3 很多能力本来就是多系统、多权限、多状态组合

场景里大量涉及前端页面、后端接口、数据库、Redis、MQTT、第三方视频、设备状态、权限裁剪、工单系统。若一开始直接接全量真实环境，不仅风险高，也会因为网络、权限、现场数据不稳定而影响演示和原型判断。

## 3. 哪些角色非常适合先用 Mock 做交互验证

以下角色的核心价值更偏向“场景理解、交互引导、证据组织、结论表达”，非常适合先用 Mock 数据做高仿真交互。

| 角色 | 是否适合 Mock 先行 | 适合原因 |
| --- | --- | --- |
| 客服坐席副驾 | 非常适合 | 重点是把模糊问题拆成标准排查路径，并展示证据链和标准回复 |
| 业务查询助手 | 非常适合 | 重点是自然语言查询、时间线组织、证据呈现、结果摘要 |
| 实施交付顾问 | 非常适合 | 重点是配置检查清单、上线体检、SOP 指引 |
| 运营分析参谋 | 非常适合 | 重点是多维汇总、趋势分析、整改建议 |

这几个角色在客户演示阶段，完全可以通过 Mock 数据模拟：

- 不同优先级案件进入案件中心。
- AI 会话根据不同问题走不同分支。
- 右侧证据链显示不同接口、表、设备、页面节点。
- 下方结论区输出不同责任人、工单类型、响应时限。
- 管理层看到日报、周报、月度复盘、整改建议。

只要 Mock 数据足够贴近真实结构，这些场景就能非常有效地证明产品价值。

## 4. 哪些角色不适合只停留在纯 Mock

以下角色虽然前期也可以用 Mock 做交互原型，但如果要向客户证明“可落地”，就不能长期停留在纯 Mock。

| 角色 | 是否可纯 Mock 交付 | 原因 |
| --- | --- | --- |
| 运维诊断助手 | 不可纯 Mock | 需要验证 Redis、MQTT、任务、设备状态、消息链路等真实运行态 |
| 研发排障助手 | 不可纯 Mock | 需要验证接口、字段、表、调用链、版本差异、真实错误码 |
| 审计与权限助手 | 不可纯 Mock | 需要验证真实权限继承、字段脱敏、审计留痕、拒绝策略 |

这三类角色如果只用 Mock，很容易出现三个问题：

1. 看起来像能查真实系统，实际上只是播剧本。
2. 看起来像有权限治理，实际上没有真实授权裁剪。
3. 看起来像能定位运行问题，实际上没有接入真实状态源。

所以，这三类角色适合做“Mock + 半真实链路”验证，而不是只做前端假交互。

## 5. 最适合本项目的方式：三层 Mock 策略

结合当前这些角色和场景，建议采用三层策略，而不是简单地说“用 Mock”或“不用 Mock”。

### 5.1 第一层：场景剧本 Mock

目标是验证产品交互和角色说服力。

这一层主要服务客户汇报、UE 评审、流程走查。数据可以预先编排成剧本，例如：

- 船舶定位超时 + 告警存在 + 权限缺失 + 视频通道未配。
- 告警已入库 + MQTT 未推送 + 前端未刷新。
- 巡查漏检 + 围栏外打卡 + 缺失证明材料。
- 闭环率下降 + 统计口径变化 + 前端筛选条件变更。

这一层最重要的是：让系统能稳定演示“怎么诊断、怎么解释、怎么分派、怎么沉淀”。

### 5.2 第二层：状态型 Mock

目标是验证交互不是静态播片，而是真的像系统在工作。

这一层的 Mock 不应只是固定文案，而应包含可切换状态：

- 不同案件切换时，聊天区、证据链、结论区、工单区整体联动。
- 同一案件可以从“待诊断”切到“诊断中”再到“已生成结论”。
- 某个工具调用可以从“排队中”切到“执行中”再到“完成/异常”。
- 同一问题可以展示不同责任归属：前端、后端、实施、设备、权限。

这一层非常适合当前诊断中心原型，因为它能模拟真实业务编排，而不是只做静态展示页。

### 5.3 第三层：受控真实链路

目标是验证系统不是只会演示，而是真的能接真实系统。

这一层不需要一开始打通全部接口，但至少要在重点场景上接入少量受控真实能力，例如：

- 查询某船告警摘要。
- 查询某船定位状态。
- 查询某条 notice 或 MQTT 推送记录。
- 查询某个巡查点最近打卡情况。
- 查询某个视频通道配置摘要。

这样对客户的表达会更稳：前端看到的诊断交互与证据链是稳定可演示的；其中部分关键证据已经来自真实受控 MCP，而不是完全前端编造。

## 6. 针对当前场景，建议怎么分配 Mock 与真实能力

| 场景 | 前期是否可用 Mock 主导 | 后续必须接真实能力的部分 |
| --- | --- | --- |
| 船舶告警查询与状态解释 | 可以 | 告警状态、租户权限、时间窗规则 |
| 地图船舶不显示诊断 | 可以 | 定位上报、设备绑定、权限裁剪 |
| 驾驶舱抓图失败排查 | 可以 | 视频通道配置、抓图返回、第三方认证结果 |
| 账号或设备质保提醒未收到 | 可以 | 定时任务、Redis、notice、MQTT |
| 巡查漏检与围栏打卡证据查询 | 可以 | 巡查记录、围栏判断、证明材料 |
| 多租户告警不推送 | 不建议只 Mock | 消息链路、租户影响面、运行态证据 |
| 版本升级后闭环率下降 | 不建议只 Mock | 升级前后接口、字段口径、统计逻辑 |
| AI 越权担忧与审计证明 | 不建议只 Mock | 权限继承、脱敏、审计日志、拒绝策略 |

换句话说：

- 以“说服客户看到系统价值”为目标的场景，适合 Mock 先行。
- 以“证明系统真的接通生产能力”为目标的场景，必须引入受控真实链路。

## 7. 对当前诊断中心原型的直接建议

如果这份分析要继续指导当前诊断中心原型，建议直接按以下原则推进：

1. 页面层全部使用结构化 Mock 数据驱动，不在组件内写死文案和状态。
2. Mock 数据不要只做静态展示，要能表达案件切换、证据变化、工具执行状态变化、责任归属变化。
3. 每个角色至少准备 2 到 3 个高质量剧本场景，其中至少 1 个是复杂严重场景。
4. 对运维、研发、审计三个角色，原型阶段允许 Mock 交互，但在一期验收前必须补上少量真实 MCP 读能力。
5. 在汇报口径上明确说明：当前演示中的“场景编排与交互”为高保真 Mock，“关键证据查询”将逐步替换为受控真实能力。

这样做的好处是：

- 原型可以快速迭代，不被真实系统接入拖死。
- 客户能先看到角色价值、交互价值和协同价值。
- 后面接真实系统时，不会推翻现有页面结构和对话编排。
- 销售、产品、前端、后端、实施都能围绕同一套场景资产协作。
