# 02_技术调研

## 一、Graph RAG 技术背景

传统 RAG（Retrieval-Augmented Generation）核心流程：

```text
用户问题
   ↓
向量检索
   ↓
召回 Chunk
   ↓
LLM 总结回答
```

这种方式存在明显问题：

| 问题 | 描述 |
|---|---|
| 缺乏全局关系 | 只能找到“相似文本”，无法理解业务关系 |
| 无法推理链路 | 不知道模块之间如何关联 |
| 多跳查询能力差 | 无法跨实体进行复杂关联推理 |
| 对代码系统理解弱 | 只能理解局部代码，无法理解系统整体 |
| 数据库理解缺失 | 无法形成业务数据模型 |
| 容易上下文漂移 | Chunk 之间缺乏稳定关联 |
| 无法形成长期知识结构 | 每次问答依赖即时召回 |

因此出现：

# Graph RAG（图谱增强检索）

核心思想：

```text
不仅存文本，
还存 “实体-关系-实体”
```

例如：

```text
用户 -> 提交 -> 工单
工单 -> 关联 -> 设备
设备 -> 归属 -> 项目
项目 -> 包含 -> 摄像头
```

系统最终形成：

```text
Knowledge Graph（知识图谱）
```

而不是简单向量库。

# 二、主流 Graph RAG 框架对比

## 1. LightRAG

### 项目定位

轻量级 Graph RAG 框架。

核心目标：

```text
低成本构建实体关系图
+
结合向量检索
+
提升复杂问答能力
```

LightRAG 本质：

```text
Graph + Vector Hybrid Retrieval
```

不是纯图数据库系统。

### 推荐运行硬件（企业初期部署）

| 项目 | 推荐配置 |
|---|---|
| CPU | 16 Core 起步 |
| 推荐内存 | 64GB~128GB |
| 推荐 GPU | RTX4090 / M4 Max / M5 Max |
| 本地模型 | ≥ 35B 参数模型 |
| 推荐模型 | Qwen3 32B / DeepSeek / Gemma 27B~35B |
| Embedding 模型 | BGE / GTE / Qwen Embedding |
| 向量库 | pgvector / Qdrant |
| 图存储 | NetworkX / Neo4j Lite |
| 推荐存储 | 1TB SSD 起步 |

```text
需要注意：

LightRAG 官方实际推荐：
在生产级知识图谱构建过程中，
需要部署至少 35B 级别的大模型。

原因是：
Entity Extraction（实体抽取）
Relationship Extraction（关系抽取）
Community Summary（社区摘要）
Graph Merge（图谱融合）

对于模型的：
- 长上下文能力
- 逻辑稳定性
- 实体一致性
- 关系抽象能力

要求较高。

小模型（7B / 14B）通常会出现：
- 实体漂移
- 关系错误
- Merge 不稳定
- 图谱碎片化
- Summary 质量低

因此：
LightRAG 虽然比 Microsoft GraphRAG 轻量。

但它并不属于：
“低算力即可运行”的系统。

它真正的定位更接近：
“中等规模 AI 知识图谱引擎”。
```

### 为什么 LightRAG 依旧比 Microsoft GraphRAG 更适合企业初期落地

| 项目 | LightRAG | Microsoft GraphRAG |
|---|---|---|
| 推荐模型规模 | 35B 左右 | 70B+ 更佳 |
| 单机部署可行性 | 高 | 较低 |
| 是否必须 GPU 集群 | 否 | 基本需要 |
| Token 消耗增长 | 中等 | 指数级 |
| 图谱层级 | 中等 | 极复杂 |
| 企业维护难度 | 可控 | 很高 |
| 初期 PoC 成本 | 可接受 | 极高 |

```text
因此：

LightRAG 的核心优势并不是：
“完全轻量”。

而是：

在保证一定 Graph 能力的情况下，
仍然可以：
- 单机部署
- 本地私有化
- 中小团队维护
- 控制 Token 成本
- 控制 GPU 成本

这也是当前阶段优先选择 LightRAG 的核心原因。
```


微软 GraphRAG 更适合：

```text
大规模研究型知识图谱
```

不太适合：

```text
企业快速落地
```

# 三、为什么当前优先选择 LightRAG

## 1. 部署成本低

相比微软 GraphRAG：

| 项目 | LightRAG | Microsoft GraphRAG |
|---|---|---|
| Token 消耗 | 低 | 极高 |
| 图谱构建复杂度 | 中 | 高 |
| 存储结构 | 轻量 | 重 |
| 本地部署难度 | 低 | 中高 |
| 对 GPU 要求 | 较低 | 高 |

---

## 2. 更适合企业初期知识库建设

当前目标：

```text
快速构建：
- 文档知识库
- 代码知识库
- 基础关系图
- 问答能力
```

LightRAG 非常适合：

```text
“先跑起来”
```

而不是：

```text
一开始就构建超大型知识图谱系统
```

---

## 3. 支持 Hybrid Retrieval（混合检索）

LightRAG 同时支持：

```text
1. 向量检索
2. Graph 检索
3. Keyword 检索
```

因此：

| 类型 | 效果 |
|---|---|
| 精准关键词问题 | 好 |
| 模糊语义问题 | 好 |
| 多跳关系问题 | 中等 |
| 全局推理问题 | 一般 |

已经明显优于：

```text
传统 Vector RAG
```

---

## 4. 可扩展性较强

LightRAG 只是：

```text
基础图谱引擎
```

后续可以继续扩展：

| 能力 | 是否可扩展 |
|---|---|
| MCP 工具调用 | √ |
| 数据库分析 | √ |
| 代码解析 | √ |
| Agent 调度 | √ |
| 业务规则引擎 | √ |
| SQL 推理 | √ |
| 系统级知识图谱 | √ |

因此：

```text
适合作为企业 AI 中台初期底座
```

# 四、LightRAG 的核心工作原理

## 1. 文档摄取流程

核心流程：

```text
文档
 ↓
文本解析
 ↓
Chunk 切块
 ↓
实体抽取
 ↓
关系抽取
 ↓
摘要生成
 ↓
Embedding
 ↓
图谱存储
 ↓
向量存储
```

---

## 2. Chunk 切块

不是简单：

```text
按 500 字切
```

而是：

| 方式 | 说明 |
|---|---|
| 段落切块 | 保留语义完整 |
| 标题结构切块 | 保留层级 |
| 表格识别 | 防止结构丢失 |
| 代码块识别 | 保持函数完整 |
| 语义边界切块 | 避免句子截断 |

---

## 3. 实体抽取

例如：

```text
“塔吊监测模块通过 MQTT 上报数据至 IoT 平台”
```

抽取：

| 类型 | 实体 |
|---|---|
| Device | 塔吊 |
| Protocol | MQTT |
| Platform | IoT 平台 |

---

## 4. 关系抽取

继续形成：

```text
塔吊 -> 使用 -> MQTT
MQTT -> 上传至 -> IoT平台
```

最终：

```text
形成 Graph
```

---

# 五、当前 LightRAG 的局限性

这是重点。

当前 LightRAG：

本质还是：

```text
“文本知识图谱”
```

不是：

```text
“系统级业务知识图谱”
```

---

## 1. 无法真正理解业务系统

它能：

```text
抽取文本关系
```

但不能真正理解：

| 内容 | 是否真正理解 |
|---|---|
| 业务流程 | × |
| 状态机 | × |
| 数据生命周期 | × |
| 系统时序 | × |
| 微服务调用链 | × |
| SQL真实业务含义 | × |
| 数据库约束关系 | × |

---

## 2. 对代码理解有限

CodeGraph 能做什么：

```text
函数调用链
类依赖
模块引用
import关系
```

但无法形成：

```text
业务抽象
```

例如：

```text
支付失败后为什么回滚？
```

它不知道。

因为：

```text
缺乏业务语义层
```

---

## 3. 无法真正理解数据库

数据库里：

```text
表
字段
索引
外键
```

只是结构。

但业务真正关键的是：

```text
字段代表什么
数据如何流转
状态如何变化
```

这些：

```text
LightRAG 本身不会理解
```

# 九、后续核心建设方向

## 为什么拥有 LightRAG 后依旧必须进行二次开发

必须明确：

当前 LightRAG 本质上仍然属于：

```text
“文档型 Graph RAG 系统”
```


即：

| 输入内容 | LightRAG 是否擅长 |

| 运维手册 | √ |
| FAQ | √ |

很多企业真实现状：

| 类型 | 实际情况 |

```text
仅靠传统文档投喂，
无法真正理解企业系统。
```

| 接口上下游关系 | × |
| 微服务调用图 | × |
| 业务状态机 | × |
| 事件流 | × |
| 系统时序关系 | × |

因此：

```text
LightRAG 更像：
“知识库层”

而不是：

“系统级业务理解层”
```

# 当前存在的两种主要方案

## 第一种方案：让大模型直接阅读代码和数据库，再生成文档

核心思路：

```text
代码 / SQL / 表结构
    ↓
LLM 分析
    ↓
自动生成业务文档
    ↓
再投喂 LightRAG
```

这种方式优点：

| 优点 | 描述 |
|---|---|
| 实现快 | 初期容易落地 |
| 技术门槛低 | 不需要大量底层开发 |
| 可以快速看到效果 | 适合 PoC 阶段 |

但问题非常明显：

| 问题 | 描述 |
|---|---|
| Token 消耗巨大 | 大型项目成本极高 |
| 上下文长度不足 | 无法完整理解大型系统 |
| 容易幻觉 | 业务关系可能错误 |
| 黑盒化严重 | 无法解释为什么这样推理 |
| 稳定性差 | 多次生成结果不一致 |
| 无法持续维护 | 代码变更后需重新生成 |
| 难形成结构化知识 | 依旧偏文本化 |

本质上：

```text
这是：
“让 LLM 猜系统”

而不是：

“真正理解系统”
```

因此：

```text
只适合作为早期辅助方案
```

不能作为最终架构。

# 第二种方案：系统级知识建模（二次开发）

这也是后期真正必须投入的方向。

核心思想：

```text
不再让 LLM 直接硬读代码。

而是：
先通过稳定工具，
将代码、数据库、接口、
转换成结构化语义。
```

再交给 LLM 理解。

核心流程：

```text
代码
 ↓
AST 抽象语法树
 ↓
语义分析
 ↓
业务关系抽取
 ↓
结构化知识图谱
 ↓
LLM 推理
```

---

# 为什么 AST 很重要

AST（Abstract Syntax Tree）：

```text
抽象语法树
```

它不是字符串。

而是：

```text
代码结构本身
```

例如：

```java
userService.createOrder(userId);
```

AST 能明确知道：

| 内容 | AST 是否知道 |
|---|---|
| 调用了哪个方法 | √ |
| 属于哪个类 | √ |
| 参数是什么 | √ |
| 返回值是什么 | √ |
| import 来源 | √ |
| 调用层级 | √ |

而不仅仅是：

```text
“这是一段文本”
```

因此：

```text
AST 是系统级代码理解的基础
```

## 4. Runtime Knowledge Layer（运行时知识层）

# 最终目标

最终不是：

```text
做一个“高级聊天机器人”
```

而是：

```text
构建：
企业级系统语义中枢
```

即：

```text
AI 能真正理解：

系统为什么这样设计、
数据为什么这样流转、
问题为什么会发生、
应该如何排查、
会影响哪些模块、
应该调用哪些工具、
如何自动修复。
```

这才是：

```text
Graph RAG 后期真正的演进方向。
```
