# 未来规划方向

## 一、项目定位

本项目第一阶段的重点，不是直接追求复杂的 GraphRAG 推理能力，而是先落地一套可查询、可复用、可追溯的知识底座。

核心目标是把现有的文档、案例、数据库、接口与代码链路整理成统一知识体系，让知识服务真正落地，并为后续图谱智能、诊断闭环和角色化智能体打基础。

一句话概括：先把经验变成资产，再把资产升级成智能能力。

## 二、第一阶段要解决什么问题

当前很多高频问题仍然依赖个人经验，客服和运维遇到问题后，往往需要反复查资料、找研发确认，问题响应和定位效率都受到影响。

第一阶段的建设目标，是先让系统具备以下能力：

- 面对高频问题时，客服和运维优先查询知识助手，而不是默认升级给研发。
- 系统能够给出带来源依据的排查路径，而不是只返回零散结论。
- 已处理的问题可以持续沉淀为统一口径、标准问答和标准 SOP。
- 团队能力从依赖个人经验，逐步转向依赖可复用的知识体系。
- 管理层可以看到高频问题分布、研发介入比例和知识缺口。

## 三、第一阶段建设内容

第一阶段围绕统一知识底座展开，优先覆盖高频问题场景，重点建设以下内容：

- 基于 LightRAG 建设统一知识底座。
- 接入产品文档、部署文档、配置手册、运维 SOP、历史案例等存量资料。
- 接入 CodeGraph 梳理出的数据库建表 SQL、字段关系、代码调用链和接口链路。
- 结合现有后台查询能力，补齐设备状态、告警规则、日志、任务状态、配置结果等信息来源。
- 通过大模型把技术事实整理成业务脉络，形成可追溯的数据链。

## 四、数据来源与数据链

### 4.1 数据来源

知识底座的核心数据将主要来自三类来源：

- CodeGraph 梳理出的数据库建表 SQL、字段定义、表关系、代码调用链、接口调用链。
- 现有系统中的产品文档、部署手册、配置说明、运维 SOP、故障记录和历史案例。
- 后台服务已有的查询能力，包括设备状态、告警规则、日志、任务状态和配置结果等。

### 4.2 数据链形成方式

数据链的形成，不是简单堆叠资料，而是把技术事实转成可理解、可追踪的业务路径：

- 先整理数据库、接口、代码和文档中的技术事实，确认真实数据源和处理链路。
- 再利用大模型将技术信息翻译成业务脉络，识别业务对象、处理步骤、判断规则和结果呈现之间的关系。
- 最终形成可追溯的数据链，回答“数据从哪里来、经过哪里处理、最终展示到哪里”。
- 在此基础上，把数据链进一步转化为问答、排查路径和证据说明。

## 五、为什么第一阶段先做 LightRAG，而不是直接做 GraphRAG

传统 RAG 更擅长从文档中找到相似内容，适合回答“文档里怎么写”；但它不擅长回答“这个问题和哪个配置、接口、表、规则有关”，也不擅长把多个系统中的真实关系串成完整链路。

图谱知识库更适合把设备、配置、规则、接口、数据库和页面结果这些对象串成一条关系链，因此更适合支撑“为什么会这样、应该先查哪里”这类问题。

但从实施路径看，GraphRAG 的前提是先有一套整理过、可复用、可追溯的知识底座。因此第一阶段先建设 LightRAG，并同步沉淀数据链和业务语义骨架，这是更稳妥、也更容易落地的路径。

一句话概括：传统知识库更像按关键词找答案，图谱知识库更像按业务关系找原因。

## 六、典型问题示例

以一个典型问题为例：为什么设备明明有数据，但页面上还是显示离线，告警也没有触发？

如果采用传统 RAG，系统更可能返回与“设备离线”“告警未触发”相关的文档段落、配置说明和接口说明，能够帮助使用者看到相关资料，但未必知道这些资料之间是否存在真实关系。

如果采用图谱化思路，系统会沿着“设备 -> 数据上报 -> 在线状态 -> 告警规则 -> 页面展示 -> 接口 -> 数据库记录”的关系链进行定位，进一步判断问题究竟是状态表未更新、规则未启用、字段映射错误，还是页面取错了数据源。

这两种方式的差异在于，前者更像帮忙翻资料，后者更接近真实的问题定位路径。

## 七、第一阶段产出与可承诺结果

### 7.1 阶段产出

第一阶段预计形成以下核心产出：

- 一套可查询的统一知识底座。
- 一批围绕高频问题的标准问答和排查路径。
- 一份可对外展示的数据链说明，用于帮助客服、运维和研发统一认知。
- 一套为第二阶段 GraphRAG 准备好的基础业务语义和关系骨架。

### 7.2 可承诺结果

围绕实际业务价值，第一阶段可以重点承诺以下结果：

- 高频重复问题中，客服和运维自主完成首轮排查的比例显著提升。
- 同类问题反复升级到研发的次数明显下降。
- 首次响应时间明显缩短，至少能够先给出排查方向和依据。
- 已关闭案例持续转化为知识条目，知识库规模持续增长。
- 前 20 类高频问题形成统一口径和基础 SOP。

### 7.3 建议试点目标

- 高频重复问题研发介入量下降 30% 以上。
- 客服和运维独立完成首轮定位的问题占比提升 30% 以上。
- 首次答复时间缩短 50% 以上。
- 沉淀一批可直接复用的高频问题标准案例，并完成核心数据链样板梳理。

## 八、长期迭代路线

### 阶段 1：知识底座与数据链建设（0-3 个月）

建设统一知识库、标准问答、排查 SOP 和数据链说明，完成第一批高频问题场景覆盖。

### 阶段 2：业务语义理解与 GraphRAG 基础建设（3-6 个月）

围绕设备、项目、协议、字段、规则、告警、任务和页面等核心对象建设业务图谱，支撑跨源实体关联、关系推理和更复杂的问题定位。

### 阶段 3：后台服务 MCP 化与角色化智能体入口（6-9 个月）

将现有查询类和执行类后台能力封装为 MCP 工具，并按角色、项目、数据范围和风险等级进行权限治理，让用户、客服、运维和开发逐步直接面向智能体工作。

### 阶段 4：诊断闭环与智能运营（9-12 个月）

打通知识回流、路径固化、案例复用、审批执行、效果评估与持续优化，逐步形成“问题识别 -> 证据汇聚 -> 诊断建议 -> 审批执行 -> 结果回流 -> 知识沉淀”的完整闭环。

最终达成的核心能力是：用户提出问题后，系统能够基于业务图谱快速锁定可能原因，联动 MCP 工具查询实时数据完成验证，再由 LLM 基于完整证据链给出最终判断和处理建议。

## 九、角色化智能体与安全治理

后续在能力开放时，将按角色进行分层治理：

- 客服：以知识检索、案例问答、摘要查看、问题建单为主，只开放低风险查询类工具。
- 运维：可查看详细证据、发起诊断、调用授权查询工具、发起审批申请。
- 开发：可查看更完整的调用链、数据链、日志证据和技术上下文，用于复杂问题定位。
- 管理员：负责工具启停、白名单、权限范围、模型配置和全局治理。
- 审计：只读查看执行记录、审批记录和工具调用留痕。

在治理原则上，需要坚持以下要求：

- 查询类与执行类工具严格分离。
- 执行类动作不能由智能体直接放行。
- 所有工具调用必须带角色权限、项目范围和审计上下文。
- 高风险动作必须经过审批流，确保系统可控、可审计、可治理。

## 十、汇报结论

第一阶段部署 LightRAG，并不是做一个概念化的 AI 项目，而是先把公司现有文档、配置说明、历史案例、数据库与接口脉络整理成一套真正可服务客服和运维的知识助手与数据链说明。

它的直接价值，是减少重复依赖研发、缩短问题响应时间、形成标准排查路径、沉淀企业知识资产。

它的长期价值，是为 GraphRAG、MCP 工具化和角色化智能体建立真正可落地的底座。

最终目标，是让系统能够直接面对用户问题，基于业务图谱快速锁定可能原因，联动 MCP 工具查询实时数据完成验证，再由 LLM 基于完整证据链输出可解释、可验证、可闭环的智能诊断结果。
