# 公交 / 船舶监管系统中的 Graph RAG 实体关系抽取示例

## 1. 原始业务文本示例：公交监管场景

假设系统中存在如下原始文本：

> 2026年5月，金海星导航科技公司为“镇江公交集团”下属的 K12 线路公交车安装了车载视频监控系统与 CAN 总线采集设备。
>
> 其中，设备编号为 CAM-3201 的车内摄像头安装于苏L03215公交车前门位置，用于驾驶员行为识别与乘客异常行为监测。
>
> CAN 设备编号为 CAN-9907，连接车辆发动机 ECU 与制动系统，用于采集转速、油耗、刹车状态等车辆运行数据。
>
> 苏L03215 所属线路为 “K12 快速公交线路”，运营区域覆盖镇江市京口区与润州区。
>
> 2026年5月18日 08:32，系统检测到该车辆在镇江南站附近连续出现急刹车告警，并同步上传至集团监管平台。
>
> 该车辆归属于镇江公交集团第三运营分公司。

## 2. Graph RAG 会提取什么

普通 RAG 主要做的是语义检索。

Graph RAG 进一步做的是：

- 识别实体
- 建立关系
- 形成可推理的业务图谱

也就是说，它不只是做 embedding，而是在构建业务世界模型。

## 6. Graph RAG 能做什么

普通 RAG 的能力：

- 语义搜索

- 关系推理

## 7. 业务问答示例

### 7.1 示例一：定位告警对应线路

用户问题：

> 镇江南站附近频繁急刹车的是哪条线路？

系统推理路径：

```text
急刹车告警
    → 苏L03215
        → K12线路
```

因此可以直接推理出对应线路。

### 7.2 示例二：筛选具备特定能力的车辆

用户问题：

> 哪些车辆安装了前门摄像头并具备驾驶员行为分析能力？

图谱筛选条件：

```text
摄像头
    → 安装位置 = 前门
    → 功能 = 驾驶员行为识别
```

据此即可直接筛出目标车辆。

### 7.3 示例三：分析是否集中于同一分公司

用户问题：

> 最近频繁出现急刹车的车辆，是否都来自同一个运营分公司？

图谱推理路径：

```text
告警
    → 车辆
        → 分公司
```

这类问题就可以进一步做聚类分析和归因分析。

## 9. Graph RAG 的真正价值

Graph RAG 的重点不是：

- 把文档直接丢进去

而是：

- 形成业务世界模型
- 让系统理解业务实体及其关联关系
- 支撑复杂业务问答、关联分析和决策辅助

系统最终理解的是这样一个实体网络：

```text
公司
    → 船队
        → 船舶
            → 设备
                → 告警
                    → 水域
                    → 航线
                    → 监管关系
```

本质上，这是一张业务知识图谱，而不是普通知识库。

## 10. 当前系统最关键的问题

当前最大的问题不是“有没有做 RAG”，而是：

- 业务文档太少
- 仅靠普通文档 RAG 不足以支撑复杂业务理解
- 需要从更多结构化和半结构化来源中补全业务知识

## 13. 进一步演进后的系统定位

当 Graph RAG、实体关系图谱与 MCP API 调用能力真正结合之后，系统的定位已经不再只是“知识库问答”。

## 14. 这套系统实际上已经具备什么基础

### 14.1 企业业务图谱能力

当前这套公交 / 船舶业务图谱，本质上已经在形成企业数字孪生的基础模型。

例如可以抽象为：

```text
集团
    → 分公司
        → 车辆 / 船舶
            → 设备
                → 告警
                → 水域 / 线路 / 航线
                → 视频
                → CAN
                → 人员
                → 工单
```

这意味着系统已经不再只是“检索文档内容”，而是在描述一个持续变化的业务实体网络。

### 14.2 系统执行能力

如果在图谱能力之上接入 MCP，那么系统就不只是能回答问题，还具备调用业务系统完成动作的能力。

例如可接入的执行能力包括：

- 查询接口
- 下发指令
- 拉取视频
- 查询轨迹
- 重启设备
- 推送工单
- 获取 CAN 数据
- 查询录像
- 告警确认

因此，这套系统最终形成的是：

- 业务世界模型 + 系统执行能力

## 15. 这时 AI 已经不只是聊天

在这个阶段，AI 的角色已经不再只是对话助手，而是企业调度中枢。

它可以同时承担三类核心职责：

- 理解业务实体、关系与上下文
- 调用业务系统执行查询和操作
- 基于图谱、规则和实时数据做推理与决策

## 16. 未来可以做到的核心能力

以下能力是图谱、RAG、MCP 与 LLM 联合后的典型落地方向。

### 16.1 面向集团监管领导

适用角色：

- 集团监管中心
- 安全总监
- 运营总监
- 值班调度

可提供的能力包括：

1. 告警聚类分析

例如用户提问：

> 最近急刹车最多的是哪些线路？

系统可通过如下路径自动聚类：

```text
线路
    → 车辆
        → 告警
```

进一步还可以结合空间信息输出热力图。

2. 风险运营分析

例如：

> 哪个运营分公司事故率最高？

系统可基于如下关系进行统计与归因：

```text
公司
    → 分公司
        → 车辆
            → 告警
```

3. AI 主动预警

例如系统可主动给出类似判断：

> K12 线路近 7 天频繁出现疲劳驾驶，建议重点检查夜班司机。

这已经不再是简单 RAG 检索，而是基于 Graph 的关系推理与趋势判断。

### 16.2 面向调度员

适用角色：

- 公交调度
- 船舶调度
- 运营值班

可提供的能力包括：

1. 实时位置查询

例如用户提问：

> 苏L03215 现在在哪？

系统先通过图谱找到：

```text
车辆
    → 北斗
    → GPS
```

再通过 MCP 调用实时接口，例如：

- /vehicle/realtime/location

返回真实位置。

2. 视频联动

例如：

> 调出刚才急刹车时的前门视频。

系统可先通过图谱定位：

```text
车辆
    → 摄像头
        → 视频流
```

然后通过 MCP 调用视频接口，例如：

- /video/playback/query

3. 自动故障定位

例如：

> 为什么这辆车频繁急刹？

系统可基于如下关系推理：

```text
CAN
    → 制动系统
        → 告警
            → ECU
```

推断可能存在制动压力异常，并进一步通过 MCP 调用实时数据接口，例如：

- /can/latest/data

来分析真实数据。

### 16.3 面向安全监管人员

适用角色：

- 安全员
- 海事监管
- 公交安全中心

可提供的能力包括：

1. 告警关联分析

例如：

> 最近偏航告警是否集中在某个水域？

系统可基于如下关系自动分析：

```text

    → 水域
    → 船舶
    → 航线
```

2. 高风险设备分析

例如：

> 哪些 CAN 设备最近离线率最高？

系统可沿着如下链路进行统计：

```text
设备
    → 车辆
        → 分公司
```

3. AI 自动巡检

例如系统可主动生成提示：

> 第三运营分公司有 3 台车辆连续 7 天摄像头离线。

随后自动创建巡检工单，并通过 MCP 调用例如：

- /workorder/create

### 16.4 面向维修部门

适用角色：

- 维修工程师
- 机务
- 设备运维

可提供的能力包括：

1. 故障根因分析

> 为什么 CAM-3201 总是掉线？

系统可沿着如下关系做根因推理：

```text
摄像头
    → 交换机
        → 电源
```

2. 设备关联故障分析

例如：

> 最近哪些设备与 ECU 异常同时出现？

系统可通过如下链路自动关联：

```text
CAN
    → ECU
        → 告警
            → 车辆
```

### 16.5 面向船长 / 驾驶员 / 现场操作员

适用角色：

- 司机
- 船长
- 现场操作员

可提供的能力包括：

1. 自然语言操作

系统可直接将自然语言意图映射为 MCP 调用，例如：

2. 自动填写业务表单

例如：

```text
    → 航次
```

### 16.6 面向领导层与监管部门

适用角色：

- 政府监管

可提供的能力包括：

## 17. 这套体系的技术本质

从能力分工上看：

- Graph RAG 负责理解业务世界
- MCP 负责操作业务系统

三者结合后，最终形成的是：

- Graph + RAG + MCP + LLM = 企业 AI Agent

## 18. 为什么传统 BI 做不到

传统 BI 更擅长的是统计分析和报表呈现。

但这里的系统已经能处理更复杂的关系结构，例如：

- 实体关系
- 设备关系
- 业务关系
- 空间关系
- 时间关系

更重要的是，它可以做跨系统推理。

例如把以下因素一起纳入分析：

- 急刹车
- 司机疲劳
- 雨天
- 制动异常
- 某条线路

这种跨实体、跨系统、跨时间的联合推理，传统 BI 很难直接完成。

## 19. 最终判断

从演进方向看，这套系统实际上正在走向“行业 AI 操作系统”，而不再只是聊天机器人。

真正企业 AI 的核心，不是模型本身有多聪明，而是模型是否真正理解企业业务世界。

而 Graph + Ontology + MCP，正是在构建这样的企业业务世界模型。
