# LightGraph 二开：智能客服系统能力边界与任务规划

## 1. 文档目的

本文档用于回答以下问题：

1. 如果以后不拘泥于当前练手项目，而是基于 LightGraph 做二次开发，系统应如何重新抽象定位。
2. 如果将后台能力以 MCP 方式接入，并将数据库结构、数据库业务数据、知识文档、工单案例等构造成知识图谱，系统具体可以做什么。
3. 这个系统的明确能力边界在哪里，哪些事情它可以辅助，哪些事情它不能直接替代人工或源系统。
4. 现阶段应如何拆任务、排优先级，并以什么顺序启动落地。

## 2. 范围重述

本次规划采用如下前提：

- 运行与编排底座以 LightGraph 为主；
- 当前 `intelligent-customer-service-system` 项目仅作为业务抽象、原型设计和已有经验输入；
- 不要求新系统继承当前练手项目的技术栈、目录结构或实现细节；
- 但要保留当前项目已经验证过的关键思想：
  - Evidence First
  - Graph + RAG + MCP 联合证据
  - 人工审批与审计闭环
  - 图谱治理与版本回滚

## 3. 现有业务抽象结论

结合现有需求与架构文档，当前业务本质不是“普通问答机器人”，而是“面向复杂业务系统的证据驱动诊断与协同平台”。

现有业务共性可以抽象为五类：

1. 问题受理：客服、运营、实施、研发接收用户问题。
2. 证据汇聚：从文档、数据库、接口、日志、配置、工单、图谱中找证据。
3. 路径推理：根据问题类型选择排查路径，决定先查什么、后查什么。
4. 风险动作：把“建议”与“执行”分开，高风险必须审批。
5. 结果沉淀：把成功案例、失败案例、路径反馈、关系修正回写为知识资产。

因此，面向 LightGraph 的正式系统，不应定义为“聊天框”，而应定义为：

```text
LightGraph Orchestrated Support Platform
=
问题理解
+ 证据规划
+ 图谱检索
+ MCP 调用
+ 数据库查询
+ 风险判断
+ 审批协同
+ 知识沉淀
```

## 4. 核心架构判断

### 4.1 LightGraph 在系统中的角色

LightGraph 适合作为以下能力的编排层：

- 会话状态机
- 多步诊断路径编排
- Graph / RAG / MCP / SQL 的路由决策
- 失败重试与回退
- Human-in-the-loop 节点
- 审计可追溯的执行轨迹

LightGraph 不适合作为以下能力的长期承载层：

- 关系图谱主存储
- 业务主数据库
- 权限源系统
- 工单源系统
- 日志主存储
- 最终审批系统

结论：LightGraph 负责“编排与状态”，不负责“事实主存”。

### 4.2 MCP 接入原则

不能把“后台所有接口”原样暴露成 MCP。

正确做法应是：

```text
后台原始接口
-> 能力抽象
-> MCP 能力目录
-> 风险分级
-> 权限绑定
-> 审计接入
-> LightGraph 调用
```

也就是说，MCP 暴露的是“能力”，不是“原始 Controller 列表”。

例如：

- `device.getStatus` 是能力
- `alarm.getRules` 是能力
- `project.getConfigSnapshot` 是能力
- `ticket.createDraft` 是能力
- `statistics.rebuild` 是高风险能力

而不是把内部几十个分页、列表、明细、批量接口直接映射为工具。

### 4.3 知识图谱接入原则

数据库结构和数据不能“全量裸导入图谱”后直接给 Agent 使用。

正确做法应是：

```text
DB Schema / DB Data / Docs / APIs / Cases / Logs
-> Source Registry
-> 解析与规范化
-> 候选实体/关系
-> 冲突检测
-> 置信度评分
-> 人工复核/规则门禁
-> 发布图谱
-> LightGraph 检索使用
```

结论：图谱必须是“治理后的业务知识图谱”，而不是“数据库镜像图”。

## 5. 这个系统具体能做什么

以下能力在“LightGraph + MCP + 业务知识图谱”形态下是成立的。

### 5.1 可解释问答与客服辅助

系统可以：

- 识别问题中的业务对象、时间范围、项目范围、设备范围；
- 根据问题类型选择检索路径；
- 联合图谱、历史案例、数据库查询和 MCP 工具返回答案；
- 输出“答案 + 证据 + 调用过程 + 置信度 + 未确认项”。

适用场景：

- 用户咨询为什么设备离线；
- 为什么告警没有触发；
- 为什么统计口径和页面展示不一致；
- 某类配置为什么没生效；
- 某个工单历史上是怎么处理的。

### 5.2 多跳证据定位

系统可以：

- 从问题实体出发做多跳图谱检索；
- 关联数据库结构、接口定义、规则配置、日志模式、历史案例；
- 给出“问题 -> 影响对象 -> 可能根因 -> 可验证证据”的链路。

这类能力比传统 FAQ 强得多，因为它不是只找相似文本，而是找关系路径。

### 5.3 实时状态补证

如果 MCP 接入的是实时系统能力，系统可以：

- 查询设备状态；
- 查询告警规则与阈值；
- 查询项目配置快照；
- 查询任务状态；
- 查询日志摘要；
- 查询关键统计指标。

因此它可以回答“现在是什么状态”，而不仅是“历史文档里怎么写”。

### 5.4 根因假设与排查建议

系统可以：

- 基于图谱路径和历史案例，给出多个候选根因；
- 按证据充分度排序；
- 提出下一步验证动作；
- 标记哪些建议只是推测，哪些已经有足够证据支持。

这使它更像“诊断副驾”，而不是简单检索器。

### 5.5 工单草拟与审批前建议

系统可以：

- 自动整理问题摘要；
- 自动生成建议工单标题、描述、处理建议；
- 生成审批申请草稿；
- 生成面向客服、实施、研发三种不同口径的答复摘要。

但这类能力应默认停留在“建议”和“草拟”，而不是自动写生产系统。

### 5.6 路径复用与 SOP 沉淀

系统可以：

- 记录成功诊断路径；
- 记录失败路径；
- 针对高频问题固化 SOP；
- 对“同类问题”优先复用已验证路径；
- 用反馈数据更新路径质量评分。

这意味着系统会越用越稳，但前提是必须有反馈和治理机制。

### 5.7 数据库与接口理解辅助

当数据库结构、OpenAPI、字段关系、业务字典进入图谱后，系统可以：

- 解释某个页面背后依赖哪些表和字段；
- 解释某个指标从哪里来；
- 解释某个接口返回值受哪些配置影响；
- 定位“这条数据为什么和页面不一致”。

这类能力对客服、运营、实施非常有价值，因为它把“研发脑内知识”外化成了可查询网络。

### 5.8 跨团队协同助手

系统可以把同一个问题拆成不同角色所需的信息：

- 给客服：用户可理解答复
- 给实施：现场核查清单
- 给运维：日志/配置/任务核查项
- 给研发：接口/表/规则/变更影响链
- 给审批人：风险等级、建议动作、回滚点

因此它不是单一角色工具，而是跨角色协同中台。

## 6. 能力边界在哪里

下面这些边界需要明确写死，否则系统会被误判为“万能 Agent”。

### 6.1 它不能替代源系统真相

知识图谱和缓存只是一层解释与路由层，不能替代：

- 生产数据库真值
- 实时设备状态真值
- 日志平台真值
- 审批系统真值

当图谱、缓存与源系统冲突时，以源系统为准。

### 6.2 它不能直接把所有接口变成可安全执行的工具

“有接口”不等于“可作为 MCP 暴露”。

必须经过：

- 风险分级
- 输入输出约束
- 调用频控
- 角色权限绑定
- 审计
- 幂等与回滚评估

否则系统会变成危险的内部万能操作台。

### 6.3 它不能保证在图谱不完整时仍然正确推理

当以下任一条件不成立时，系统只能给出低置信度建议：

- 关键知识源未入图
- 别名未归一
- 数据字段映射缺失
- 日志模式未沉淀
- 实时能力不可用
- 反馈闭环未建立

所以这个系统的上限由“知识治理质量”决定，而不是只由模型决定。

### 6.4 它不能默认自动执行生产动作

对于 L3 以上能力，默认边界应是：

- 可以分析
- 可以建议
- 可以草拟执行方案
- 可以发起审批
- 不可绕过审批自动执行

即便未来开放自动执行，也只能在白名单、低风险、幂等、可回滚场景中受控开放。

### 6.5 它不能替代复杂业务裁决

以下场景仍应由人做最终判断：

- 多部门责任归属
- 高风险参数修改
- 合规与审计认定
- 敏感数据查看授权
- 影响客户或资金的最终操作

### 6.6 它不能在缺少权限上下文时回答全部问题

系统必须受项目、租户、角色、数据域限制。

因此它不能：

- 向客服暴露研发级日志明细
- 向普通角色暴露跨项目数据
- 向非审批角色暴露执行细节
- 向任何人暴露脱敏前敏感字段

### 6.7 它不是“一次建完就永远有效”的系统

这个系统要长期有效，必须持续做：

- 知识源接入
- 图谱修正
- MCP 治理
- 路径复盘
- 指标评估
- 反馈标注

没有治理运营，它会退化成另一个不可信知识库。

## 7. 面向 LightGraph 的推荐能力分层

```text
L1 交互层
  - 问答工作台
  - 工单协同
  - 审批工作台
  - 运营治理后台

L2 编排层（LightGraph）
  - Intent Router
  - Context Completion
  - Retrieval Planner
  - Tool Planner
  - Human Approval Gate
  - Trace Recorder
  - Feedback Loop

L3 证据层
  - Graph Retrieval
  - Vector Retrieval
  - BM25 Retrieval
  - SQL Query Service
  - MCP Tool Gateway

L4 知识治理层
  - Source Registry
  - Canonical Entity Resolver
  - Candidate Review
  - Graph Publish
  - Route Library

L5 事实层
  - 业务数据库
  - 图数据库
  - 对象存储
  - 日志平台
  - 外部业务系统
```

## 8. 推荐任务规划

以下任务规划按“先做正确抽象，再做业务闭环，再做扩张能力”排序。

### 8.1 工作流 A：统一能力目录与工具治理

目标：把“后台接口”重构成“可被 Agent 使用的 MCP 能力目录”。

任务：

1. 盘点后台接口，按查询类、建议类、执行类、管理类分组。
2. 抽象 capability code，而不是直接暴露 API path。
3. 为每个 capability 定义：
   - 业务说明
   - 输入 schema
   - 输出 schema
   - 权限范围
   - 风险等级
   - 缓存策略
   - 审计要求
4. 建立 MCP capability registry。
5. 建立启停、灰度、依赖影响分析能力。

输出物：

- MCP 能力总表
- 能力分级规范
- 能力审计规范
- 能力生命周期策略

### 8.2 工作流 B：知识图谱治理与入图规范

目标：把“数据库 + 文档 + 案例 + 接口”沉淀为可用于推理的业务知识图谱。

任务：

1. 定义 Source Registry。
2. 定义 Schema Graph、Business Graph、Case Graph 三类图谱边界。
3. 定义 canonical entity 与 alias 规则。
4. 定义 candidate -> review -> publish 主流程。
5. 定义 source version、graph revision、rollback 机制。
6. 定义敏感数据脱敏与禁止入图清单。

输出物：

- 图谱分层模型
- 实体归一规范
- 图谱发布门禁
- 数据脱敏规则

### 8.3 工作流 C：LightGraph 状态机设计

目标：把客服系统从“聊天回答”升级为“可解释诊断编排”。

任务：

1. 设计主状态流：
   - intent_detect
   - context_complete
   - evidence_plan
   - graph_retrieve
   - mcp_call
   - sql_query
   - evidence_merge
   - answer_generate
   - risk_gate
   - handoff_or_approve
   - feedback_writeback
2. 明确每个节点的输入、输出、失败回退。
3. 设计 trace schema。
4. 设计 human-in-the-loop 节点。
5. 设计降级路径：Graph 不足、MCP 不可用、SQL 超时、权限不足。

输出物：

- LightGraph 状态图
- 节点契约文档
- Trace / Audit 模型
- 降级策略表

### 8.4 工作流 D：问答能力与诊断能力拆层

目标：避免系统一开始就承担过重自动化责任。

建议拆成三层能力：

1. P0 问答辅助层：
   - 问题理解
   - 知识检索
   - 证据展示
   - 建议输出
2. P1 诊断协同层：
   - 路径推荐
   - 多工具联合查询
   - 工单草拟
   - 责任人建议
3. P2 受控执行层：
   - 审批申请
   - 低风险动作执行
   - 回滚建议
   - 自动化闭环指标

输出物：

- 能力分期矩阵
- 角色权限矩阵
- 审批门禁清单

### 8.5 工作流 E：评估体系与运营闭环

目标：保证系统不是“看起来很聪明，实际不可用”。

关键指标：

- 首屏可用答案率
- 有证据答案率
- 错答率
- 无法回答率
- MCP 调用成功率
- 图谱命中率
- 路径复用成功率
- 用户反馈有效率
- 工单草拟采纳率
- 审批建议采纳率

输出物：

- 评测指标定义
- 标注集构建方案
- 反馈闭环流程

## 9. 推荐分阶段执行顺序

### Phase 0：架构冻结与范围澄清

目标：先把边界说清楚。

建议先完成：

1. LightGraph 在系统中的职责定义
2. MCP capability 设计原则
3. 图谱分层模型
4. 风险分级与审批门禁
5. 脱敏边界与权限边界

### Phase 1：P0 可解释问答闭环

目标：先把“能回答、能解释、能追溯”做稳。

范围：

- 问题理解
- Graph/RAG/SQL/MCP 联合证据
- Execution Trace
- 只读能力
- 问题总结与工单草拟

### Phase 2：P1 诊断协同闭环

目标：从“回答”走向“协同处理”。

范围：

- 路径库
- 路径反馈
- 角色化答复
- 工单流转建议
- 高价值 MCP 组合调用

### Phase 3：P2 受控执行闭环

目标：从“建议”走向“审批后执行”。

范围：

- 执行前审批
- 低风险白名单执行
- 可回滚动作
- 风险审计

## 10. 当前建议立即启动的任务

如果现在就开始执行，建议先开以下 6 个任务包：

1. `LG-001` LightGraph 状态机与节点契约设计
2. `MCP-001` 后台能力盘点与 capability 抽象
3. `KG-001` 业务知识图谱分层与入图门禁设计
4. `SEC-001` 权限、脱敏、审计与审批边界设计
5. `EVAL-001` 评测指标、反馈闭环与样本集设计
6. `PILOT-001` 选择 3 个高频业务问题做试点闭环

推荐优先试点的 3 类问题：

1. 设备离线/状态异常
2. 告警未触发/误触发
3. 统计结果与页面不一致

原因：

- 这三类问题通常既需要静态知识，也需要实时证据；
- 既能检验图谱质量，也能检验 MCP 编排能力；
- 既适合客服辅助，也适合后续进入审批与工单链路。

## 11. 当前必须明确的待确认项

以下问题如果不确认，系统仍然只能停留在方案层：

1. LightGraph 在你这里承担的是“全编排引擎”还是“局部工作流引擎”。
2. 计划接入 MCP 的系统范围有哪些，是否先只覆盖查询类能力。
3. 哪些数据库允许结构入图，哪些数据库允许业务数据入图，哪些只能保留 schema 不进业务数据。
4. 哪些敏感字段必须脱敏或禁止入图。
5. 哪些问题类型属于 P0 试点范围。
6. 哪些动作永远不能自动执行。
7. 审批流复用现有系统还是在新系统内闭环。
8. 图谱发布是否允许单人发布，还是必须双人审核。

## 12. 结论

结论可以收敛为三句话：

1. 如果以 LightGraph 为核心二开，这个系统完全可以从“智能客服”升级为“证据驱动的业务诊断与协同平台”。
2. 它真正的价值不在于会聊天，而在于能把图谱、数据库、接口、日志、案例和实时工具编排成一条可解释、可审计、可复用的处理路径。
3. 它的边界也必须明确：不能把全部后台接口裸暴露成 MCP，不能把全量数据库原样塞进图谱，更不能绕过权限、审批和审计直接替代源系统执行生产动作。
