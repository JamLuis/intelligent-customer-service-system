# 架构评审与下一阶段演进建议

## 1. 文档目标

本文档用于评估当前“通用知识图谱 + 智能客服 + Agent 基座平台”设计是否合理，并输出：

- 当前架构优势
- 当前核心缺陷
- 性能风险评估
- 下一阶段演进方向
- 长期技术路线

目标不是建设一个普通知识库系统，而是建设：

```text
代码理解
+
数据库理解
+
知识图谱
+
Agent工具调用
+
业务诊断
+
自动排查
+
最终形成统一AI能力基座
```

---

## 2. 当前架构评分

| 项目 | 评分 | 评价 |
|------|------|------|
| 整体架构合理性 | 8.2/10 | 方向正确 |
| 扩展性 | 8.8/10 | 拆层合理 |
| 可维护性 | 7.8/10 | 后期需要治理 |
| Agent化能力 | 6.5/10 | 规划合理但未完全落地 |
| 性能风险控制 | 6/10 | 后期存在瓶颈 |
| 业务理解能力 | 5.5/10 | 当前仍偏知识检索 |

### 总体评价

> 当前设计已经超过普通企业知识库系统，正在向 **业务理解平台 + Agent 平台 + 智能诊断平台** 演进。

---

## 3. 当前设计合理部分

#### 3.1 PostgreSQL + Neo4j 双存储设计合理

#### 当前

```text
PostgreSQL
├─ 原始知识
├─ chunk
├─ embedding
├─ BM25
├─ candidate
└─ 状态管理

Neo4j
└─ 图谱草稿
```

#### 优势

- PostgreSQL负责事实存储
- Neo4j负责关系推理
- 避免所有查询压到图数据库
- 后期扩展性较强

#### 结论

✅ 合理

---

#### 3.2 Candidate审核机制合理

#### 流程

```text
原文
↓
block
↓
candidate entity
↓
candidate relation
↓
draft graph
↓
published
```

#### 优势

- 防止AI错误污染知识库
- 支持人工审核
- 支持知识治理

#### 结论

✅ 必须保留

---

#### 3.3 AI服务独立拆分合理

#### 当前

```text
Java
负责：
业务编排
数据库
状态管理

Python
负责：
Embedding
LLM
推理
抽取
```

#### 优势

- 后续切换模型成本低
- Java业务稳定
- Python负责AI能力演进

#### 结论

✅ 合理

---

#### 3.4 Evidence First方向正确

#### 当前

```text
证据
↓
检索
↓
LLM
↓
Fallback
```

不是：

```text
用户问题
↓
LLM直接回答
```

#### 优势

- 降低幻觉
- 支持可追溯
- 后期适合监管类系统

#### 结论

✅ 必须保留

## 4. 当前核心缺陷

#### 4.1 Embedding闭环未完全接通

#### 问题

当前embedding设计存在，但链路未形成完整闭环。

#### 风险

```text
只有BM25
↓
语义召回能力弱
↓
复杂业务问答失败
```

#### 优先级

P0

#### 建议

- 完成Embedding写入
- QueryVector接线
- 引入Hybrid Retrieval

#### 目标

```text
BM25
+
Vector
+
Graph
+
Rerank
```

---

#### 4.2 Neo4j未真正参与推理

#### 问题

当前图谱更偏展示层。

#### 风险

```text
图存在
↓
查询不走图
↓
图谱价值下降
```

#### 建议

增加：

```text
Question
↓
Entity Detect
↓
Graph Expand
↓
Path Search
↓
Evidence Merge
↓
LLM
```

#### 目标

真正让图参与推理。

#### 优先级

P1

---

## 9. 最终结论

### 架构结论

当前方向没有跑偏。

真正需要补的不是功能数量，而是：

```text
图谱真正参与推理
+
代码理解
+
数据库理解
+
业务关系抽象
+
Planner能力
```

最终目标：

```text
输入问题
↓
系统理解代码
↓
系统理解数据库
↓
系统理解日志
↓
系统理解业务关系
↓
自动输出定位路径
↓
给出修复建议
```

这将不再是传统知识库，而是统一AI业务理解平台。
