# Intelligent Customer Service System 系统架构总体设计

## 1. 文档信息

- 对应需求：面向 wnx-web 与 wnx-serve 的智能诊断与客服平台
- 关联 PM 产物：04 / 04B / 04C / 04D / 05
- 编写人：Copilot 初始化
- 版本：V0.1

## 2. 系统边界

| 边界类型 | 内容 |
| --- | --- |
| 本系统负责 | 多源工程知识入图、跨源实体关联、问题接入、诊断编排、证据链、知识检索、审批门禁、工具白名单、审计追踪 |
| 本系统不负责 | 设备原始接入、业务平台核心业务处理、原始告警生成、生产系统直接写入 |
| 上游系统 | wnx-web、wnx-serve、代码仓库、需求/设计/部署/运维文档源、设备协议、OpenAPI、数据库 schema、历史工单与研发记录、日志平台 |
| 下游系统 | Neo4j、PostgreSQL/pgvector、Redis、Flowable、LLM 提供方、对象存储、可观测平台 |
| 数据事实源 | wnx-serve 查询接口、日志平台、项目配置、数据库 schema、审批结果、图谱构建批次 |
| 业务事实源 | PM 五件套、目标平台权限模型、需求文档、设计文档、协议文档、部署说明、运维手册、案例沉淀 |

## 3. 形态与拆分决策

| 决策项 | 选项 | 决定 | 依据（量化） | 替代方案 | 不选原因 |
| --- | --- | --- | --- | --- | --- |
| 形态 | 单体 / 模块化单体 / 微服务 / 多端 | 模块化单体 + 外围独立能力服务 | 【假设】一期内部用户 DAU 小于 150，诊断峰值请求小于 5 req/s，1 到 1.5 月内需交付可用版本 | 全量微服务 | 服务治理、链路追踪、发布与联调成本过高 |
| 拆分依据 | 业务域 / 组织 / 伸缩性 / 合规 / 性能 | 按技术隔离和风险隔离拆分：前端、网关、诊断核心、MCP、图谱、RAG、流程 | MCP 需独立隔离查询与执行工具；图谱和向量库是独立基础设施；审批需独立治理 | 纯按业务域拆微服务 | 一期业务域尚未稳定，拆分收益低于成本 |
| BFF 是否引入 | 是 / 否 | 否 | 一期只有一个 Web 工作台，页面不需要多端差异聚合；前端接口峰值预计小于 40 QPS【假设】 | 单独 BFF | 增加一层服务但收益有限 |
| 网关 | 自建 / 云厂商 / 无 | Spring Cloud Gateway | 后续至少接入 3 类内部服务和 1 类审批回调，需统一鉴权、限流、审计和路由 | 直接由前端访问编排服务 | 无法统一做鉴权、审计和灰度 |

## 5.1 代码工程目录映射

```text
intelligent-customer-service-system/
   frontend/                 # Vue3 + Element Plus，对用户提供诊断工作台

   backend-java/             # Java Spring Boot 主后台，对外提供业务 API 和统一鉴权审计
      auth/                   # 登录、Token、SSO/RBAC 适配
      user/                   # 用户与角色
      project/                # 项目与数据范围
      device/                 # 设备上下文与设备诊断入口
      diagnosis/              # 诊断案例、证据链、AI Service 调用
      ticket/                 # 工单和历史问题
      approval/               # Flowable 审批与执行门禁
      audit/                  # 工具调用、审批、诊断审计

   ai-service-python/        # AI + GraphRAG / Unified Engineering Graph 能力
      document_parser/        # Docling / Unstructured / LlamaParse 结构恢复
      entity_extractor/       # LLM Extract 实体关系抽取
      graph_builder/          # Entity Normalize / Conflict Detect / Cross Link / Neo4j 写入
      rag/                    # PostgreSQL + pgvector 语义召回
      diagnosis_agent/        # LangGraph Diagnosis Agent

   mcp-server-node/          # MCP 工具层，隔离实时查询和受控执行
      tools/device/           # 设备状态、心跳、绑定关系
      tools/alarm/            # 告警规则、告警历史、触发结果
      tools/config/           # 项目配置、规则快照、阈值配置
      tools/log/              # API、任务、设备日志查询
      tools/statistics/       # 统计查询与审批后重算

   infra/                    # 本地和测试基础设施
      docker-compose.yml
      postgres/               # PostgreSQL + pgvector 初始化
      neo4j/                  # Neo4j 图谱存储
      redis/                  # 缓存、限流、任务状态
```

代码调用链：`frontend -> backend-java -> ai-service-python -> Neo4j / pgvector / LLM API`；实时系统调用链：`backend-java -> mcp-server-node -> wnx-web / wnx-serve / 设备系统 / 日志系统`。

## 6. 技术选型

| 类别 | 选型 | 版本 | 为什么选 | 替代方案 | 不选原因 | 风险 |
| --- | --- | --- | --- | --- | --- | --- |
| 后端语言/框架 | Java + Spring Boot | JDK 25 / Spring Boot 3.5.x | 新项目不背 Java 8 技术债，直接采用当前本机最新 JDK，并为虚拟线程等现代 Java 能力预留空间 | Node.js / Python / Java 8 + Spring Boot 2.7 | 编排核心、审批、企业治理链路更适合 Java 团队维护；Java 8 已进入存量维护阶段，不适合作为新项目主线 | 本地和 CI 必须统一安装 JDK 25；若接入旧系统 SDK，需检查字节码和依赖兼容性 |
| 前端框架 | Vue3 + Vite + Element Plus | Vue 3.5.x / Vite 5.x / Element Plus 2.x | 匹配你给出的目标骨架，前端开发体验和组件生态成熟 | 延续 Vue2 / React | Vue2 技术债高；React 会增加团队切换成本 | 需补足统一设计规范 |
| 移动端 | 暂不单独建设，后续考虑 H5 嵌入 | N/A | 一期只有桌面工作台需求，避免扩张范围 | 小程序 / 原生 App | 当前场景不需要单独移动端投入 | 后续多端扩展需补 BFF 评估 |
| 主数据库 | PostgreSQL + pgvector | PostgreSQL 16 / pgvector 0.7.x | 同时承载业务数据和向量检索，一期成本最低 | MySQL + 向量库 / Milvus | MySQL 无原生向量能力；Milvus 运维成本高 | 随 chunks 增长需评估索引与分区 |
| 缓存 | Redis | 7.x | 用于热点缓存、SSE 状态、限流计数、短期工具结果缓存 | Caffeine / 本地缓存 | 单实例本地缓存无法支撑多节点一致性 | 需要防止缓存击穿 |
| 消息队列 | PostgreSQL Outbox + Spring Scheduler | N/A | 一期异步量可控，避免额外引入 MQ | RabbitMQ / Kafka | 首期规模不大，独立 MQ 增加部署复杂度 | outbox 积压需监控 |
| 文件/对象存储 | MinIO（开发）/ S3 兼容 OSS（生产） | MinIO RELEASE / 对象存储托管版 | 存协议文档、案例附件、报告导出，兼容本地和云环境 | 本地磁盘 | 本地盘不利于扩容与审计 | 对象命名和权限策略需标准化 |
| 网关 | Spring Cloud Gateway | 2023.x | 与 Spring Boot 技术栈一致，支持路由、限流、认证、审计扩展 | Nginx 直转发 / Kong | Nginx 无业务级鉴权和上下文处理；Kong 新增运维成本 | 配置治理需规范 |
| 鉴权方案 | JWT Access Token + Gateway Token Relay + 项目级 RBAC | JWT 30 分钟 + Refresh 7 天【假设】 | 既支持独立项目起步，又可后续兼容 wnx-web 单点适配 | 纯 Session / 全量 OAuth2 立刻接入 | Session 不适合多服务；OAuth2 细节取决于现有平台未明 | 权限复用方案仍待确认 |
| 监控/日志/链路 | Prometheus + Loki + Grafana + OpenTelemetry | Prometheus 2.x / Loki 3.x / Grafana 11.x | 满足指标、日志、链路统一观测，且与你的目标架构一致 | ELK / SkyWalking | 一期更重视低成本部署和统一看板 | Loki 查询性能需关注标签设计 |
| 任务调度 | Flowable + Spring Scheduler | Flowable 6.8.x | 审批流程、回调状态机和简单定时任务可统一治理 | Camunda / 纯自研 | Camunda 学习成本更高；纯自研审批长期维护重 | 二期接入时需明确审批归属 |
| 实时通信 | SSE | HTTP SSE | 诊断过程主要是服务端单向推送，简单且易于网关透传 | WebSocket | 一期不需要双向持续会话 | 浏览器断线重连策略需补足 |
| 设备接入 | 不直接接设备，统一经 MCP 查询目标系统 | HTTP / 内部 SDK / MCP | 避免本系统直接承担设备协议接入复杂度，聚焦诊断 | 本系统重建设备接入链路 | 范围过大，与一期目标不匹配 | 上游接口质量直接影响体验 |
| AI/视频分析 | LLM Provider Adapter（DeepSeek/Qwen 优先，Claude/GPT 作为增强） | 适配层自定义 | 允许多模型切换，先用成本较低模型做理解与规划，复杂场景再升级 | 单一模型绑定 / 自建模型 | 单一绑定有供应商风险；自建模型成本过高 | 成本和时延需持续监控 |

## 7. 权限与认证体系

| 项 | 内容 |
| --- | --- |
| 认证方式 | 系统内部统一 JWT，网关负责 Token 校验与上下文透传；后续可适配 wnx-web SSO |
| Token 有效期 | Access Token 30 分钟【假设】 |
| 刷新策略 | Refresh Token 7 天，刷新时重新校验角色和项目范围【假设】 |
| 鉴权模型 | RBAC + 项目级数据范围控制，执行类动作再叠加审批权限 |
| 数据范围维度 | 项目、角色、审批归属、审计只读范围 |
| 多端会话策略 | 一期仅 Web 工作台，多标签页共享会话；后续嵌入式接入走同源或 Token Relay |
| 越权防护 | 网关鉴权 + 服务端二次校验 + 字段级脱敏 + 执行动作白名单校验 |
| 审计要求 | 保存问题输入、诊断证据、工具调用、审批、执行、回滚与关闭结果，留存期待业务确认 |
