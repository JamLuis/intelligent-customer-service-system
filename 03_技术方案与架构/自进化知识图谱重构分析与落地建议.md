# 自进化知识图谱重构分析与落地建议

## 1. 文档目标

本文档基于以下输入进行重构分析：

- 新版架构图与 PreProcess 14 步设计
- LightRAG 参考实现吸纳计划
- 当前仓库真实代码结构
- 当前数据库与接口契约

本文档输出四类结果：

- 当前实现与目标架构的差距判断
- 本轮重构的核心切入点
- 各子系统的重构建议
- 可执行的落地顺序与约束

目标不是简单把现有代码拆文件，而是把当前“可运行的单体实现”演进成“可扩展、可回溯、可治理的知识生产线”。

---

## 2. 当前代码现状判断

### 2.1 总体判断

当前项目已经具备以下基础：

- Java 后端已形成知识录入、候选实体关系、草稿图构建、检索问答的主业务骨架
- Python AI Service 已形成解析、抽取、embedding、问答的统一入口
- PostgreSQL、pgvector、Neo4j、Redis 基础设施已具备
- 前端已具备知识中心、问答中心、模型配置等管理入口
- MCP 工具边界已具备，后续可接入 Planner 作为实时证据源

但当前实现本质上仍是：

```text
rawText
↓
简单分块
↓
规则/LLM 抽取
↓
candidate
↓
draft graph
↓
chat answer
```

这说明项目目前具备“知识抽取原型”能力，但尚未进入“自进化知识图谱系统”阶段。

### 2.2 当前最主要的结构性问题

#### 问题一：Python AI Service 仍是单文件单体

当前 `ai-service-python/app/main.py` 约 1400 行，承担了以下多种职责：

- HTTP 路由
- 解析器分发
- block 构建
- SQL / Markdown / CSV 解析
- 规则抽取
- LLM OpenIE 抽取
- embedding 调用
- answer evidence 拼装
- retrieval plan 输出

这意味着：

- 模块边界不清晰
- 无法对单个步骤独立测试与替换
- 新增 parser / chunker / extractor 时会持续堆积到单文件
- 后续引入 OCR、Layout Recover、IR Builder、Quality Check 时改动风险极高

#### 问题二：PreProcess Layer 实际不存在

当前 `parse_knowledge()` 与 `build_blocks()` 只完成了轻量 block 切分，距离目标 PreProcess 14 步差距很大。

当前已有能力主要是：

- Markdown 分段
- SQL DDL 解析
- CSV 行切块
- 文本 normalize

当前缺失能力包括：

- Format Parse 路由层
- OCR
- Layout Recover
- IR Builder
- Structure Detect
- 多策略 Chunk Build
- Metadata Build
- Classification
- Entity Pre-Extract 与 Relation Pre-Extract 的预处理分层
- Summary Build
- Quality Check
- 重复检测与内容哈希治理

#### 问题三：Java 编排仍是同步顺序调用

`backend-java/src/main/java/com/company/smartsupport/knowledge/KnowledgeIngestionPipeline.java` 当前执行链是：

```text
parse
↓
persist block
↓
embed
↓
extract
↓
graph build
↓
write neo4j draft
```

这个设计适合 P0/P1 阶段，但不适合后续的长链路演进，原因是：

- 各阶段状态太粗
- 无 batch 粒度调度
- 无阶段级重试与取消
- 无 sidecar / IR / chunk version 管理
- 无异步拆分能力
- 一旦 parse 阶段变复杂，同步链会明显拖慢录入体验

#### 问题四：当前候选抽取还不是“治理前候选层”

当前 candidate 的存在是正确的，但仍有三个不足：

- 缺少 chunk 级去重和文档级去重
- 缺少跨 chunk 原子合并机制
- 缺少从 candidate 到 taxonomy proposal / pattern proposal 的治理扩展面

也就是说，当前 candidate 更像“抽取结果暂存区”，还不是“知识治理输入层”。

#### 问题五：检索与问答链条已存在，但 Planner 闭环未形成

当前 Python 侧已有 `build_answer_evidence_pack()`、`answer_prompt()`、`retrieve_plan()`；Java 侧已有 `ChatAnswerService`、`GraphSearchService`、`HybridRetrievalService`。

这说明使用层入口已经具备雏形。

但当前仍缺：

- LangGraph 式显式状态图
- MCP 证据纳入统一路径规划
- 路径失败反馈
- Planner 路由评分
- 基于反馈的检索与路径迭代

因此当前仍是“检索增强问答”，不是“可进化 Planner”。

## 3. 当前架构与目标架构差距

| 目标层 | 目标能力 | 当前状态 | 差距判断 |
| --- | --- | --- | --- |
| PreProcess | 14 步生产线 | 只有 parse + block | 差距极大 |
| Candidate Store | 候选治理输入层 | 已有 candidate entity/relation | 基础可用，但治理不足 |
| Embedding | block/entity/relation 多对象向量化 | 仅 block embedding 主路径可用 | 需要扩展 |
| Cluster | HDBSCAN 聚类 | 未实现 | 空白 |
| Pattern Mining | 模式发现 | 未实现 | 空白 |
| Auto Taxonomy | 类型/关系提案 | 未实现 | 空白 |
| Human Review | 候选、taxonomy、pattern 审核 | 仅局部管理能力 | 不完整 |
| Graph Publish | 草稿到正式发布闭环 | draft graph 已有 | publish 治理不足 |
| Planner | 显式状态图编排 | 仅 retrieval plan 雏形 | 差距较大 |
| Feedback | 反馈驱动持续优化 | 未形成闭环 | 空白 |

结论：

> 当前系统已经完成了“架构方向验证”，但还没有完成“知识生产层”和“知识治理层”的工程化落地。

## 4. 重构原则

### 4.1 先拆职责，再补能力，不直接重写

不建议直接重写 `ai-service-python/app/main.py`，因为当前主链路已经可跑，完全推倒会带来回归风险。

建议顺序是：

```text
先抽模块边界
↓
再把现有逻辑迁入模块
↓
再增量接入新能力
↓
最后切异步 worker
```

### 4.2 先定义统一中间表示，再扩展 parser

如果没有统一 IR，后续每接一个 parser 都会继续输出自己的一套 block 结构，最终导致：

- chunker 无法统一
- metadata 无法统一
- quality check 无法统一
- sidecar 无法统一

因此本轮重构的第一关键产物不是 OCR，也不是新 parser，而是 `IRDoc / IRBlock / IRSpan / IRAsset` 的统一契约。

### 4.3 先保留 Java 总编排，再逐步下沉为阶段调度

当前 Java 后端已经承担知识录入、任务状态、草稿图写入、数据库落库，是当前稳定编排中心。

因此建议：

- 短期保留 Java 作为总调度入口
- Python 先完成内部流水线分层
- 当 PreProcess 和抽取阶段耗时增长后，再把 Java 的同步链路切成异步阶段任务

### 4.4 先做“可回溯”，再做“更智能”

很多能力看起来是算法问题，实际首先是工程可回溯问题。

例如：

- 没有 sidecar，无法知道 chunk 来源
- 没有 content hash，无法去重
- 没有 parser version，无法比较抽取质量
- 没有 stage status，无法定位失败点

因此优先级必须是：

```text
可追溯
>
可治理
>
可优化
>
可智能化
```

### 5.2 第一阶段必须抽离的模块

第一阶段不要求把所有能力全部实现，但至少应先把以下逻辑从 `main.py` 中抽离：

- `parse_knowledge()` → `api/routes/knowledge.py`
- `build_blocks()`、`markdown_blocks()`、`sql_blocks()`、`csv_blocks()` → `preprocess/parsers/*`
- `extract_candidates()` 与规则抽取方法 → `extraction/pipeline.py` + `rule_extractor.py`
- `extract_openie_with_llm()`、`openie_prompt()` → `extraction/openie_extractor.py`
- `embed_blocks()` → `embedding/service.py`
- `build_answer_evidence_pack()`、`answer_prompt()`、`fallback_evidence_answer()` → `answer/*`
- `retrieve_plan()` → `retrieval/planner.py`

这样做的价值是：

- 主链路不变
- 风险最小
- 后续新增能力有明确挂载点

### 5.3 第二阶段新增能力建议

在模块边界形成后，再逐步增加：

- `routing.py`：解析器路由
- `ir/models.py`：统一 IR
- `metadata/sidecar.py`：sidecar 输出
- `quality/dedup.py`：内容哈希与重复检测
- `chunking/paragraph_semantic.py`：默认切块策略
- `normalize/structure_detector.py`：标题层级与 sectionPath 恢复

### 5.4 Python 侧最关键的新增数据对象

建议新增以下对象定义：

| 对象 | 作用 |
| --- | --- |
| `IRDoc` | parser 统一输出 |
| `IRBlock` | 结构块表示 |
| `TextUnit` | chunk 后的语义单元 |
| `ChunkMetadata` | sectionPath、parser、confidence、pageNo 等 |
| `ParseArtifact` | parse 阶段输出聚合对象 |
| `ExtractArtifact` | entity/relation/summary/labels 输出聚合对象 |
| `QualityReport` | 覆盖率、重复率、超长块、空块等质检结果 |

这些对象一旦稳定，后续 OCR、Docling、MinerU、代码解析、日志解析都可以接入同一条链。

### 5.5 实体/关系稳定抽取是系统核心

这两份文档当前对“结构重构”和“PreProcess 生产线”描述较完整，但如果从系统价值看，最核心的能力仍然是：

```text
稳定、准确、可回溯地抽取实体和关系
```

因此抽取层不能只写成 `Rule Extract + OpenIE`，必须单独设计成一条可测试、可解释、可治理的子流水线。

当前代码已经具备一些正确雏形：

- `/knowledge/extract` 已采用 rule-first 思路
- 抽取受 taxonomy 中 entity type / relation type 约束
- SQL DDL 抽取是确定性规则，稳定性高
- LLM OpenIE 已设置 `temperature=0`，并要求输出严格 JSON
- `canonical_resolver.py` 已有 unique key、alias、regex、embedding、CodeGraph、LLM verify 的合并评分思路

但当前仍缺少一层正式的“抽取治理模型”。建议把抽取设计提升为以下链路：

```text
TextUnit
↓
Candidate Generation
  ├─ Deterministic Rule
  ├─ Parser-aware Extractor
  ├─ Taxonomy Rule
  ├─ NER / GLiNER
  └─ LLM OpenIE
↓
Evidence Grounding
↓
Normalization / Canonicalization
↓
Relation Assembly
↓
Validation / Gating
↓
Merge / Dedup
↓
Candidate Store
↓
Review / Publish
```

这条链路的关键不是让 LLM 抽得更多，而是让每个候选都回答清楚五个问题：

1. 从哪段原文来？
2. 为什么认为它是这个实体类型？
3. 为什么认为这两个实体之间有这个关系？
4. 置信度由哪些信号组成？
5. 低置信度时应该拒绝、降级、还是进入人工审核？

### 5.6 候选实体与候选关系契约补强

为了保证抽取稳定，建议候选对象必须从“简单结果”升级为“带证据的判断”。

候选实体建议字段：

| 字段 | 说明 |
| --- | --- |
| `tempId` | 单次抽取中的临时 ID |
| `entityType` | taxonomy 约束下的实体类型 |
| `rawName` | 原文出现形式 |
| `canonicalName` | 归一化名称 |
| `aliases` | 别名列表 |
| `mentionSpans` | 原文 span，包含 sourceId、blockId、start、end |
| `evidenceRefs` | 支撑该实体的证据块 |
| `extractor` | rule / parser / ner / llm_openie / human |
| `extractorVersion` | 抽取器版本 |
| `confidence` | 总置信度 |
| `confidenceBreakdown` | 规则、span、类型、上下文、LLM 校验等分项 |
| `mergeKey` | 合并键，优先使用 unique key / 业务 ID |
| `qualityFlags` | ambiguous、no_span、type_conflict、too_generic 等 |
| `reviewStatus` | accepted / reviewing / rejected / merged |

候选关系建议字段：

| 字段 | 说明 |
| --- | --- |
| `relationType` | taxonomy 约束下的关系类型 |
| `sourceTempId` | 源实体 |
| `targetTempId` | 目标实体 |
| `rawPredicate` | 原文触发词或 LLM predicate |
| `direction` | forward / reverse / unknown |
| `evidenceSpan` | 关系触发证据 span |
| `extractor` | rule / parser / llm_openie / human |
| `confidence` | 总置信度 |
| `confidenceBreakdown` | span、触发词、实体置信、类型匹配、方向校验等 |
| `dedupKey` | source + relationType + target + evidence scope |
| `validationFlags` | missing_entity、direction_uncertain、predicate_not_allowed 等 |
| `reviewStatus` | accepted / reviewing / rejected / merged |

如果实体/关系没有 evidence span，默认不能自动入图，只能进入 reviewing 或 rejected。

### 5.7 抽取准确性的关键策略

建议抽取层遵循以下硬规则：

| 策略 | 说明 |
| --- | --- |
| Span-grounded | 实体和关系必须绑定原文 span 或结构化 parser 来源 |
| Taxonomy-constrained | LLM 不允许自由创造 entity type / relation type |
| Rule-first | SQL、枚举、key-value、日志模式、代码符号等确定性来源优先 |
| Parser-aware | DDL、表格、代码、日志走专用抽取器，不交给通用 OpenIE 兜底 |
| LLM-as-supplement | LLM 只补召回，不直接决定最终发布 |
| Confidence gating | 高置信自动 accepted，中置信 reviewing，低置信 rejected |
| Direction validation | 关系方向必须由触发词、模板或结构关系校验 |
| Negative constraints | Prompt 和规则中维护禁止项，避免“公司下有五个部门”被抽成坏实体 |
| Deterministic merge | 合并必须优先 unique key / alias / regex，embedding 只能作为提示 |
| Regression set | 每类抽取规则必须有正例、反例、边界样本 |

其中最重要的是：

```text
没有证据 span 的候选，不允许自动进入图谱。
```

### 5.8 抽取置信度建议

建议将实体置信度拆成可解释分项，而不是只保存一个浮点数。

实体置信度参考：

| 信号 | 权重建议 | 说明 |
| --- | --- | --- |
| parser / unique key | 0.30 | DDL 表名、字段名、代码符号、业务 ID |
| taxonomy type match | 0.20 | 类型是否命中允许范围 |
| evidence span quality | 0.20 | span 是否完整、是否过泛、是否噪声 |
| rule / regex hit | 0.15 | 是否命中确定性规则 |
| context support | 0.10 | sectionPath、邻近词、上下文是否支持 |
| llm verify | 0.05 | LLM 校验只做小权重补充 |

关系置信度参考：

| 信号 | 权重建议 | 说明 |
| --- | --- | --- |
| source/target entity confidence | 0.25 | 两端实体是否可靠 |
| relation trigger match | 0.25 | 触发词、结构边、parser 关系是否明确 |
| type pair allowed | 0.20 | entity type pair 是否允许该关系 |
| evidence span quality | 0.15 | 关系证据是否完整 |
| direction confidence | 0.10 | 方向是否明确 |
| llm verify | 0.05 | LLM 校验只做补充 |

建议门禁：

| 总分 | 处理 |
| --- | --- |
| `>= 0.88` | 可自动 accepted，但仍保留 evidence |
| `0.65 - 0.88` | reviewing |
| `< 0.65` | rejected 或仅保留为低置信样本 |

### 5.9 抽取模块建议结构

建议将 `extraction/` 明确拆成以下模块：

```text
extraction/
  pipeline.py
  models.py
  candidate_generator.py
  rule_extractor.py
  parser_extractors/
    sql_ddl_extractor.py
    table_extractor.py
    code_symbol_extractor.py
    log_event_extractor.py
  ner_extractor.py
  openie_extractor.py
  evidence_grounder.py
  normalizer.py
  relation_assembler.py
  validator.py
  confidence.py
  merger.py
  regression_cases.py
```

其中：

- `candidate_generator.py` 负责聚合 rule / parser / ner / llm 的候选输出
- `evidence_grounder.py` 负责把候选绑定到 TextUnit span
- `validator.py` 负责 taxonomy、类型对、方向、证据完整性校验
- `confidence.py` 负责生成 `confidenceBreakdown`
- `merger.py` 负责同名实体、同义实体、重复关系合并
- `regression_cases.py` 负责抽取回归样本入口

这样抽取能力才会稳定地演进，而不是继续在一个函数里累积规则。

### 5.10 抽取回归评测必须前置

如果最看重准确稳定，那么 RG-00 不能只做接口 smoke，还必须补一套抽取 gold set。

建议至少建设以下样本集：

| 样本类型 | 用途 |
| --- | --- |
| SQL DDL 正例 | 表、字段、主键、注释、约束抽取 |
| SQL DDL 反例 | 注释缺失、复杂类型、默认值、联合主键 |
| Markdown 业务正例 | 模块、流程、规则、角色、接口抽取 |
| 枚举结构正例 | “包含 A、B、C”“有 N 个 X” |
| 坏实体反例 | “五个部门”“相关信息”“系统能力”等泛词 |
| 关系方向反例 | 管理/被管理、依赖/被依赖、调用/被调用 |
| LLM OpenIE 边界样本 | 代词、省略、长句、多关系句 |
| 噪声样本 | 页眉页脚、目录、重复段落、日志堆栈 |

建议指标：

| 指标 | 目标 |
| --- | --- |
| Entity Precision | P0 不低于 0.90 |
| Entity Recall | P0 不低于 0.75 |
| Relation Precision | P0 不低于 0.85 |
| Relation Recall | P0 不低于 0.65 |
| Bad Entity Reject Rate | P0 不低于 0.90 |
| Evidence Span Coverage | P0 不低于 0.95 |

系统初期可以牺牲部分召回，但不能牺牲 precision。因为错误实体和错误关系一旦进入图谱，会污染后续 Planner 与反馈闭环。

## 6. Java Backend 重构建议

### 6.1 当前问题定位

`KnowledgeIngestionPipeline` 当前职责过重，同时承载：

- 阶段状态推进
- Python 调用
- block 持久化
- embedding 回写
- candidate 入库
- draft graph 构建
- Neo4j 写入

建议把它从“执行器”改成“总编排器”。

### 6.2 建议拆分的服务边界

建议演进为：

```text
knowledge/
  KnowledgeIngestionOrchestrator
  ParseStageService
  EmbeddingStageService
  ExtractStageService
  GraphBuildStageService
  GraphPublishStageService
  KnowledgeTaskStateService
```

对应职责：

- `KnowledgeIngestionOrchestrator`：只负责编排顺序与失败回滚策略
- `ParseStageService`：调用 Python parse，并落库 block / sidecar / parse metadata
- `EmbeddingStageService`：处理 embedding 回写与版本记录
- `ExtractStageService`：处理 candidate entity/relation 入库
- `GraphBuildStageService`：构建 draft graph
- `GraphPublishStageService`：后续承接 publish 闭环
- `KnowledgeTaskStateService`：统一状态迁移、重试次数、错误落库

### 6.3 Java 当前最值得保留的部分

当前 Java 侧有三部分不建议重写：

- `KnowledgeRepository` 的数据落库主干
- `GraphTaxonomyService` 的 taxonomy 读取入口
- `AiServiceClient` 的 Python 边界调用方式

建议在这些稳定边界之外做增量分层，而不是整体换框架。

### 6.4 中期异步化建议

当 parse / OCR / chunk / extract 变重后，建议演进为：

```text
KnowledgeSourceService
↓
create ingestion task
↓
submit preprocess stage
↓
submit extract stage
↓
submit graph build stage
↓
submit publish/review stage
```

短期可以先使用数据库任务表驱动；中期再切 Kafka topic。

这样做的原因是：

- 当前项目已有 `knowledge_ingestion_task` 表，适合先承接阶段任务化
- 先用库表状态机即可完成幂等、重试、失败恢复
- 不必过早引入 Kafka 运维复杂度

## 7. 数据模型补强建议

### 7.1 当前可复用基础

当前已具备以下表基础：

- `knowledge_source`
- `knowledge_ingestion_task`
- `graph_asset`
- `graph_revision`
- `graph_protected_taxonomy`
- `knowledge_model_config`

这些表说明主数据框架已具备，不需要重做主表体系。

### 7.2 建议新增或补强的字段/对象

建议优先补强以下数据：

| 对象 | 建议补强内容 |
| --- | --- |
| `knowledge_source` | `content_hash`、`parser_version`、`preprocess_status` |
| `knowledge_block` | `unit_type`、`section_path`、`chunk_strategy`、`summary`、`quality_score` |
| `knowledge_ingestion_task` | `stage_code`、`attempt_no`、`retryable`、`input_ref`、`output_ref` |
| candidate entity/relation | `merge_key`、`dedup_key`、`extractor_version`、`review_status` |
| graph build record | `source_version`、`taxonomy_version`、`embedding_version` |

### 7.3 Sidecar 落地建议

建议 sidecar 不单独引入复杂文件存储方案，第一阶段直接以以下二选一方式实现：

- 方案 A：sidecar JSON 存 PostgreSQL JSONB
- 方案 B：sidecar JSON 落磁盘/对象存储，数据库仅存 URI

当前阶段更推荐方案 A，因为：

- 查询与比对更方便
- 无需增加额外存储系统
- 便于调试和回放

```text

↓

↓

↓

↓

↓
published graph
↓

```

如果没有这类管理界面，后续即使后端能力补齐，也很难做质量治理。

## 9. MCP 与 Planner 衔接建议

### 9.1 当前状态

当前 `mcp-server-node/src/index.ts` 已提供基础 Mock 能力，Java 后端也已具备 `McpServerClient` 边界。

这意味着工具证据通道已经存在。

### 9.2 下一步建议

Planner 不要直接从“问答生成”开始做，而是先把证据路由做出来：

```text
question
↓
intent / entity detect
↓
选择 graph / vector / bm25 / mcp / codegraph
↓
多路证据融合
↓
answer
```

也就是说，第一步不是实现完整 LangGraph，而是先把当前 `retrieve_plan()` 从静态策略升级为可解释的证据路径规划器。

## 10. 建议的重构阶段划分

### 阶段 A：结构拆分，不改主行为

目标：把单体逻辑拆出稳定边界。

范围：

- Python `main.py` 拆模块
- Java `KnowledgeIngestionPipeline` 拆阶段服务
- 抽出统一 DTO / schema
- 不改变主接口契约

完成后结果：

- 系统仍按原路径运行
- 但具备新增 PreProcess 能力的挂载点

### 阶段 B：补齐 PreProcess 基础能力

目标：先让 PreProcess 成为真正的生产线。

范围：

- parser routing
- IRBuilder
- structure detect
- paragraph semantic chunking
- metadata build
- content hash + dedup
- summary build
- quality check

完成后结果：

- parse 输出从 block 列表升级为可追溯 artifact
- 为 extract / review / publish 奠定稳定输入

### 阶段 C：补齐治理层

目标：让 candidate 不再只是暂存区。

范围：

- entity/relation merge
- review status 细化
- taxonomy proposal
- pattern proposal
- graph publish 闭环

完成后结果：

- 知识治理层形成
- 可以区分 draft、reviewing、published、rejected

### 阶段 D：补齐使用与学习层

目标：从检索问答升级为 Planner 闭环。

范围：

- evidence routing
- planner state machine
- MCP evidence integration
- feedback event
- evaluation store
- rerank / path score

完成后结果：

- 系统开始具备“越来越准”的基础条件

## 12. 风险判断

| 风险 | 描述 | 建议 |
| --- | --- | --- |
| 过早重写 Python 主链路 | 容易把现有可运行链条打断 | 先拆模块，再迁逻辑 |
| 过早引入 Kafka | 当前治理链条尚未稳定 | 先用任务表状态机 |
| 没有统一 IR 就扩 parser | 后续每个 parser 都会产生新口径 | 先定义 IR |
| 直接上复杂 OCR / 布局恢复 | 会显著拉长周期 | 先做文本与结构路由层 |
| Candidate 无法追踪来源 | 后续审核与纠错无从下手 | 必须补 span / metadata / sidecar |
| Graph publish 规则不清 | 容易让低质量抽取污染图谱 | 先补 draft/review/publish 门禁 |

---

## 13. 结论

当前项目不需要推翻重来，核心问题也不是“模型能力不够”，而是“知识生产链缺少工程分层与治理基础”。

本轮重构的正确方向不是：

```text
继续在 main.py 中叠加功能
```

而是：

```text
先拆服务边界
↓
定义统一 IR
↓
补齐 PreProcess
↓
补齐 candidate 治理
↓
补齐 graph publish
↓
补齐 planner / feedback
```

如果按这个顺序推进，当前代码基础可以平滑演进到新版架构，而不需要中断现有主链路。

下一份文档《PreProcess 与自进化图谱重构任务规划》用于把以上建议转成可派发、可验收的任务包。
