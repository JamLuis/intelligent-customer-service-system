# 知识库问答与模型配置隔离设计

## 1. 背景与目标

本阶段目标是把 `/chat` 从 Mock 诊断入口升级为“必须先从知识库寻找答案”的问答验证链路，用真实知识库检索结果来验证图谱关系质量、证据覆盖和问答效果。

同时，模型配置必须从当前“一个表单切换本地/云端”的形态改为强隔离：

1. **用途隔离**：聊天对话模型与知识抽取模型分开配置、分开验证、分开启用。
2. **模式隔离**：同一用途下，本地模型参数与云端模型参数分开保存；切换 tab 不得覆盖另一个 tab 的配置。
3. **证据优先**：问答模型只能基于检索到的知识库证据回答；没有证据时必须明确“不足以回答”，不得编造。
4. **可验证**：每次回答必须返回命中的实体、关系、来源块、图谱路径、模型配置版本和降级原因。

## 2. 当前实现差距

| 模块 | 当前状态 | 差距 |
| --- | --- | --- |
| `/chat` 前端 | 创建 session 后调用诊断 Mock 流程 | 尚未直接展示知识库检索证据与问答引用 |
| `DiagnosisController` | 仍调用 `MockSupportService.startDiagnosis` | 未接入真实 GraphSearch + Answer Generator |
| `GraphSearchService` | 已有 `/api/v1/graphs/search/diagnosis`，返回 hybrid/vector evidence 骨架 | 尚未把检索证据打包给对话模型生成答案 |
| `knowledge_model_config` | 一个项目一条配置，服务于知识抽取 | 无法区分聊天/抽取；本地/云端切换会混用字段 |
| 前端模型配置页 | segmented 切换 `providerMode`，同一 form 对象承载所有参数 | 切 tab 会复用/污染参数，不满足隔离要求 |

## 3. 总体链路

```text
用户问题
  -> 会话建单 / 上下文补齐
  -> Query Planner：抽取关键词、向量查询文本、可能实体
  -> Knowledge Retrieval：BM25 + pgvector + Neo4j 图关系 + source evidence
  -> Evidence Pack：按来源块、关系路径、置信度、时间排序
  -> Answer Generator：对话模型仅基于 Evidence Pack 生成答案
  -> Answer Verifier：检查答案是否引用证据、是否越界、是否需要追问
  -> 前端展示：答案 + 引用证据 + 图谱路径 + 执行过程 + 反馈入口
```

## 4. 模型配置隔离方案

### 4.1 配置用途

| purpose | 中文名 | 使用位置 | 默认启用策略 |
| --- | --- | --- | --- |
| `knowledge_extract` | 知识抽取模型 | `/knowledge/extract` OpenIE、normalize 校验 | 可降级，规则抽取继续运行 |
| `chat_answer` | 对话问答模型 | 知识库问答、追问、答案总结 | 不可绕过证据；模型失败则返回检索证据摘要 |

### 4.2 数据模型建议

新增通用配置表，替代后续继续扩展 `knowledge_model_config`：

```text
ai_model_profile
  tenant_id
  project_id
  purpose                -- knowledge_extract / chat_answer
  provider_mode          -- cloud / local
  profile_key            -- default-cloud / default-local / gemma-local-gguf
  display_name
  provider               -- bailian / openai / local-openai-compatible / llama-cpp
  api_base_url
  api_key_ciphertext     -- 加密存储，前端只返回 masked
  workspace_id
  model_name
  embedding_model
  embedding_dim
  local_runtime          -- ollama / llama.cpp / lm-studio / vllm
  model_file_path        -- 仅本地 GGUF 场景使用
  context_window
  temperature
  max_tokens
  force_graph_grounding -- 仅 chat_answer 生效，强制答案必须引用知识库关系/证据
  enabled
  active
  status
  last_check_result
  updated_by / updated_at
```

约束：

1. `UNIQUE(tenant_id, project_id, purpose, provider_mode, profile_key)`。
2. 同一 `(tenant_id, project_id, purpose)` 只能有一个 `active=true`。
3. 前端切换本地/云端 tab 时只切换 active profile，不改变另一个 tab 的表单状态。
4. 旧 `knowledge_model_config` 仅作为兼容读取来源，迁移后由 `purpose=knowledge_extract` 的 profile 承接。

### 4.3 前端交互规则

每个用途一张配置页或一个主页面下的用途 Tabs：

```text
模型配置
  ├─ 对话问答模型 chat_answer
  │   ├─ 云端大模型 tab：cloudForm
  │   └─ 本地模型 tab：localForm
  └─ 知识抽取模型 knowledge_extract
      ├─ 云端大模型 tab：cloudForm
      └─ 本地模型 tab：localForm
```

强约束：

1. `cloudForm` 与 `localForm` 是两个独立对象，不允许共用同一个 `form`。
2. 切 tab 只切展示，不自动写库；必须点击“保存当前 tab 配置”。
3. “设为当前使用”与“保存配置”分离，避免用户编辑草稿后立即影响生产问答。
4. 验证连接只验证当前 tab profile，并把结果写回该 profile 的 `last_check_result`。
5. 页面必须显示当前 `/chat` 使用的 active profile 和知识抽取使用的 active profile。

### 4.4 强制关系图谱回答开关

`chat_answer` profile 与 `/chat` 页面均提供 `forceGraphGrounding` 开关，最终执行规则为：

1. 前端开关用于当前问题即时覆盖，Profile 开关用于默认策略。
2. 后端组装请求时执行 `request.forceGraphGrounding OR activeProfile.forceGraphGrounding` 的强约束语义。
3. 开关开启后，Answer Generator 必须优先依据 `graphPaths`、`matchedEntities`、`vectorEvidence` 生成回答；没有来源块、实体或关系证据时直接返回 `cannotAnswerReason=NO_KNOWLEDGE_EVIDENCE/NO_GRAPH_EVIDENCE`。
4. 开关开启后，模型输出必须包含 `evidenceRefs`；若模型生成了无引用答案，系统丢弃该答案并降级为证据摘要或不可回答。
5. 开关关闭时，系统仍然先检索知识库并展示证据，但允许返回“证据摘要式”回答；不得把外部常识伪装成知识库结论。

## 6. 问答生成策略

### 6.1 Answer Prompt 边界

对话模型输入只能包含：

1. 用户问题与已补齐上下文。
2. Evidence Pack：来源块摘要、实体关系、图谱路径、来源文件、更新时间、置信度。
3. 输出格式要求。

禁止输入：

1. 未经脱敏的 API Key、内网密钥、原始敏感日志。
2. 未命中的知识库外部猜测。
3. 发布状态不是 `published/accepted` 且未声明为候选的关系。

### 6.2 输出 Schema

```json
{
  "answer": "基于证据的回答",
  "confidence": 0.0,
  "evidenceRefs": [
    {"blockId": "...", "sourceId": "...", "fileName": "...", "quote": "..."}
  ],
  "graphPaths": [
    {"nodes": ["..."], "relations": ["..."], "confidence": 0.0}
  ],
  "missingContext": ["需要补充的问题"],
  "cannotAnswerReason": "证据不足时填写",
  "modelProfileId": "...",
  "degraded": false
}
```

### 6.3 回答规则

| 场景 | 系统行为 |
| --- | --- |
| 证据 >= 1 且置信度足够 | 生成答案，并逐条引用来源 |
| 证据不足 | 不调用或不采纳 LLM 编造，返回“知识库证据不足”并建议导入/补充资料 |
| 知识关系冲突 | 展示冲突来源，要求人工复核，不给确定结论 |
| 对话模型不可用 | 返回检索证据摘要，标记 `degraded=true` |
| 查询命中大量无关证据 | 降低置信度，记录 queryId 用于后续优化 |

## 7. API 设计草案

| API | 用途 |
| --- | --- |
| `GET /api/v1/admin/model-profiles?purpose=chat_answer` | 查询某用途所有模型 Profile |
| `PUT /api/v1/admin/model-profiles/{purpose}/{providerMode}/{profileKey}` | 保存单个 Profile |
| `POST /api/v1/admin/model-profiles/{purpose}/{providerMode}/{profileKey}/check` | 验证当前 Profile 连接 |
| `POST /api/v1/admin/model-profiles/{purpose}/{providerMode}/{profileKey}/activate` | 设为该 purpose 当前使用模型 |
| `POST /api/v1/chat/knowledge-answer` | 基于知识库证据生成回答 |
| `POST /api/v1/chat/knowledge-answer/evaluate` | 用户反馈答案有效性与关系错误 |

## 8. 性能与容量边界

| 阶段 | 目标耗时 | 说明 |
| --- | ---: | --- |
| Query Planner | <= 500ms | 本地规则优先，必要时小模型抽关键词 |
| Knowledge Retrieval | <= 1500ms | 复用 07F traversal budget，默认 maxNodes=300/maxEdges=800 |
| Evidence Pack 排序 | <= 300ms | Top 8 来源块 + Top 5 图路径 |
| Answer Generator 云端 | P95 <= 8s | 流式输出优先 |
| Answer Generator 本地 GGUF | P95 <= 20s【待实测】 | 小机器上需允许降级为证据摘要 |

## 9. 验证计划

1. 选择已入库的 MD 样本，准备 5 个问题，覆盖实体、关系、来源证据和缺失问题。
2. 对每个问题记录：命中实体、命中关系、来源块、回答引用、置信度、耗时。
3. 人工标注：答案是否正确、关系是否正确、证据是否足够、是否存在错误关联。
4. 将错误分为：切块问题、关系抽取问题、检索召回问题、排序问题、模型总结问题、提示词越界问题。
5. 优先修图谱与检索，再修回答 prompt；禁止用 prompt 掩盖错误关系。

## 10. 风险与回流

| 编号 | 风险 | 影响 | 处理 |
| --- | --- | --- | --- |
| QA-FB-001 | GGUF 运行时未确定 | 无法直接通过文件路径完成推理 | 需确认使用 llama.cpp、LM Studio、Ollama 还是 vLLM |
| QA-FB-002 | 对话模型与抽取模型混用 | 会出现配置互相覆盖和效果不可复现 | 必须先落 `ai_model_profile` 隔离模型配置 |
| QA-FB-003 | 知识库证据不足 | LLM 容易编造 | 系统必须先返回证据不足，不允许无证据回答 |
| QA-FB-004 | 本地模型回答延迟高 | 影响对话体验 | 支持流式输出、证据摘要降级、模型切换 |
