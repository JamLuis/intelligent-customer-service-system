# Unified Engineering Knowledge Graph 项目框架

## 1. 定位修正

本项目的底座不是单一 Code Graph，也不是普通 GraphRAG，而是 Unified Engineering Knowledge Graph（统一工程知识图谱），也可称为 Multi Source Engineering Graph。

它要把智慧工地监管平台中的代码、需求文档、设计文档、设备协议、部署说明、接口说明、配置、数据库、历史工单、运维日志和实时系统状态统一关联。Diagnosis Agent 不是直接在文档 chunk 上问答，而是先通过统一图谱定位工程事实，再结合 MCP 实时查询、历史案例和 LLM 推理生成证据链与结论。

## 2. 技术清单

| 模块 | 技术 | 说明 |
| --- | --- | --- |
| 图数据库 | Neo4j | 保存工程实体、关系、跨源映射、证据路径 |
| 向量检索 | PostgreSQL + pgvector | 作为语义召回补充，不替代真实关系 |
| 文档解析 | Docling / Unstructured / LlamaParse | 优先恢复标题、表格、段落、图片说明和页码结构 |
| 代码图谱 | CodeGraph | 提取仓库文件、类、方法、调用、依赖、入口 |
| AST | TreeSitter | 作为多语言语法解析基础，用于补足 CodeGraph 覆盖不足的结构 |
| Agent 编排 | LangGraph | 编排文档入图、跨源关联、诊断推理、人工确认流程 |
| MCP | Node MCP | 封装实时查询、日志查询、配置查询和受控执行工具 |
| LLM | DeepSeek / Qwen | 负责实体关系抽取、跨源验证、结论组织；复杂问题可切高阶模型 |
| 审批 | Flowable | 承载执行类动作审批、回调、超时升级和审计 |
| 主存储 | PostgreSQL | 保存任务、来源、版本、chunk、审计、图谱构建批次 |
| 缓存 | Redis | 保存任务状态、热点查询、短 TTL 实时工具结果 |

## 3. 总体分层

```text
[Source Layer]
  代码仓库 / 需求文档 / 设计文档 / 协议 PDF / 运维文档 / OpenAPI / DB Schema / 工单 / 日志 / 实时系统
        |
        v
[Source Ingestion Layer]
  文件采集 / Repo 扫描 / OpenAPI 导入 / information_schema 采集 / 工单导入 / 日志索引连接
        |
        v
[Extraction Layer]
  Document Graph Pipeline / Code Graph Pipeline / Protocol Agent / API Extract / DB Extract / Case Extract / Ops Extract
        |
        v
[Graph Build Layer]
  Entity Normalize / Conflict Detect / Cross Link Agent / Merge Agent / Evidence Source Registry
        |
        v
[Storage Layer]
  Neo4j Engineering Graph + PostgreSQL metadata + pgvector semantic supplement + Object Storage
        |
        v
[Diagnosis Runtime Layer]
  Question Classifier / Entity Resolver / Graph Locator / MCP Planner / Evidence Builder / Response Builder / Workflow Guard
        |
        v
[User Layer]
  诊断工作台 / 证据链 / 审批 / 知识回流 / 运维看板
```

## 4. 核心项目模块

| 模块编号 | 模块名 | 职责 | 主要输入 | 主要输出 |
| --- | --- | --- | --- | --- |
| UEG-001 | Source Registry | 统一登记数据源、来源版本、权限级别、解析策略 | 仓库地址、文件、接口、数据库连接、日志索引 | sourceId、sourceVersion、accessScope |
| UEG-002 | Document Graph Pipeline | 解析需求、设计、运维、部署、Excel、PPT、手册等非结构化文档 | PDF、Word、Markdown、Excel、PPT | Business Entity、Process Entity、Rule Entity、Relation |
| UEG-003 | Code Graph Pipeline | 抽取代码实体与调用关系 | wnx-web、wnx-serve、后续新项目仓库 | Controller、Service、Mapper、DTO、API、Page、CallGraph |
| UEG-004 | Protocol Graph Pipeline | 抽取设备协议实体 | 协议 PDF、Word、Excel、字段表 | Protocol Field、Metric、Unit、Alarm Rule、Threshold |
| UEG-005 | API Graph Pipeline | 抽取接口实体 | OpenAPI、Knife4j、Swagger、接口说明 | API、Parameter、DTO、Controller、Service |
| UEG-006 | Database Graph Pipeline | 抽取数据库结构实体 | information_schema、DDL、ER 文档 | Table、Column、Index、ForeignKey、Enum、Dict |
| UEG-007 | Case Graph Pipeline | 抽取历史问题与研发经验 | 工单、周报、故障记录、聊天纪要 | Symptom、Cause、Fix、Module、Owner、Evidence |
| UEG-008 | Ops Graph Pipeline | 抽取运维与日志实体 | Prometheus、Loki、Grafana、Nginx、Kafka、任务日志 | Metric、Alert、LogPattern、Trace、Job、ConsumerLag |
| UEG-009 | Entity Normalize | 统一实体命名、别名、枚举、单位、项目范围 | 各类候选实体 | canonicalEntity、alias、confidence |
| UEG-010 | Conflict Detect | 发现跨源冲突 | 同名不同义、同义不同名、版本差异 | conflictItem、reviewTask |
| UEG-011 | Cross Link Agent | 自动建立文档、代码、协议、DB、工单、日志之间的关系 | 候选实体、embedding、规则、LLM 验证 | crossSourceRelation、confidence、evidence |
| UEG-012 | Merge Agent | 合并节点和关系并写入 Neo4j | canonicalEntity、crossSourceRelation | graphNode、graphEdge、sourceTrace |
| UEG-013 | Diagnosis Agent | 消费统一图谱与实时 MCP 工具完成诊断 | 用户问题、上下文、图谱路径、实时工具结果 | rootCause、confidence、evidenceChain、actionSuggestion |

## 5. 实体模型框架

| 实体域 | 典型实体 | 示例 |
| --- | --- | --- |
| 文档实体 | Module、BusinessRule、Process、Role、Page、Field、Config、Alarm | 扬尘设备、环境监测告警、广播联动、通知流程 |
| 代码实体 | Repository、File、Class、Method、Controller、Service、Mapper、DTO、FrontendPage | AlarmController、DeviceService、alarmList.vue |
| 接口实体 | API、Endpoint、RequestParam、ResponseField、ErrorCode | /device/list、deviceId、projectId |
| 协议实体 | Protocol、Metric、Field、Unit、Threshold、AlarmTrigger | moment、力矩、吨米、超载告警 |
| 数据库实体 | Schema、Table、Column、Index、Enum、Dictionary | alarm_rule、alarm_history、alarm_type=101 |
| 工单实体 | Incident、Symptom、Cause、FixAction、Owner、ReviewResult | 设备离线、SIM 卡欠费、现场断电 |
| 运维实体 | Metric、Alert、LogPattern、TraceId、Job、ConsumerGroup | 接口 500、Kafka 消费积压、统计任务异常 |
| 实时实体 | DeviceStatus、AlarmStatus、TaskStatus、ConfigSnapshot | 在线状态、规则快照、任务状态 |

## 6. 关系模型框架

| 关系类型 | 含义 | 示例 |
| --- | --- | --- |
| TRIGGERS | 触发 | 扬尘设备异常 -> 环境监测告警 |
| DEPENDS_ON | 依赖 | 统计报表 -> alarm_statistics |
| CALLS | 调用 | Controller -> Service -> Mapper |
| QUERIES | 查询 | Mapper -> alarm_history |
| DISPLAYS | 展示 | 页面 -> 字段 |
| BELONGS_TO | 属于 | 告警规则 -> 项目 / 设备类型 |
| CONTROLS | 控制 | 配置项 -> 告警触发逻辑 |
| HAS_FIELD | 包含字段 | 协议 -> moment |
| MAPS_TO | 跨源映射 | 超载告警 -> OVERLOAD_ALARM -> alarm_type=101 |
| POSSIBLE_CAUSE | 可能原因 | 设备离线 -> SIM 卡欠费 |
| FIXED_BY | 处理方式 | SIM 卡欠费 -> 联系运营商充值 |
| OBSERVED_IN | 观测到 | 接口 500 -> Nginx error log |
| VERIFIED_BY | 被证据验证 | 根因结论 -> 日志片段 / 实时状态 / 代码路径 |

## 7. 文档入图 Pipeline

```text
PDF / Word / Markdown / Excel / PPT
  -> Docling / Unstructured / LlamaParse 结构恢复
  -> 标题层级、表格、段落、图片说明、页码、附件元数据标准化
  -> Chunk，但 chunk 只作为抽取单元，不作为最终知识形态
  -> LLM Extract 抽取实体和关系
  -> Entity Normalize 统一命名、单位、枚举和上下文
  -> Conflict Detect 发现冲突或低置信度关系
  -> Merge Agent 写入 Neo4j
  -> chunk、source、page、paragraph、hash 写入 PostgreSQL 与 pgvector
```

关键原则：不要把 PDF 直接切 chunk 后做问答。文档的价值在业务实体、规则、流程、字段和配置之间的真实关系。

## 8. 跨源关联框架

Cross Link Agent 负责把不同来源中“看起来不同、实质相同”的工程概念统一起来。

```text
候选召回：Embedding 相似度 + 别名词典 + 枚举字典 + 命名规则
  -> 规则校验：设备类型、项目范围、字段单位、枚举值、模块归属
  -> LLM 验证：判断是否同义、上下位、因果、依赖、配置映射
  -> 冲突检测：同名异义、版本冲突、字段含义冲突、单位冲突
  -> 人工复核：低置信度或高风险关系进入 reviewTask
  -> 写图：保存 MAPS_TO / DEPENDS_ON / TRIGGERS / VERIFIED_BY 等关系
```

示例：

```text
文档：超载告警
  -> 代码：OVERLOAD_ALARM
  -> 数据库：alarm_type=101 / alarm_rule
  -> 协议：moment > threshold
  -> 设备协议：塔吊协议
  -> 运维证据：告警触发日志 / 统计任务日志
```

统一后，Diagnosis Agent 才能从一句“塔吊超载告警为什么没触发”定位到协议字段、规则配置、代码路径、数据库记录、实时状态和历史案例。

## 9. Diagnosis Agent 运行框架

```text
用户问题
  -> Question Classifier 识别问题类型
  -> Entity Resolver 从统一图谱识别项目、设备、协议字段、告警、接口、页面、时间范围
  -> Graph Locator 查找相关业务链、代码链、DB 链、协议链、历史案例链
  -> MCP Planner 判断需要查询哪些实时工具
  -> Node MCP 查询设备状态、告警规则、日志、配置、任务状态
  -> Evidence Builder 合并图谱路径、文档出处、代码位置、DB 记录、实时数据、工单经验
  -> LLM Reasoner 生成根因、置信度、风险等级和下一步动作
  -> Workflow Guard 对执行动作做 L0-L5 风险分级和审批门禁
  -> Response Builder 输出可追溯证据链
```

## 10. 第一阶段落地边界

Phase 1 不追求全量智能，先把“最有价值、最容易沉淀”的工程知识链打通。

| 优先级 | 范围 | 交付内容 |
| --- | --- | --- |
| P0 | 文档图谱 | 需求、设计、运维、部署、协议文档结构恢复与实体关系抽取 |
| P0 | 代码图谱 | wnx-web 与 wnx-serve 的 Controller、Service、Mapper、页面、API 关系 |
| P0 | Cross Link | 超载告警、设备离线、统计异常、接口 500 等高频问题的跨源关联 |
| P0 | Diagnosis Agent | 支持“问题 -> 图谱定位 -> MCP 查询 -> 证据链 -> 结论”闭环 |
| P1 | 工单图谱 | 导入历史故障与研发处理经验 |
| P1 | 运维图谱 | 接入日志模式、Prometheus 告警、Grafana 看板关联 |
| P2 | 自动修复 | 仅在审批流、回滚策略、审计链完整后开放低风险动作 |
