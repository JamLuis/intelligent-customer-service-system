## 1A. 通用化原则（V0.3 必须遵守，不可违反）

1. 本系统是**通用知识图谱平台**，不内置任何业务领域本体。
2. 仅以下三类「平台保护类型」由系统下发，租户不可删除：
   - 实体类型：`SourceBlock`、`Document`、`Section`（证据与文档锚点）
   - 关系类型：`HAS_EVIDENCE`、`HAS_SECTION`、`IN_SECTION`
3. 所有业务实体类型、关系类型、图谱分类必须由**租户/项目**通过 KG-ADMIN-* 管理 API 自行注册；系统不下发任何默认业务分类、不预置 `geo-vessel` / `vessel-device` / `device-alarm` 之类的领域分类。
4. 文档中出现的设备/船舶/告警/规则/协议/接口/案例等实体词都仅为**举例说明结构与流程**，不得在 schema、seed、Java/Python 代码、前端常量、Mock 中以硬编码方式出现。
5. CHECK 约束不得枚举业务领域值（如 domain、batch_type、reason_code 由字符正则校验，业务域语义由元数据与应用层管理）。
6. 默认 seed 只产生平台保护类型；示例本体（如 `examples/graph_taxonomy_example_marine.sql`）仅供参考，不参与 init 自动加载。
7. 前端禁止把任何分类/实体/关系作为枚举写死，必须 100% 由 KG-001 与 KG-ADMIN-* 返回的数据驱动。

## 2. 核心结论

1. 知识图谱不能再以 Mock JSON 表示，必须形成三层真实存储：
   - PostgreSQL：知识源、解析块、抽取候选、构建批次、图谱资产、版本、复核任务、检索日志。
   - Neo4j：真实实体节点、关系、跨源证据、版本标签、项目/租户隔离属性。
   - pgvector：文本块、表格块、图片 OCR 块、实体描述、关系描述的语义召回索引。
2. 录入入口必须先选择图谱分类，再创建知识源。分类不是前端下拉写死，而是后端配置化管理。
3. 结构化文本与非结构化文件走同一条入图状态机，但解析策略不同。
4. LLM 只能做候选实体/关系抽取和验证，不能直接写入发布图谱。所有写入必须经过规则校验、置信度评分、冲突检测、版本化与审计。
5. 图谱检索必须支持两类查询：
   - 管理检索：按分类、实体、关系、版本、来源查看和维护历史图谱。
   - 诊断检索：给定问题上下文，召回相关子图、证据链、相邻关系和可调用 MCP 工具。
6. V0.2 最小可用目标是“真实录入 -> 真实抽取 -> 写 Neo4j -> 可按关系查询 -> 前端关系图展示 -> 可保存草稿版本”。

## 6. 核心数据流

### 6.1 结构化文本入图

```text
前端选择 graphCategoryId + contentMode=structured_text
  -> POST /api/v1/knowledge/sources
  -> Java 创建 knowledge_source + ingestion task(parse/extract/graph_build)
  -> Python 结构化解析器识别 JSON/CSV/KV/规则文本
  -> 生成 DocumentBlock / TableBlock / CandidateEntity / CandidateRelation
  -> Java 保存候选与向量
  -> 规则校验 + LLM 验证 + 冲突检测
  -> 写 graph_build_batch
  -> 写 Neo4j 草稿子图 graphVersion=draft
  -> 前端入图预览展示
  -> 管理员发布后 graph_asset.active_revision_id 生效
```

### 6.2 非结构化文件入图

```text
前端选择 graphCategoryId + 上传 file
  -> Java 保存文件到 object storage，计算 source_hash
  -> 创建 knowledge_source(status=uploaded)
  -> 创建 parse task
  -> Python Parser：按文件类型执行解析
       txt/md/log/ini/json/csv -> 文本/表格解析
       pdf/docx/xlsx -> 文档结构恢复
       jpg/png -> OCR 后进入文本解析
  -> 块级存储：blockId、pageNo、sectionPath、tableCell、rawText、hash
  -> embedding 入 pgvector
  -> 抽取候选实体/关系
  -> 进入同一图谱构建与复核流程
```

### 6.3 诊断检索

```text
用户问题 + 上下文
  -> Java 创建 SupportSession
  -> Python/Java Entity Resolver 按租户已注册的实体类型与 extractor_rules 抽取上下文实体与时间范围
  -> Graph Retrieval：Neo4j 精确实体查询 + 路径扩展
  -> Vector Retrieval：pgvector 召回相关原文块作为证据补充
  -> Evidence Join：将 Neo4j path 与 source block/page/line 绑定
  -> MCP Planner：根据图谱命中的设备、告警、协议决定实时查询工具
  -> 生成 evidenceItems + graphPaths + mcpCalls
```

## 7. 图谱分类与本体设计（通用、配置驱动）

### 7.1 设计原则

1. 分类（`graph_category`）、实体类型（`graph_entity_type`）、关系类型（`graph_relation_type`）三张表共同构成**本体元模型**；本系统只提供元模型的存储与管理能力，不内置任何业务领域本体。
2. 系统启动时**只下发平台保护类型**：实体 `SourceBlock`/`Document`/`Section`；关系 `HAS_EVIDENCE`/`HAS_SECTION`/`IN_SECTION`。
3. 所有业务分类、业务实体类型、业务关系类型必须由租户/项目通过 KG-ADMIN-* 管理 API 注册，作用域为 `(tenantId, projectId)`；不允许使用 `project_id='*'` 作为内置默认值。
4. 同一租户/项目内，`graph_category` 维度的 `entity_type_scope` / `relation_type_scope` 必须引用本租户已注册的类型；引用未注册类型应在管理 API 层报错（不在 CHECK 中硬编码）。
5. 类型名命名规则：实体类型推荐 UpperCamel（如 `MyEntity`），关系类型推荐 UPPER_SNAKE（如 `MY_RELATION`），由管理 API 做正则校验，schema 仅做最宽字符校验。
6. 「保护类型」可在管理 API 中查询但不可禁用/删除/修改 `unique_key_schema`；用于保障证据链一致性。

### 7.2 元模型字段语义（仅描述结构，不规定语义）

| 表 | 关键字段 | 语义 |
| --- | --- | --- |
| `graph_category` | `category_id`、`category_name`、`domain`、`entity_type_scope`、`relation_type_scope` | 业务分类编码、显示名、业务域标签（自由文本）、允许的实体/关系类型范围 |
| `graph_entity_type` | `entity_type`、`label`、`unique_key_schema`、`property_schema`、`extractor_rules` | 类型标识、显示名、唯一键字段名、属性 JSON schema、抽取规则（正则/词典/LLM 提示）|
| `graph_relation_type` | `relation_type`、`label`、`from_entity_types`、`to_entity_types`、`property_schema`、`inverse_relation_type` | 关系标识、显示名、允许的起/终点类型集合、属性 schema、可选反向关系 |

### 8.1 节点通用属性

所有业务节点必须包含：


### 8.2 关系通用属性

```text
relationId      string
relationType    string
tenantId        string
projectId       string
graphCategoryId string
sourceRefs      list<string>
evidenceRefs    list<string>
confidence      float
status          draft|reviewing|published|deprecated|rolled_back
revisionId      string
validFrom       datetime|null
validTo         datetime|null
createdAt       datetime
updatedAt       datetime
createdBy       string
```

### 8.3 约束与索引

```cypher
CREATE CONSTRAINT entity_unique IF NOT EXISTS
FOR (n:EngineeringEntity)
REQUIRE (n.tenantId, n.projectId, n.entityType, n.entityId) IS UNIQUE;

CREATE INDEX entity_name IF NOT EXISTS
FOR (n:EngineeringEntity)
ON (n.tenantId, n.projectId, n.name);

CREATE INDEX entity_category IF NOT EXISTS
FOR (n:EngineeringEntity)
ON (n.tenantId, n.projectId, n.graphCategoryIds);

CREATE INDEX relation_revision IF NOT EXISTS
FOR ()-[r:ENGINEERING_RELATION]-()
ON (r.tenantId, r.projectId, r.graphCategoryId, r.revisionId, r.status);
```

实现建议：业务节点同时打通用 Label `EngineeringEntity` 和租户在 KG-ADMIN-* 中注册的具体 Label（名称由租户决定，例如用户注册的 `<EntityTypeA>`），关系使用具体关系类型（例如 `[:<RELATION_A>]`），并保留 `relationType` 属性。Java backend 在写入前应检查 Label/关系名是否已在本租户 taxonomy 中注册，未注册者拒绝写入。

## 10. 文件解析设计

| sourceType | 推荐解析器 | 输出 block | 必做校验 |
| --- | --- | --- | --- |
| text/md/log/ini | Python 原生 + regex | paragraph/log/json/k-v | 编码、长度、敏感词 |
| json | Python json parser | json path block | JSON 合法性 |
| csv | pandas/csv | table row block | 表头、列数 |
| xlsx | openpyxl/pandas | sheet/table row block | sheetName、合并单元格 |
| docx | python-docx / unstructured | title/paragraph/table | 标题层级、表格 |
| pdf | Docling 优先，Unstructured 兜底 | page/title/paragraph/table/image | 页码、表格结构、失败兜底 OCR |


## 11. 抽取设计

### 11.1 抽取策略顺序

1. 规则抽取：适合结构化文本、JSON、CSV、配置、协议字段表。
2. 词典/别名抽取：设备号、船舶名、告警码、协议名、表名、接口路径。
3. LLM 抽取：用于自然语言段落、复杂表格说明、运维经验。
4. Cross Link：对候选实体做去重、合并、跨源映射。
5. Conflict Detect：发现同名异义、阈值冲突、设备绑定冲突、协议版本冲突。

### 11.2 LLM 抽取输出 Schema

LLM 只允许输出 JSON，禁止自然语言混入。

```json
{
  "entities": [
    {
      "tempId": "e1",
      "entityType": "<EntityTypeA>",
      "rawName": "<原始名称>",
      "canonicalName": "<规范名>",
      "uniqueKey": {"<keyField>":"<value>"},
      "properties": {"<prop>":"<value>"},
      "confidence": 0.88,
      "evidenceBlockIds": ["block-1"]
    }
  ],
  "relations": [
    {
      "sourceTempId": "e1",
      "targetTempId": "e2",
      "relationType": "<RELATION_A>",
      "properties": {"<prop>":"<value>"},
      "confidence": 0.84,
      "evidenceBlockIds": ["block-1"]
    }
  ]
}
```

说明：`entityType` 与 `relationType` 必须是调用方随请求传入的本租户 taxonomy 中已注册的名称，AI Service 不能凭空生出名称。

### 11.3 置信度规则

| 来源 | 初始置信度 | 加分 | 降分 |
| --- | --- | --- | --- |
| 结构化字段明确匹配 | 0.90 | 唯一键完整 +0.05 | 字段缺失 -0.10 |
| 表格行列映射 | 0.85 | 表头命中本体 +0.05 | 合并单元格不确定 -0.10 |
| LLM 文本抽取 | 0.70 | 多证据块一致 +0.10 | 只出现一次 -0.10 |
| OCR 文本抽取 | 0.60 | OCR 置信度高 +0.10 | OCR 置信度低 -0.20 |
| Cross Link 关系 | 0.65 | 规则+embedding+LLM 三者一致 +0.20 | 任一校验冲突 -0.30 |

自动接受阈值建议：

| 对象 | 自动 accepted | reviewing | rejected |
| --- | --- | --- | --- |
| 实体 | confidence >= 0.80 且唯一键完整 | 0.50 <= confidence < 0.80 | < 0.50 |
| 关系 | confidence >= 0.82 且关系类型合法 | 0.55 <= confidence < 0.82 | < 0.55 |
| 高风险关系 | 不自动发布，最高只到 reviewing | 全部人工复核 | 明显非法 |

高风险关系由租户在注册关系类型时通过 `propertySchema.riskLevel='high'`（或同类标记）声明，系统按此判断。示例（仅供参考）：任何涉及人员职责、生产控制、权限变更的关系。

## 12. 图谱构建与版本化

### 12.1 状态机

```text
knowledge_source.uploaded
  -> parsing
  -> extracted
  -> graph_ready
  -> published

knowledge_ingestion_task.pending
  -> running
  -> success / failed / canceled

graph_candidate_entity/relation.candidate
  -> accepted / reviewing / rejected / conflict / merged

graph_asset.draft
  -> reviewing
  -> published
  -> deprecated / rolled_back
```

### 12.2 写图规则

1. Java backend 是唯一写 Neo4j 发布图谱的入口。
2. Python AI Service 只返回候选图谱，不直接写 Neo4j。
3. 每次入图必须创建 `graph_build_batch`。
4. Neo4j 写入必须携带 `revisionId` 和 `status`。
5. 发布时只把 `status=published` 且 `revisionId=activeRevisionId` 的节点/关系纳入诊断检索。
6. 回滚时不删除历史节点关系，只切换 `activeRevisionId` 并把旧版本状态改为 rolled_back/deprecated。

### 12.3 草稿与发布

```text
候选图谱生成
  -> Neo4j 写入 status=draft, revisionId=draft-xxx
  -> 前端预览与人工编辑
  -> 保存草稿：updateGraphAssetDraft
  -> 管理员发布：publishOrRollbackGraph(action=publish)
  -> Java 将 draft revision 标为 published
  -> graph_asset.active_revision_id = revisionId
```

### 13.3 Cypher 示例（示例中的 Label 与关系类型均以 `<EntityTypeA>` / `<RELATION_A>` 占位，实际名称由租户注册后代入）

一跳邀居与其他关系：

```cypher
MATCH (n:EngineeringEntity {tenantId:$tenantId, projectId:$projectId, entityType:$entityType, entityId:$entityId})
OPTIONAL MATCH p1=(:EngineeringEntity)-[r:`<RELATION_A>` {status:'published'}]->(n)
OPTIONAL MATCH p2=(n)-[r2 {status:'published'}]->(:EngineeringEntity)
WHERE r2.relationType IN $allowedRelationTypes
RETURN p1, p2
LIMIT 50;
```

多跳拓展（按租户传入的实体/关系类型过滤）：

```cypher
MATCH (s:EngineeringEntity {tenantId:$tenantId, projectId:$projectId, entityType:$srcType, entityId:$srcId})
OPTIONAL MATCH p1=(s)-[r {status:'published'}]-(n:EngineeringEntity)
WHERE r.relationType IN $allowedRelationTypes
  AND n.entityType IN $allowedEntityTypes
RETURN p1
LIMIT 100;
```

关系路径查询：

```cypher
MATCH p = shortestPath(
  (s:EngineeringEntity {tenantId:$tenantId, projectId:$projectId, entityId:$sourceId})-[*1..$maxDepth]-
  (t:EngineeringEntity {tenantId:$tenantId, projectId:$projectId, entityId:$targetId})
)
WHERE ALL(r IN relationships(p) WHERE r.status = 'published' AND r.relationType IN $allowedRelationTypes)
RETURN p
LIMIT 20;
```

说明：Java backend 在拼接关系类型过滤前，必须校验 `$allowedRelationTypes` / `$allowedEntityTypes` 均是本租户已注册的类型；禁止用户输入拼接到 Cypher 中。

### 13.4 pgvector 召回

用途：当实体识别不完整或用户用自然语言描述时，先召回相关块，再从块上找实体关系。

```sql
SELECT block_id, source_id, normalized_text, metadata,
       1 - (embedding <=> :query_embedding) AS score
FROM knowledge_block
WHERE tenant_id = :tenant_id
  AND project_id = :project_id
  AND (:graph_category_id IS NULL OR metadata->>'graphCategoryId' = :graph_category_id)
ORDER BY embedding <=> :query_embedding
LIMIT 20;
```

向量召回结果不能直接作为图谱关系，只能作为证据补充或候选抽取输入。

6. 验证回滚后诊断检索只使用 active revision。
7. **验证默认 taxonomy 为空：**`GET /api/v1/graphs/taxonomy` 返回 `{categories:[], entityTypes:[仅保护类型], relationTypes:[仅保护关系]}`；在未注册业务本体前创建业务 source/candidate 应报 `ICSS-KG-400-CATEGORY_INVALID` 或 `ICSS-KG-400-ENTITY_TYPE_INVALID`。
8. **验证保护类型不可删：**调用 KG-ADMIN 删除 `SourceBlock`/`Document`/`Section`/`HAS_EVIDENCE` 等应报 `ICSS-KG-403-PROTECTED_TYPE`。

## 22. 验收标准（示例主体全部使用占位本体，验收时由租户注册后代入）

| 编号 | 场景 | 验收标准 |
| --- | --- | --- |
| AC-KG-000 | 默认 taxonomy | 初始部署后 `GET /graphs/taxonomy` 返回：`categories:[]`、`entityTypes:[SourceBlock,Document,Section]`、`relationTypes:[HAS_EVIDENCE,HAS_SECTION,IN_SECTION]` |
| AC-KG-000B | 保护类型 | 调用 KG-ADMIN-* 删除/禁用保护类型返回 `ICSS-KG-403-PROTECTED_TYPE` |
| AC-KG-000C | 租户注册本体 | 租户可通过 KG-ADMIN-* 注册任意实体类型、关系类型、分类，后续入图/检索可用。未注册名称被使用时报错 |
| AC-KG-001 | 结构化文本入图 | 以租户已注册的 `<EntityTypeA>` `<RELATION_A>` 为例，输入表达两个实体之间关系的句子，系统生成对应实体与关系 candidate |
| AC-KG-002 | 非结构化文件入图 | 上传含示例本体重要信息的 docx/pdf，系统生成租户已注册类型的实体与关系 |
| AC-KG-003 | 图谱查询 | 按 (`entityType`, `entityId`) 查询，能返回本租户邀居与路径 |
| AC-KG-004 | 证据溯源 | 点击关系能看到来源 source、block、页码/章节、原文摘要 |
| AC-KG-005 | 分类维护 | 能按租户注册的 `graphCategoryId` 筛选历史图谱 |
| AC-KG-006 | 低置信度复核 | OCR 低置信度或 LLM 不确定关系不得自动发布，进入 review task |
| AC-KG-007 | 发布版本 | 保存草稿后发布，新诊断检索只命中 published activeRevision |
| AC-KG-008 | 回滚版本 | 回滚后旧版本不再被诊断检索命中，历史仍可查看 |
| AC-KG-009 | 向量补充 | 用户模糊描述能召回相关 source block，但结论必须绑定图谱关系或标低置信度 |
| AC-KG-010 | 权限隔离 | P001 用户不能查询 P002 图谱节点、关系、原文证据 |

## 23. 不允许的实现方式

1. 不允许只把文件切 chunk 后做向量问答，必须抽实体和关系。
2. 不允许 LLM 结果直接写入发布图谱。
3. 不允许只在 PostgreSQL JSON 字段保存 nodes/edges 而不写 Neo4j。
4. 不允许前端写死图谱分类、本体、关系类型。
5. 不允许删除历史版本来“回滚”。
6. 不允许诊断检索使用 draft/reviewing 图谱。
7. 不允许没有 sourceRefs/evidenceRefs 的关系进入 published。
