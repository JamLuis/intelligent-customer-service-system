## 1A. 通用化原则（V0.3 必须遵守，不可违反）

1. 本系统是**通用知识图谱平台**，不内置任何业务领域本体。
2. 仅平台保护类型和平台中立候选类型由系统下发，租户不可删除：实体类型包括 `SourceBlock`、`Document`、`Section`、`ExtractedObject`、`ExtractedIdentifier`、`ExtractedQuantity`；关系类型包括 `HAS_EVIDENCE`、`HAS_SECTION`、`IN_SECTION`、`HAS_COMPONENT`、`HAS_IDENTIFIER`、`HAS_QUANTITY`、`HAS_VALUE`、`MENTIONS`。
3. 所有业务实体类型、关系类型、业务图谱分类必须由**租户/项目**通过 KG-ADMIN-* 管理 API 自行注册；系统不下发任何默认业务分类、不预置 `geo-vessel` / `vessel-device` / `device-alarm` 之类的领域分类。平台可下发 `uncategorized` 兜底分类，仅用于未归类来源先落库留证据，不表达任何业务本体。
4. 文档中出现的设备/船舶/告警/规则/协议/接口/案例等实体词都仅为**举例说明结构与流程**，不得在 schema、seed、Java/Python 代码、前端常量、Mock 中以硬编码方式出现。
5. CHECK 约束不得枚举业务领域值（如 domain、batch_type、reason_code 由字符正则校验，业务域语义由元数据与应用层管理）。
6. 默认 seed 只产生平台保护类型；示例本体（如 `examples/graph_taxonomy_example_marine.sql`）仅供参考，不参与 init 自动加载。
7. 前端禁止把任何分类/实体/关系作为枚举写死，必须 100% 由 KG-001 与 KG-ADMIN-* 返回的数据驱动。
8. Neo4j 物理建模仅允许一个业务 Label `:KnowledgeEntity` 与一个业务关系类型 `:RELATION`，所有 `entityType` / `relationType` 仅以**节点/关系属性**存在；禁止根据租户输入动态创建 Label / RelTypeName，避免 metadata 表膨胀与 schema cache 抖动（详见 §8）。

## 2. 核心结论

1. 知识图谱不能再以 Mock JSON 表示，必须形成三层真实存储：
   - PostgreSQL：知识源、解析块、抽取候选、构建批次、图谱资产、版本、复核任务、检索日志。
   - Neo4j：真实实体节点、关系、跨源证据、版本标签、项目/租户隔离属性。
   - pgvector：文本块、表格块、图片 OCR 块、实体描述、关系描述的语义召回索引。
2. 录入入口不得要求用户预先选择业务分类；系统先将来源落入 `uncategorized / 待归类资料` 并抽取证据块、平台中立候选实体和候选关系，后续由模型检索、自动归类建议或人工治理迁移到正式分类。分类不是前端下拉写死，而是后端配置化管理。
3. 结构化文本与非结构化文件走同一条入图状态机，但解析策略不同。
4. LLM 只能做候选实体/关系抽取和验证，不能直接写入发布图谱。所有写入必须经过规则校验、置信度评分、冲突检测、版本化与审计。
5. 图谱检索必须支持两类查询：
   - 管理检索：按分类、实体、关系、版本、来源查看和维护历史图谱。
   - 诊断检索：给定问题上下文，召回相关子图、证据链、相邻关系和可调用 MCP 工具。
6. V0.2 最小可用目标是“真实录入 -> 真实抽取 -> 写 Neo4j -> 可按关系查询 -> 前端关系图展示 -> 可保存草稿版本”。

## 6. 核心数据流

### 6.1 结构化文本入图

```text
前端选择 graphCategoryId + contentMode=structured_text
  -> POST /api/v1/knowledge/sources
  -> Java 创建 knowledge_source + ingestion task(parse/extract/graph_build)
  -> Python 结构化解析器识别 JSON/CSV/KV/规则文本
  -> 生成 DocumentBlock / TableBlock / CandidateEntity / CandidateRelation
  -> Java 保存候选与向量
  -> 规则校验 + LLM 验证 + 冲突检测
  -> 写 graph_build_batch
  -> 写 Neo4j 草稿子图 graphVersion=draft
  -> 前端入图预览展示
  -> 管理员发布后 graph_asset.active_revision_id 生效
```

### 6.2 非结构化文件入图

```text
前端选择 graphCategoryId + 上传 file
  -> Java 保存文件到 object storage，计算 source_hash
  -> 创建 knowledge_source(status=uploaded)
  -> 创建 parse task
  -> Python Parser：按文件类型执行解析
       txt/md/log/ini/json/csv -> 文本/表格解析
       pdf/docx/xlsx -> 文档结构恢复
       jpg/png -> OCR 后进入文本解析
  -> 块级存储：blockId、pageNo、sectionPath、tableCell、rawText、hash
  -> embedding 入 pgvector
  -> 抽取候选实体/关系
  -> 进入同一图谱构建与复核流程
```

### 6.3 诊断检索

```text
用户问题 + 上下文
  -> Java 创建 SupportSession
  -> Python/Java Entity Resolver 按租户已注册的实体类型与 extractor_rules 抽取上下文实体与时间范围
  -> Graph Retrieval：Neo4j 精确实体查询 + 路径扩展
  -> Vector Retrieval：pgvector 召回相关原文块作为证据补充
  -> Evidence Join：将 Neo4j path 与 source block/page/line 绑定
  -> MCP Planner：根据图谱命中的设备、告警、协议决定实时查询工具
  -> 生成 evidenceItems + graphPaths + mcpCalls
```

## 7. 图谱分类与本体设计（通用、配置驱动）

### 7.1 设计原则

1. 分类（`graph_category`）、实体类型（`graph_entity_type`）、关系类型（`graph_relation_type`）三张表共同构成**本体元模型**；本系统只提供元模型的存储与管理能力，不内置任何业务领域本体。
2. 系统启动时**只下发平台保护与平台中立候选类型**：实体 `SourceBlock`/`Document`/`Section`/`ExtractedObject`/`ExtractedIdentifier`/`ExtractedQuantity`；关系 `HAS_EVIDENCE`/`HAS_SECTION`/`IN_SECTION`/`HAS_COMPONENT`/`HAS_IDENTIFIER`/`HAS_QUANTITY`/`HAS_VALUE`/`MENTIONS`。
3. 系统启动时可下发平台级兜底分类 `uncategorized / 待归类资料`，作用域可为 `project_id='*'`；该分类仅表示“尚未归类”，其 `entity_type_scope` / `relation_type_scope` 为空，不构成业务本体。
4. 所有业务分类、业务实体类型、业务关系类型必须由租户/项目通过 KG-ADMIN-* 管理 API 注册，作用域为 `(tenantId, projectId)`；不允许使用 `project_id='*'` 作为内置业务默认值。
5. 同一租户/项目内，`graph_category` 维度的 `entity_type_scope` / `relation_type_scope` 必须引用本租户已注册的类型；引用未注册类型应在管理 API 层报错（不在 CHECK 中硬编码）。
6. 类型名命名规则：实体类型推荐 UpperCamel（如 `MyEntity`），关系类型推荐 UPPER_SNAKE（如 `MY_RELATION`），由管理 API 做正则校验，schema 仅做最宽字符校验。
7. 「保护类型」可在管理 API 中查询但不可禁用/删除/修改 `unique_key_schema`；用于保障证据链一致性。

### 7.2 元模型字段语义（仅描述结构，不规定语义）

| 表 | 关键字段 | 语义 |
| --- | --- | --- |
| `graph_category` | `category_id`、`category_name`、`domain`、`entity_type_scope`、`relation_type_scope` | 业务分类编码、显示名、业务域标签（自由文本）、允许的实体/关系类型范围 |
| `graph_entity_type` | `entity_type`、`label`、`unique_key_schema`、`property_schema`、`extractor_rules` | 类型标识、显示名、唯一键字段名、属性 JSON schema、抽取规则（正则/词典/LLM 提示） |
| `graph_relation_type` | `relation_type`、`label`、`from_entity_types`、`to_entity_types`、`property_schema`、`inverse_relation_type` | 关系标识、显示名、允许的起/终点类型集合、属性 schema、可选反向关系 |

## 8. Neo4j 设计

### 8.0 Label 与关系类型结构策略（强约束）

多租户 + 多领域场景下绝不使用动态 Label / 动态关系类型。原因：N 租户 × M EntityType 会让 Neo4j metadata 表、schema cache、index registry 爆炸，查询计划缓存命中率下降，运维不可控。

| 对象 | 存储形式 | 业务类型表达 |
| --- | --- | --- |
| 业务实体 | 固定单一 Label `:KnowledgeEntity` | 用节点属性 `entityType` 区分 |
| 平台证据 | 固定 Label `:SourceBlock` / `:Document` / `:Section` | 受保护，不可被租户覆盖 |
| 业务关系 | 固定单一关系类型 `[:RELATION]` | 用关系属性 `relationType` 区分 |
| 平台证据关系 | 固定 `[:HAS_EVIDENCE]` / `[:HAS_SECTION]` / `[:IN_SECTION]` | 受保护 |

Java `Neo4jGraphRepository` 是唯一允许拼接 Label / 关系类型的位置，且其仅能从上面表中的固定集合拼接；entityType / relationType 绝对不拼进 Cypher Label 位，只能作为属性参数传入。

### 8.1 节点通用属性

所有业务节点（`:KnowledgeEntity`）必须包含：

```text
tenantId        string
projectId       string
entityId        string  // 业务唯一 ID
entityType      string  // 租户 taxonomy 中已注册的实体类型名
name            string
aliases         list<string>
graphCategoryIds list<string>
sourceRefs      list<string>
confidence      float
status          draft|reviewing|published|deprecated|rolled_back|frozen
revisionId      string
createdAt       datetime
updatedAt       datetime
createdBy       string
```

### 8.2 关系通用属性

所有业务关系（`[:RELATION]`）必须包含：

```text
relationId      string
relationType    string  // 租户 taxonomy 中已注册的关系类型名
tenantId        string
projectId       string
graphCategoryId string
sourceRefs      list<string>
evidenceRefs    list<{blockId,weight,sourceType}>   // 参见 §11.2
confidence      float
status          draft|reviewing|published|deprecated|rolled_back|frozen
revisionId      string
validFrom       datetime|null
validTo         datetime|null
createdAt       datetime
updatedAt       datetime
createdBy       string
```

### 8.3 约束与索引

```cypher
// 唯一性：租户×项目×类型×实体 ID
CREATE CONSTRAINT entity_unique IF NOT EXISTS
FOR (n:KnowledgeEntity)
REQUIRE (n.tenantId, n.projectId, n.entityType, n.entityId) IS UNIQUE;

// 名称与别名检索
CREATE INDEX entity_name IF NOT EXISTS
FOR (n:KnowledgeEntity) ON (n.tenantId, n.projectId, n.name);

CREATE INDEX entity_aliases IF NOT EXISTS
FOR (n:KnowledgeEntity) ON (n.tenantId, n.projectId, n.aliases);

// 按类型过滤（避免全表扫描）
CREATE INDEX entity_type IF NOT EXISTS
FOR (n:KnowledgeEntity) ON (n.tenantId, n.projectId, n.entityType);

CREATE INDEX entity_category IF NOT EXISTS
FOR (n:KnowledgeEntity) ON (n.tenantId, n.projectId, n.graphCategoryIds);

// 关系上的复合索引：路径展开依赖它
CREATE INDEX relation_type IF NOT EXISTS
FOR ()-[r:RELATION]-() ON (r.tenantId, r.projectId, r.relationType, r.status);

CREATE INDEX relation_revision IF NOT EXISTS
FOR ()-[r:RELATION]-() ON (r.tenantId, r.projectId, r.revisionId, r.status);
```

### 8.4 写入与查询示例（固定 Label）

写入节点：

```cypher
MERGE (n:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityType:$entityType, entityId:$entityId})
ON CREATE SET n += $createProps
ON MATCH  SET n += $updateProps;
```

写入关系（严禁在 Cypher 中拼接 `$relationType` 为关系 Label）：

```cypher
MATCH (s:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityType:$srcType, entityId:$srcId})
MATCH (t:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityType:$tgtType, entityId:$tgtId})
MERGE (s)-[r:RELATION {relationId:$relationId}]->(t)
ON CREATE SET r += $createProps
ON MATCH  SET r += $updateProps;
```

查询（按属性 `relationType` 过滤，不需动态 Label）：

```cypher
MATCH (s:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityType:$srcType, entityId:$srcId})
      -[r:RELATION]->(t:KnowledgeEntity)
WHERE r.status = 'published'
  AND r.relationType IN $allowedRelationTypes
  AND t.entityType IN $allowedTargetTypes
RETURN s, r, t
LIMIT $limit;
```

### 8.5 平台证据子图（完全隔离）

证据侧使用单独 Label与关系，不与业务子图混用，起到助于冷热分离、避免遇到业务查询时穿透进大量证据节点：

```cypher
// 证据指向业务实体
MATCH (n:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityId:$entityId})
MATCH (b:SourceBlock {tenantId:$tenantId, projectId:$projectId, blockId:$blockId})
MERGE (n)-[:HAS_EVIDENCE {weight:$weight}]->(b);
```

## 10A. 非结构化文件 → blocks → candidates 端到端实现

本节用于回答"一个非结构化文件被上传后，系统如何一步步把它变成可追溯的 blocks，再变成可入图的 candidate 实体与 candidate 关系"。整条链路涉及 4 个进程：**前端 / Java 后端 / PostgreSQL+pgvector / Python AI Service**，外加对象存储和 Neo4j。Python AI Service 是无状态计算服务，不直接读写 Postgres / Neo4j；所有写入由 Java 后端完成，便于事务与权限收口。

### 10A.2 各进程职责切分（强约束）

| 进程 | 必须做 | 严禁做 |
| --- | --- | --- |
| 前端 | 选择 `graphCategoryId`（来自 KG-001 返回值）、上传文件、轮询任务状态、展示 blocks/candidates | 任何位置硬编码 entityType/relationType/categoryId 字符串 |
| Java 后端 | 鉴权、租户/项目隔离、对象存储、状态机、事务、Neo4j 写入、taxonomy 校验、调用 Python | 自己做正则/LLM 抽取、把 Python 返回数据原样落库不校验 |
| Python AI Service | 文件解析、句子/段落切分、embedding、Rule/Dict/LLM 抽取、normalize、conflict detect、retrieval planning | 读写 Postgres、读写 Neo4j、持有租户状态、缓存跨请求数据 |
| PostgreSQL+pgvector | 存 knowledge_source / knowledge_block / candidate_* / review_task / taxonomy；做向量召回 | 存放业务实体真实值（在 Neo4j） |
| Neo4j | 发布态实体与关系 | 候选态、未复核数据 |

### 10A.3 解析阶段（步骤 ⑥–⑫）详细规则

1. **解析器分发**：`ParserRegistry` 按 `sourceType` + 文件 MIME 选择解析器；解析器统一返回 `List[BlockEnvelope]`。`BlockEnvelope` 不含 ID、不含 tenant/project，由 Java 端补齐，保证 Python 无状态。
2. **BlockEnvelope 必备字段**：`blockType`、`rawText`、`normalizedText`、`sectionPath`、`pageNo`、`rowNo`、`colNo`、`contentHash`、`metadata{ parser, parserVersion, bbox?, ocrConfidence?, sheetName? }`。
3. **归一化（normalizedText）**：去掉控制字符、统一全/半角、保留原文行号映射；后续抽取与展示一律基于 `normalizedText`，但 `rawText` 必须保留作为证据。
4. **幂等键**：`(tenant_id, project_id, source_id, content_hash)` 唯一索引；同一文件重复解析不会双写。`content_hash = sha256(blockType + normalizedText + sectionPath + pageNo + rowNo + colNo)`，由 Python 端生成、Java 端校验。
5. **Embedding 异步化**：parse 完成即可允许进入 extract；embedding 用独立任务批量回填，避免阻塞用户。维度由 `application.yml` 的 `ai.embedding.dim` 决定，默认 1536，与 `knowledge_block.embedding vector(...)` 必须一致。
6. **失败兜底**：
   - PDF Docling 失败 → 切 Unstructured → 仍失败 → 切 OCR；任一兜底命中必须在 block `metadata.parser` 中体现实际使用的解析器。
   - 文件过大（默认 50MB）或页数超限（默认 500 页）直接进入 `parser_status=failed`，落 `error_code=ICSS-KG-422-FILE_TOO_LARGE`，**不调用 Python**，避免雪崩。

### 10A.4 抽取阶段（步骤 ⑭–⑲）详细规则

1. **三层抽取顺序固定**：先 Rule（确定性最高），再 Dictionary/Alias（已有实体回链），再 LLM（兜底）；后一层只处理前一层未覆盖的 block。每个 candidate 必须带 `extractor ∈ {rule, dict, llm}` 字段，供后续置信度计算。
2. **taxonomy 入参必须完整**：Java 端调用 `/knowledge/extract` 时必须传入：
   - 本租户的 `categories[]`（含 `entityTypeScope/relationTypeScope`）
   - `entityTypes[]`（含 `uniqueKeySchema`/`propertySchema`/`extractorRules`/`aliasPatterns`）
   - `relationTypes[]`（含 `fromEntityTypes`/`toEntityTypes`/`propertySchema`）
   - 该 source 的 `graphCategoryId`
   Python 端**只能**在该 taxonomy 内产出名称；越界视为非法输出，Java 端必须丢弃并记 `reviewReason='extractor_out_of_taxonomy'`。
3. **Rule extractor 的可注册结构**：每个 entityType 可在 taxonomy 注册 `extractorRules: [{type:"regex"|"jsonpath"|"csvHeader"|"keyValue", expression, captureMap}]`，由 Python 在运行时编译。系统不内置任何业务正则。
4. **LLM extractor 提示词模板**：模板里 placeholder 注入"当前可用 entityTypes / relationTypes / 上下文 block 文本 / 输出 JSON schema"。模板本身不含任何业务名称，**业务名称全部来自请求入参**。
5. **去重与归一（normalize 步骤 ⑱）**：
   - 同一 source 内：以 `(entityType, canonicalName)` 或 `uniqueKey` 合并 candidate，evidence 取并集。
   - 跨 source：用 `(entityType, uniqueKey)` 或 `embedding(canonicalName) cosine > 0.92` 触发"建议合并"，但不自动合并，必须生成 review task。
6. **冲突检测**：常见冲突由 Python 检出，由 Java 决定是否生成 review：
   - 同一关系实例同时由两份证据指向不同对端
   - 同一 relationType 在 taxonomy 标记 `cardinality='ONE'` 但出现多对一
   - candidate 属性值与既有 published 实体属性值不一致
   每条冲突必须带 `reasonCode` + `evidenceBlockIds[]`，进入 `graph_review_task.reason='conflict_*'`。

### 10A.5 写库阶段（步骤 ⑳–㉒）详细规则

1. **单事务**：blocks 反向回填、candidate UPSERT、review_task 插入、source 状态更新必须在同一个 Postgres 事务里完成，失败整体回滚，避免出现"candidate 已落但 source 仍 pending"的脏态。
2. **幂等 UPSERT 键**：
   - `graph_candidate_entity`: `(tenant_id, project_id, source_id, entity_type, unique_key_hash)`
   - `graph_candidate_relation`: `(tenant_id, project_id, source_id, source_candidate_id, target_candidate_id, relation_type)`
   `unique_key_hash = sha256(jsonb_canonical(uniqueKey))`。
3. **状态枚举**：candidate 状态只能在 `candidate → reviewing → accepted → published` 或 `→ rejected/merged` 流转；published 必须由 KG-BE-007 的 publish 流程改写，不允许 extract 阶段直接置 published。
4. **审计**：所有由 LLM 产出且 confidence < 自动接受阈值的 candidate 必须生成 `audit_log` 记录，字段含 `extractor`、`promptVersion`、`modelVersion`、`tokenUsage`。
5. **可观测**：每条 extract 任务结束写一条 `graph_build_batch`，记录 `source_id / blocksIn / entitiesOut / relationsOut / conflicts / durationMs / aiServiceVersion`，供前端"批次回放"与运维 dashboard。

### 10A.6 关键接口签名（仅形态，详细字段见 09J / 06_PythonAIServiceAgent任务书）

```http
POST /knowledge/parse        # Python; in: {sourceMeta, objectRef|rawText};       out: {blocks:[BlockEnvelope]}
POST /knowledge/embed        # Python; in: {blocks:[{blockId,normalizedText}]};   out: {embeddings:[{blockId,vector}]}
POST /knowledge/extract      # Python; in: {blocks, taxonomy, graphCategoryId};   out: {candidateEntities,candidateRelations}
POST /knowledge/normalize    # Python; in: {candidates, existingAliases, taxonomy}; out: {normalized,conflicts}
POST /graphs/retrieve-plan   # Python; in: {questionText, context, taxonomy};    out: {plan, vectorQueryText}
```

所有 Python 接口**无状态**：每次请求都重新接收 taxonomy 与上下文，不读 DB、不缓存租户数据，便于水平扩展与灰度。

### 10A.7 失败与恢复

| 失败位置 | 表现 | 系统行为 |
| --- | --- | --- |
| 解析超时/异常 | `parser_status=failed`、`error_code` 标记 | 任务标记 retryable；超过 maxRetry 转人工 |
| Python 返回非法 JSON / 类型越界 | extract 阶段丢弃该 batch | candidate 不入库，task 进入 `failed`，UI 显示原始错误片段（脱敏） |
| Postgres 事务失败 | candidate/review/source 全部回滚 | 任务回到 pending，可重跑；blocks 不会重复写（受唯一键保护） |
| embedding 维度不一致 | UPDATE 时报错 | embedding 任务失败，但不影响 extract；运维需调整 `ai.embedding.dim` |
| LLM provider 不可用 | extract 仅走 rule/dict 层 | 标记 `degraded=true`，给前端徽标提示"未启用 LLM"；不阻断主链路 |

### 10A.8 与其它章节的对齐

- 解析输出的 BlockEnvelope 与 `knowledge_block` 表 1:1 对齐（§9.x）。
- candidate 表与 §11.2 LLM 输出 schema 字段对齐。
- 高风险关系定义遵循 §11.3 由 taxonomy 声明，不在代码硬编码。
- Neo4j 写入仅在 publish 流程（§12）发生，extract 阶段绝不直接写 Neo4j。
- 任何步骤都必须能从 `00_输入与总控/03_项目状态总表.md` 的当前任务 ID 追溯到本节对应小节，确保中断恢复时不重做已完成步骤。

## 11. 抽取设计

### 11.1 抽取策略顺序

1. 规则抽取：适合结构化文本、JSON、CSV、配置、协议字段表（具体匹配规则由租户在 `entityType.extractorRules` 内注册，系统不内置）。
2. 词典/别名抽取：基于 taxonomy 中已注册实体的 `aliasPatterns` 与既有 canonicalName 做回链，禁止内置任何业务别名表。
3. OpenIE/LLM 抽取：用于自然语言段落、复杂表格说明、运维经验；实现采用 OpenAI-compatible Provider Adapter，可接云端大模型，也可接本地 vLLM / Ollama / LM Studio 等小模型服务。后台必须提供模型方式、服务地址、模型名称、API Key、Embedding 参数配置，并支持点击验证 `/models`、Chat 与 Embedding 调用状态。提示词模板里所有可用名称由调用方动态注入。
4. Cross Link：对候选实体做去重、合并、跨源映射，依据 `uniqueKey` 与 embedding 相似度。
5. Conflict Detect：依据 taxonomy 中 relationType 的 `cardinality / propertySchema` 与已发布数据，发现同名异义、属性冲突、基数冲突。

### 11.2 LLM 抽取输出 Schema

LLM 只允许输出 JSON，禁止自然语言混入。**evidence 仅以“带权重的对象数组”格式输出。**

```json
{
  "entities": [
    {
      "tempId": "e1",
      "entityType": "<EntityTypeA>",
      "rawName": "<原始名称>",
      "canonicalName": "<规范名>",
      "uniqueKey": {"<keyField>":"<value>"},
      "properties": {"<prop>":"<value>"},
      "confidence": 0.88,
      "evidence": [
        {"blockId": "block-1", "weight": 1.0, "sourceType": "table_cell"}
      ]
    }
  ],
  "relations": [
    {
      "sourceTempId": "e1",
      "targetTempId": "e2",
      "relationType": "<RELATION_A>",
      "properties": {"<prop>":"<value>"},
      "confidence": 0.84,
      "evidence": [
        {"blockId": "block-1", "weight": 0.9, "sourceType": "paragraph"},
        {"blockId": "block-7", "weight": 0.4, "sourceType": "ocr"}
      ]
    }
  ]
}
```

说明：

- `entityType` 与 `relationType` 必须是调用方随请求传入的本租户 taxonomy 中已注册的名称，AI Service 不能凭空生出名称。
- `evidence[].weight` 范围 0–1，推荐取值：`table_cell=1.0`、`paragraph=0.85`、`table_caption=0.7`、`ocr=0.4`、`code_comment=0.5`。后续冲突仕裁与 Evidence 排序都以 `weight` 优先、时间次优。
- `sourceType` 是枚举：`title|paragraph|table_cell|table_caption|list_item|code|json_field|csv_cell|ocr|kv_pair`。Java 端不使用无枚举值。
- 代码中不会冗余保留 `evidenceBlockIds` 字段；如需调用方兼容，由 Python 端提供 `evidenceBlockIds = [e.blockId for e in evidence]` 的推导视图，不落库。

### 11.3 置信度规则

| 来源 | 初始置信度 | 加分 | 降分 |
| --- | --- | --- | --- |
| 结构化字段明确匹配 | 0.90 | 唯一键完整 +0.05 | 字段缺失 -0.10 |
| 表格行列映射 | 0.85 | 表头命中本体 +0.05 | 合并单元格不确定 -0.10 |
| LLM 文本抽取 | 0.70 | 多证据块一致 +0.10 | 只出现一次 -0.10 |
| OCR 文本抽取 | 0.60 | OCR 置信度高 +0.10 | OCR 置信度低 -0.20 |
| Cross Link 关系 | 0.65 | 规则+embedding+LLM 三者一致 +0.20 | 任一校验冲突 -0.30 |

自动接受阈值建议：

| 对象 | 自动 accepted | reviewing | rejected |
| --- | --- | --- | --- |
| 实体 | confidence >= 0.80 且唯一键完整 | 0.50 <= confidence < 0.80 | < 0.50 |
| 关系 | confidence >= 0.82 且关系类型合法 | 0.55 <= confidence < 0.82 | < 0.55 |
| 高风险关系 | 不自动发布，最高只到 reviewing | 全部人工复核 | 明显非法 |

高风险关系由租户在注册关系类型时通过 `propertySchema.riskLevel='high'`（或同类标记）声明，系统按此判断。示例（仅供参考）：任何涉及人员职责、生产控制、权限变更的关系。

## 12. 图谱构建与版本化

### 12.1 状态机

```text
knowledge_source.uploaded
  -> parsing
  -> extracted
  -> graph_ready
  -> published

knowledge_ingestion_task.pending
  -> running
  -> success / failed / canceled

graph_candidate_entity/relation.candidate
  -> accepted / reviewing / rejected / conflict / merged / frozen

graph_asset.draft
  -> reviewing
  -> published
  -> deprecated / rolled_back

# 节点 / 关系发布后的可选 frozen 屏障
KnowledgeEntity / RELATION (status):
  published -> frozen     // 人工“锁定”：freeze API，需 graph:freeze 权限
  frozen    -> published  // 仅能人工 unfreeze API，需 graph:unfreeze 权限
```

`frozen` 语义（强约束）：

1. normalize / Canonical Resolver / auto-merge 任意步骤遇到 frozen 节点或关系必须跳过，仅记录 `cross_link_hint` 供人工参考。
2. 后续 extract batch 如果产生与 frozen 节点冲突的 candidate，应进入 `conflict_*` review task 而不是直接覆盖。
3. rollback / republish 不能减一个节点或关系脱离 frozen，只能走人工 unfreeze 。
4. 面向检索：frozen 仍可被诊断检索命中（认为与 published 同等可信），但响应包体上需带上状态标识供前端显示锁形徽标。

### 12.2 写图规则

1. Java backend 是唯一写 Neo4j 发布图谱的入口。
2. Python AI Service 只返回候选图谱，不直接写 Neo4j。
3. 每次入图必须创建 `graph_build_batch`。
4. Neo4j 写入必须携带 `revisionId` 和 `status`。
5. 发布时只把 `status=published` 且 `revisionId=activeRevisionId` 的节点/关系纳入诊断检索。
6. 回滚时不删除历史节点关系，只切换 `activeRevisionId` 并把旧版本状态改为 rolled_back/deprecated。

### 12.3 草稿与发布

```text
候选图谱生成
  -> Neo4j 写入 status=draft, revisionId=draft-xxx
  -> 前端预览与人工编辑
  -> 保存草稿：updateGraphAssetDraft
  -> 管理员发布：publishOrRollbackGraph(action=publish)
  -> Java 将 draft revision 标为 published
  -> graph_asset.active_revision_id = revisionId
```

#### 13.2A Traversal Budget（强约束）

在 Neo4j 节点 10w / 关系 30w 规模下，任何 `[*1..N]` 未带兴趣过滤的查询都可能出现"路径爆炸"导致单查询拖垮集群。本节为所有多跳求路 / 邻居拓展 / 路径检索接口定义统一预算调度：

1. Java backend 实现 BFS 走 Neo4j 时，必须记录 `visitedNodes/visitedEdges`，超限立即截断并设 `truncated=true`，把已收集的子集返回。
2. 未配权的低价值关系（如 `HAS_EVIDENCE`）不参与多跳展开，仅在末端节点按需拉取（避免诊断检索把整本文档的证据节点全拽出来）。
3. Cypher 必须携 `LIMIT $maxEdges` / `LIMIT $maxNodes` / `$maxFanOutPerNode`，不允许未带 LIMIT 的多跳查询上线。
4. 调用方未传 budget 时使用默认值（300/800/5/80/1500ms）；调用方传入的值经 `min(传入, 默认上限)` 后采用，禁止外部放大。

### 13.3 Cypher 示例（固定 Label `KnowledgeEntity` + 固定关系 `RELATION` + 属性过滤；示例中 `<EntityTypeA>` / `<RELATION_A>` 为租户 taxonomy 占位）

一跳邻居（带 traversal budget）：

```cypher
MATCH (n:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityType:$entityType, entityId:$entityId})
OPTIONAL MATCH p1=(m:KnowledgeEntity)-[r:RELATION {status:'published'}]->(n)
  WHERE r.relationType IN $allowedRelationTypes
OPTIONAL MATCH p2=(n)-[r2:RELATION {status:'published'}]->(t:KnowledgeEntity)
  WHERE r2.relationType IN $allowedRelationTypes
    AND t.entityType IN $allowedEntityTypes
WITH n, collect(DISTINCT p1)[0..$maxFanOutPerNode] AS inPaths,
        collect(DISTINCT p2)[0..$maxFanOutPerNode] AS outPaths
RETURN n, inPaths, outPaths
LIMIT $maxNodes;
```

多跳拓展（按租户传入的实体/关系类型过滤 + 硬上限）：

```cypher
MATCH (s:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityType:$srcType, entityId:$srcId})
MATCH p = (s)-[rels:RELATION*1..$maxDepth]-(n:KnowledgeEntity)
WHERE ALL(r IN rels WHERE
        r.status IN ['published','frozen']
    AND r.relationType IN $allowedRelationTypes)
  AND ALL(x IN nodes(p) WHERE x.entityType IN $allowedEntityTypes)
RETURN p
LIMIT $maxNodes;
```

关系路径查询（shortestPath + budget）：

```cypher
MATCH (s:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityId:$sourceId})
MATCH (t:KnowledgeEntity {tenantId:$tenantId, projectId:$projectId, entityId:$targetId})
MATCH p = shortestPath((s)-[rels:RELATION*1..$maxDepth]-(t))
WHERE ALL(r IN rels WHERE
        r.status IN ['published','frozen']
    AND r.relationType IN $allowedRelationTypes)
RETURN p
LIMIT $maxEdges;
```

说明：

1. 所有 `$allowedRelationTypes` / `$allowedEntityTypes` 必须是本租户已注册的类型，由 Java backend 在拼接前校验；用户输入不得拼接进 Cypher。
2. 上述查询必须携 `$maxDepth/$maxNodes/$maxEdges/$maxFanOutPerNode` 参数（§13.2A），不允许走缺省。
3. `status` 过滤同时允许 `published` 与 `frozen`；draft / reviewing / rolled_back / deprecated 绝不入诊断检索。

### 13.4 Hybrid Retrieval（pgvector + BM25 + GraphBoost）

纯向量召回对于"型号、错误码、代码片段、人名"类强关键词查询表现差，必须与全文检索、图增益融合。Java 后端在 GraphSearchService 内职责融合，调用 Python `/graphs/retrieve-plan` 只用于生成检索计划（vectorQueryText / keywords / 另需拉取的关系类型）。

#### 13.4.1 定义

```text
HybridScore = 0.45 * VectorScore
            + 0.35 * BM25Score
            + 0.20 * GraphBoost
          [+ 0.05 * RecencyScore]   // 可选：对 metadata.eventTime / updatedAt 加权
```

- VectorScore = `1 - (embedding <=> $query_embedding)`。
- BM25Score = PostgreSQL `ts_rank_cd(to_tsvector(normalized_text), plainto_tsquery($keywords))` 后归一化到 [0,1]。
- GraphBoost = 该 block 是否为已命中实体的证据（0.6）、是否与已命中路径同一 source（0.4）的加总，上限 1。
- RecencyScore = `exp(-Δt / τ)`，默认 `τ=30 天`；仅在调用方开启 `recencyAware=true` 时生效。

权重可由 `application.yml → graph.search.hybrid.weights` 调，但总和必须为 1。

#### 13.4.2 表与索引

需为全文检索增建索引，随 §9.4 一起迁移：

```sql
ALTER TABLE knowledge_block
  ADD COLUMN IF NOT EXISTS ts tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', coalesce(normalized_text,''))) STORED;

CREATE INDEX IF NOT EXISTS idx_knowledge_block_ts
  ON knowledge_block USING GIN (ts);
```

#### 13.4.3 召回 SQL（三路并行，后在应用层加权合并）

```sql
-- 向量召回（embedding_model / embedding_version 必须与查询使用的模型一致，不一致不纳入）
SELECT block_id, source_id, normalized_text, metadata,
       1 - (embedding <=> :query_embedding) AS vector_score
FROM knowledge_block
WHERE tenant_id = :tenant_id
  AND project_id = :project_id
  AND embedding_model = :embedding_model
  AND embedding_version = :embedding_version
  AND (:graph_category_id IS NULL OR metadata->>'graphCategoryId' = :graph_category_id)
ORDER BY embedding <=> :query_embedding
LIMIT :vector_limit;

-- BM25 召回
SELECT block_id, source_id, normalized_text, metadata,
       ts_rank_cd(ts, plainto_tsquery('simple', :keywords)) AS bm25_score
FROM knowledge_block
WHERE tenant_id = :tenant_id
  AND project_id = :project_id
  AND ts @@ plainto_tsquery('simple', :keywords)
ORDER BY bm25_score DESC
LIMIT :bm25_limit;
```

#### 13.4.4 与图谱的关系

- Hybrid 召回负责提供"证据候选"，绝不直接作为关系写进图谱。
- Java 后端将 HybridScore Top-K 中的 block 反向查出 `KnowledgeEntity` 邻居，作为诊断响应的 `vectorEvidence`；同时由该 block 命中的 entityId 反哺为 `matchedEntities`，走 §13.3 多跳查询。
- Hybrid 召回仍遵守 §13.2A Traversal Budget（反查邻居同样使用 `$maxFanOutPerNode/$maxNodes`）。

#### 13.4.5 不允许的作法

- 不允许纯向量返回结论。
- 不允许跨 embedding 模型/版本合并召回。
- 不允许在未提供 `keywords` 的情况下跳过 BM25 路径。如果 Python `/graphs/retrieve-plan` 未抽取出关键词，需退化为 `simple_tokenize(questionText)` 后照常走 BM25。

| graph_build_duration_ms | 写图耗时 | P95 < 10s/1000 节点以内 |
| candidate_accept_rate | 自动接受率 | 初期 40%-70% |
| review_task_count | 待复核数量 | 不得长期堆积 |
| graph_query_p95 | 图谱查询耗时 | P95 < 800ms/3 跳以内 |
| vector_query_p95 | 向量查询耗时 | P95 < 500ms/20条以内 |
| diagnosis_graph_hit_rate | 诊断图谱命中率 | 按高频问题逐步提升 |
| path_cache_hit_ratio | 路径缓存命中率（Redis Key: `kg:path:{tenant}:{src}:{dst}:{depth}`） | 热点提问下 > 60% |
| neighbor_cache_hit_ratio | 邻居缓存命中率（Redis Key: `kg:neighbor:{tenant}:{entity}:{depth}:{relTypes}`） | > 50% |
| evidence_cache_hit_ratio | 证据缓存命中率（Redis Key: `kg:evidence:{tenant}:{entity\|relation}:{id}`） | > 70% |
| hybrid_retrieval_recall_at_k | Hybrid 召回@K 与人工判定金标的召回率 | 随现场可调 |

默认缓存策略（V0.2 可先不启用，仅作为接口占位）：TTL=5min；发布 / 回滚 / unfreeze 任一 graph_asset 动作触发 `kg:*:{tenant}:*` 刷新，Redis Pub/Sub 广播。严禁不带失效机制的常驻缓存，避免发布后查到旧图。

日志要求：每个 sourceId、batchId、graphId、revisionId、queryId 必须能串联。

## 20. 容量与性能假设

【假设】V0.2 本地/测试环境目标：

| 项 | 数值 |
| --- | --- |
| 知识源数量 | 1,000 份以内 |
| 单文件大小 | 文本/Office/PDF <= 50MB，图片 <= 20MB |
| Neo4j 节点 | 100,000 以内 |
| Neo4j 关系 | 300,000 以内 |
| 单次管理查询 | 1-3 跳，返回 <= 500 节点/关系 |
| 诊断检索 | P95 3 秒内完成图谱+向量召回 |
| 并发录入任务 | 2-5 个 |
| 并发诊断查询 | 20 QPS 以内 |

超过以上规模时需要引入任务队列、批量写图、Neo4j 读写分离和更严格分页。

## 23. 不允许的实现方式

1. 不允许只把文件切 chunk 后做向量问答，必须抽实体和关系。
2. 不允许 LLM 结果直接写入发布图谱。
3. 不允许只在 PostgreSQL JSON 字段保存 nodes/edges 而不写 Neo4j。
4. 不允许前端写死图谱分类、本体、关系类型。
5. 不允许删除历史版本来“回滚”。
6. 不允许诊断检索使用 draft/reviewing 图谱。
7. 不允许没有 sourceRefs/evidenceRefs 的关系进入 published。
