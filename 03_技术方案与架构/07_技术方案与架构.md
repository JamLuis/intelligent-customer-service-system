# Intelligent Customer Service System 技术方案与架构

## 1. 方案概述

- 目标：围绕“多源工程知识入图 -> 跨源实体关联 -> 图谱定位 -> MCP 实时查询 -> 诊断证据链 -> 审批执行 -> 知识回流”建立统一工程知识图谱驱动的诊断平台。
- 约束：
	- 一期必须快速上线，优先减少研发被打断，而不是一次性做成完整自治系统。
	- 需要低侵入接入 wnx-web 与 wnx-serve，不直接替换其核心业务能力。
	- 最大信息源是非结构化工程文档，不能只做代码图谱或 PDF 直接 chunk 问答。
	- 任何执行类动作不能由 LLM 直接触发，必须通过审批流和受控工具层。
	- 当前未拿到完整的权限复用方案、实时接口清单、审批归属与审计留存期，相关项按【假设】推进并登记回流。
- 推荐方案：采用“Unified Engineering Knowledge Graph + Diagnosis Agent + Node MCP + Workflow Guard”的分层方案。Neo4j 承载真实工程关系，PostgreSQL + pgvector 作为元数据与语义补充，Docling / Unstructured / LlamaParse 负责文档结构恢复，CodeGraph / TreeSitter 负责代码结构抽取，LangGraph 编排抽取、归一、跨源关联与诊断流程。
- 不采用方案：
	- 不采用一期全量微服务：研发和运维成本过高，不利于 1 到 1.5 月快速落地。
	- 不采用一期 Milvus：部署和运维复杂度高于当前阶段收益。
	- 不采用“PDF 直接切 chunk + 向量问答”作为主方案：会丢失业务规则、流程、字段、协议和代码之间的真实关系。
	- 不采用单一 Code Graph：智慧工地场景的关键知识大量存在于需求文档、协议、部署说明、运维记录和工单中。
	- 不采用 LLM 直接访问业务系统：无法满足审批、审计与安全要求。
	- 不采用前端直连 wnx-web 或 wnx-serve：会导致权限、审计和诊断流程失控。

## 2. 系统边界

- 本系统负责：
	- 问题接入、问题分类、实体抽取、追问补齐。
	- 多源数据采集、文档结构恢复、实体关系抽取、实体归一、冲突检测、跨源关联。
	- Graph 检索、语义补充检索、MCP 工具编排、证据汇聚。
	- 诊断结论生成、证据链展示、建议动作分级。
	- 工单/审批单生成、审批流对接、执行前后审计。
	- 知识案例沉淀、知识检索、案例复用、图谱增量更新。
- 外部系统负责：
	- wnx-web 提供既有项目、设备、用户、权限、告警页面上下文候选能力。
	- wnx-serve 提供设备状态、告警规则、日志、任务状态等查询能力。
	- LLM 厂商提供语义理解与推理能力。
	- 审批系统或 Flowable 提供流程状态机与审批回调能力。
- 交互边界：
	- 前端只访问本系统网关，不直接调用外部业务平台。
	- 诊断编排服务只通过 MCP 工具层访问外部实时系统。
	- 执行类动作只能通过审批流批准后再进入工具执行通道。

## 3. 模块拆分

| 模块 | 职责 | 输入 | 输出 | 依赖 |
| --- | --- | --- | --- | --- |
| Frontend Console | 问题输入、诊断展示、审批、知识查询 | 用户问题、会话上下文 | 页面状态、工单/审批提交 | Gateway |
| API Gateway | 统一鉴权、路由、限流、审计入口 | Web 请求、Token | 内部服务调用 | Auth、Diagnosis Orchestrator |
| Diagnosis Core | 编排诊断全流程 | 会话、实体、工具结果 | 诊断案例、证据链、建议动作 | Graph、RAG、MCP、LLM |
| Question Classifier | 识别问题类型 | 问题文本 | issueCategory | LLM Adapter、规则库 |
| Entity Extractor | 识别项目、设备、时间、告警类型 | 问题文本、上下文 | 结构化实体 | LLM Adapter、词典 |
| Planner | 生成 Graph/MCP/RAG 查询计划 | 问题类型、实体 | toolPlan、graphPlan、ragPlan | 规则、模型配置 |
| Evidence Builder | 汇聚图谱、向量、实时查询证据 | 图谱结果、RAG 结果、工具结果 | evidenceItems | Graph、RAG、MCP |
| Response Builder | 生成根因、置信度、建议动作 | evidenceItems、风险策略 | 诊断结论、风险等级 | LLM Adapter、策略引擎 |
| Source Registry | 登记数据源、来源版本、权限级别 | 仓库、文档、接口、DB、日志 | sourceId、sourceVersion | PostgreSQL、对象存储 |
| Document Graph Pipeline | 恢复文档结构并抽取业务实体关系 | PDF、Word、Markdown、Excel、PPT | Business Entity、Relation | Docling、Unstructured、LLM |
| Code Graph Pipeline | 抽取代码实体与调用关系 | 研发代码仓库 | Controller、Service、Mapper、Page、CallGraph | CodeGraph、TreeSitter |
| Protocol/API/DB/Case/Ops Pipelines | 抽取协议、接口、数据库、工单、运维实体 | 协议、OpenAPI、information_schema、工单、日志 | Protocol/API/DB/Case/Ops Entity | LLM、规则、连接器 |
| Cross Link Agent | 建立跨源实体关联 | 候选实体、embedding、规则、LLM 验证 | MAPS_TO、DEPENDS_ON、VERIFIED_BY | pgvector、Neo4j、LLM |
| Graph Layer | 保存业务关系图 | 协议文档、知识抽取、案例沉淀 | 图节点与关系 | Neo4j |
| RAG Layer | 保存知识切片与向量 | 文档、案例、手册 | chunk 检索结果 | PostgreSQL、pgvector |
| MCP Layer | 查询实时业务数据与受控执行 | 工具调用请求 | 结构化查询结果、执行结果 | wnx-web、wnx-serve |
| Workflow Layer | 审批、回调、执行前门禁 | 审批申请、审批结果 | 审批状态、执行许可 | Flowable、MCP |
| Observability Layer | 指标、日志、审计、链路追踪 | 服务日志、事件、指标 | 查询看板、告警 | Prometheus、Loki、Grafana |

## 4. 核心技术设计

- 前端设计：
	- 采用 Vue3 + Vite + Element Plus + Pinia + Axios + ECharts。
	- 一期采用独立工作台，路由包含 dashboard、diagnosis、device、alarm、knowledge、approval、history。
	- 诊断过程采用 SSE 推送阶段性状态，不为一期引入 WebSocket 双向复杂性。
- 后端设计：
	- 网关采用 Spring Cloud Gateway，负责统一入口、鉴权转发、限流、审计埋点。
	- 核心编排采用 Spring Boot 模块化单体，内部模块拆为 diagnosis-core、question-classifier、entity-extractor、planner、evidence-builder、response-builder。
	- Workflow 一期先预留独立层，二期接入 Flowable 审批流引擎。
- 缓存设计：
	- Redis 用于会话热点缓存、工具结果短 TTL 缓存、限流计数、SSE 状态存储。
	- 设备状态/规则类查询默认缓存 TTL 30 秒，【假设】可由业务再确认。
- 消息/异步设计：
	- 一期不引入独立 MQ，使用 PostgreSQL outbox 表 + Spring Scheduler 处理知识沉淀、审计回写和重试任务。
	- 当异步事件吞吐超过每秒 200 条或审批/知识回写出现明显积压时，再演进到独立消息队列。
- 文档与图谱构建设计：
	- 运维文档、协议手册、需求设计文档、部署说明、案例附件、导出报告统一存对象存储；开发环境可用 MinIO，生产可映射到 S3/OSS 兼容服务。
	- 文档先用 Docling / Unstructured / LlamaParse 做结构恢复，再以 chunk 作为抽取单元，最终沉淀为实体和关系。
	- Cross Link Agent 使用 embedding 候选召回、规则校验、LLM 验证和人工复核，把“超载告警 / OVERLOAD_ALARM / alarm_type=101 / moment > threshold / 塔吊协议”统一成可追溯链路。
	- 所有下载通过鉴权代理或签名 URL 控制，避免外链裸露。
- 安全设计：
	- 统一由网关执行身份校验、Token 传递、接口限流和黑白名单。
	- 查询类与执行类工具分离，执行类必须带审批单号和审计上下文。
	- LLM 不持有生产写权限，所有工具由 MCP 层白名单封装。
- 性能设计：
	- 普通诊断首屏结论目标 P95 10 秒，复杂诊断阶段性结果目标 P95 30 秒。
	- 每次诊断默认最多编排 8 个工具调用；单工具超时 3 秒，最多重试 1 次，只对只读操作生效。
	- Graph 与 RAG 查询合并后先形成证据草稿，再触发 LLM，总体减少模型调用次数。

## 5. 异常与降级

| 场景 | 风险 | 降级策略 | 恢复策略 |
| --- | --- | --- | --- |
| Graph Layer 不可用 | 业务关系链缺失，定位准确率下降 | 仅走 RAG + MCP 查询，标记图谱证据缺失 | Graph 恢复后补跑图谱索引与案例关系修复 |
| RAG Layer 不可用 | 无法命中历史案例和文档知识 | 仅走 Graph + MCP + 人工规则，置信度下调 | 向量库恢复后重新执行 embedding 回填 |
| MCP 工具超时 | 实时证据不足 | 降级为静态知识答复并明确“实时数据暂不可用” | 工具恢复后允许用户点击“重新诊断” |
| LLM 提供方异常 | 无法完成抽取或结论整合 | 回退到规则模板和固定追问模板，仅输出有限结论 | 切换备用模型供应商或重试 |
| 文档解析质量不足 | 结构、表格、流程和字段抽取不完整 | 降级为人工复核任务，低置信度关系不入主图 | 调整解析策略并重跑 sourceVersion |
| 跨源关联冲突 | 同一实体在文档、代码、DB、协议中含义不一致 | 进入 Conflict Detect 与人工复核，不用于自动诊断 | 复核后写入 canonicalEntity 与别名规则 |
| Workflow 不可用 | 执行类动作无法审批 | 仅允许生成待处理工单，不允许执行 | 审批流恢复后补发待审单 |
| 上游接口变更 | 工具调用失效或数据字段不兼容 | 工具层熔断并提示具体上游故障 | 更新契约映射并补充回归测试 |
