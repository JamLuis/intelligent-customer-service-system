# Intelligent Customer Service System 数据库设计

## 1. 文档信息

- 设计阶段：V0.1 P0 数据库设计
- 数据库类型：PostgreSQL 16 + pgvector，关系图谱使用 Neo4j 独立存储
- 设计边界：支撑可解释问答闭环、基础知识录入、MCP 能力管理、执行日志、路径反馈
- 不包含范围：真实生产写操作执行表、完整审批流编排表、复杂双人图谱审核流
- 上游依据：04C 权限矩阵与状态枚举、07_Gate冻结评审清单、00_数据库API设计启动输入

## 2. 总体设计原则

1. 主键统一采用 `uuid`，默认 `gen_random_uuid()`，便于多服务生成和后续跨系统同步。
2. 多租户隔离采用行级隔离，核心业务表均保留 `tenant_id`、`project_id`，查询必须以授权项目范围过滤。
3. V0.1 不启用数据库物理外键，采用应用层约束 + 索引约束，避免 Mock/Adapter 阶段数据源不稳定导致联调阻塞。
4. 状态枚举值必须与 04C 一致，使用 `varchar` + `CHECK` 约束表达，避免新增枚举值时需要重建 PostgreSQL enum 类型。
5. 审计字段统一为 `created_at`、`updated_at`、`created_by`、`updated_by`、`deleted_at`；业务删除默认软删除。
6. 大体量日志类表按时间归档，`execution_trace`、`execution_trace_step`、`mcp_call_log`、`audit_log` 在线留存 180 天。
7. JSONB 仅用于结构变化快的图谱路径、MCP 输入输出、抽取结果、Mock 返回摘要；核心过滤字段必须独立列化。

## 3. ER 模型总览

```text
support_session 1 --- N diagnostic_case 1 --- N execution_trace 1 --- N execution_trace_step
												   |
												   +--- N mcp_call_log --- 1 mcp_capability

knowledge_source 1 --- N knowledge_ingestion_task
knowledge_source 1 --- N graph_build_batch 1 --- N graph_asset 1 --- N graph_revision

route_template 1 --- N route_evaluation
execution_trace N --- 0/1 route_template
diagnostic_case 1 --- N route_evaluation

all business tables --- N audit_log by object_type/object_id
```

## 4. 数据模型总览

| 表名 | 业务含义 | 主键 | 核心关系 | 备注 |
| --- | --- | --- | --- | --- |

| diagnostic_case | 诊断案例 | case_id | N-1 support_session，1-N execution_trace | 根因、证据摘要、风险等级 |

| mcp_call_log | MCP 调用日志 | call_id | N-1 execution_trace，N-1 mcp_capability | 记录工具调用与脱敏返回 |
| knowledge_source | 知识源 | source_id | 1-N knowledge_ingestion_task / graph_build_batch | 文件、图片、文本入口 |
| knowledge_ingestion_task | 知识入图任务 | task_id | N-1 knowledge_source | 解析、OCR、抽取、入图任务 |
| graph_build_batch | 图谱构建批次 | batch_id | N-1 knowledge_source，1-N graph_asset | 批次回滚粒度 |
| graph_asset | 图谱资产 | graph_id | N-1 graph_build_batch，1-N graph_revision | Neo4j 子图元数据 |
| graph_revision | 图谱版本 | revision_id | N-1 graph_asset | 版本发布、废弃、回滚记录 |
| mcp_capability | MCP 能力 | capability_id | 1-N mcp_call_log / mcp_capability_status_log | 能力边界、schema、风险等级 |
| mcp_capability_status_log | MCP 能力状态日志 | status_log_id | N-1 mcp_capability | 启停、异常、退役留痕 |

| route_evaluation | 路径评估 | evaluation_id | N-1 route_template / diagnostic_case / execution_trace | 答案反馈和重建触发 |
| audit_log | 审计日志 | audit_id | 逻辑关联 object_type/object_id | 敏感操作、导出、启停留痕 |

## 9. 迁移与回滚

- 迁移方式：V0.1 为新建系统，采用初始化建表 SQL；后续通过版本化 migration 管理。
- 兼容策略：真实 wnx 接入前，所有外部字段保留 `external_*` 和 `source_system`，避免替换 Adapter 时改表。
- 回滚方案：建表阶段可按表逆序删除；图谱数据通过 `graph_build_batch` 和 `graph_revision` 做业务回滚，PostgreSQL 元数据不物理删除。
- 数据修复：状态异常通过审计日志和状态日志恢复，禁止直接修改历史 MCP 原始返回。
